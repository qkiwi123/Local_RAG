### 2.1 已确认的目标

- 测试语料继续保持恰好 1000 篇文档，不把新增 20 道不可回答题对应的上游 gold 文档加入 corpus。

## 5. 已完成操作：100 题和 1000 篇文档的构建

### 5.1 为什么先选题再反向选文档

直接从大文档库随机取 1000 篇，再寻找其中能回答的问题，无法稳定控制题目数量、单文档题与多文档题比例，也难以证明 gold 文档确实在 corpus 中。因此采用：

1. 从上游 QA 中确定性选择约 100 道题。
2. 根据每道题的 `news*` 反向收集必须文档。
3. 对 gold 文档按规范化文本 hash 去重。
4. 从固定文档分片补充 non-gold 文档，直到 corpus 恰好为 1000 篇。

这样既能保证可回答题所需文档在 corpus 中，又能用大量非 gold 文档模拟真实检索干扰。

### 5.2 题目选择规则

构建器为 `eval/crud_rag_1000/prepare_dataset.py`，固定 seed 为 `20260819`。目标分布为：

- `questanswer_1doc`：34 题
- `questanswer_2docs`：33 题
- `questanswer_3docs`：33 题

选择前过滤：

- 缺失 ID；
- 缺失问题；
- 缺失答案；
- 缺失需要的 `news*` 文本；
- 同一题内部的 gold 文档重复；
- 规范化后问题重复。

过滤后的有效候选数分别为 800、789、783。每类候选按以下键排序后取固定数量：

```text
SHA-256(seed | category | upstream ID | normalized question)
```

因此只要上游固定文件、seed 和代码不变，选择结果就不依赖机器时间或文件系统遍历顺序。

### 5.3 gold 文档和 distractor 的生成

100 道题理论上涉及 199 份 evidence；对 `news*` 规范化并按 SHA-256 去重后，得到 193 篇唯一 gold 文档，写入：

```text
eval/crud_rag_1000/corpus/support/
```

文件名使用规范化正文 SHA-256 的前 16 位，例如：

```text
support/9d0f610b32515cab.txt
```

其余 807 篇文档从固定分片 `documents_dup_part_1_part_1` 顺序扫描得到，写入：

```text
eval/crud_rag_1000/corpus/distractor/
```

补充文档过滤规则包括：

- 不能与 gold 或已选 distractor 正文 hash 完全相同；
- 文本长度不能少于 80 字符；
- 使用字符 5-gram SimHash，与 gold 和已选 distractor 的汉明距离必须大于 5。

实际扫描 811 条，接受 807 条，4 条因近重复规则被拒绝。最终组成：

| 类型 | 数量 |
|---|---:|
| support/gold 文档 | 193 |
| non-gold distractor | 807 |
| 总文档 | 1000 |

需要保留一个事实边界：`distractor` 只表示“不是这 100 道题声明的 gold，并通过了去重规则”，不等于已经人工证明它与所有问题语义无关。

### 5.4 evidence 生成

每个 gold 文档需要生成 Dataset v3 可定位的 evidence。构建器将文档拆成句子窗口，使用字符二元组重合度评分：

```text
2 × answer bigram overlap + 1 × question bigram overlap
```

优先选择唯一的单句或最多三句窗口，允许的候选长度为 20 至 500 字符。当前 199 条 evidence 都找到了唯一窗口，没有使用整篇文档 fallback。

这套方法保证 evidence 可重复生成和定位，但并不等于人工证明窗口长度最适合检索指标；后续发现的跨 chunk 误判正说明需要区分“gold 文档命中”和“完整 evidence 字符串被单个 chunk 包含”。

从仓库根目录重建当前基线的命令为：

```powershell
.\.venv\Scripts\python.exe eval\crud_rag_1000\prepare_dataset.py --build
.\.venv\Scripts\python.exe -m eval.dataset_v3 validate `
  --dataset eval\crud_rag_1000\questions_v3.json `
  --corpus eval\crud_rag_1000\corpus `
  --manifest eval\crud_rag_1000\corpus_v3_manifest.json
```

重建脚本会按期望集合清理本夹具 `corpus/support` 和 `corpus/distractor` 中多余的生成文件。因此正式执行前必须先冻结当前 hash，并且不能把用户自有文件放入这两个生成目录。

### 6.2 为什么修改了评测适配器

现有 `eval/adapters.py` 原先只遍历 corpus 根目录，不能发现嵌套在 `support/` 和 `distractor/` 下的 1000 个文件。为保留两类文档边界和稳定的相对文档名，新增递归、稳定排序的 `_iter_structured_corpus_files()`，并让结构化 parse 和 ingest 共用该遍历逻辑。

该修改保证：

- `support/...`、`distractor/...` 的相对路径进入 metadata；
- 文档 ID 根据稳定相对路径生成；
- parse 校验与实际 ingest 使用完全相同的文件集合；
- 不需要把 1000 个文件平铺到同一目录。

### 7.2 选题流程

#### 步骤 U1：建立候选池

从固定的 `source/split_merged.json` 中重新读取三类 QA，排除：

- 已被当前 100 题使用的 upstream ID；
- 与当前 100 题规范化问题重复的条目；
- 缺问题、答案或任一 `news*` 的条目；
- 同题 gold 文档重复的条目。

按下列稳定键排序，以保证可重建：

```text
SHA-256(20260819 | unanswerable-v3 | category | upstream ID | normalized question)
```

#### 步骤 U2：确认原 gold 全部未被选入

对每个候选题规范化其全部 `news*`，计算 SHA-256。只有满足以下条件才进入下一步：

- 所有 gold hash 都不在 193 篇 support 中；
- 所有 gold hash 都不在 807 篇 distractor 中；
- gold 文档名或正文没有通过其他题目的去重关系间接进入 corpus；
- 1doc/2docs/3docs 题的全部 gold 都缺失，不能只缺其中一篇就直接标记 `out_of_scope`。

#### 步骤 U3：排除近重复和转载泄漏

仅检查精确 hash 不够。同一新闻可能以改写、截断或转载形式存在于其他文档中。需要对每份被排除 gold 与 1000 篇 corpus 做：

1. 规范化全文完全匹配；
2. 字符 5-gram SimHash 距离检查；
3. 长公共子串/句子窗口检查；
4. 原答案和关键实体、数字、日期的全 corpus 扫描；
5. Dense Top50、BM25 Top50、Hybrid Top50 候选审查。

只要任一 corpus 文档足以支持完整答案，就拒绝该候选或把它重新归类为可回答题。存在部分支持时，应人工判断是否属于 `insufficient_detail`。

#### 步骤 U4：人工 whole-corpus 审核

Dataset v3 对不可回答题的正式 strict 条件要求 `whole_corpus_checked=true`。自动检索不能单独证明“整个 corpus 均不可回答”，因此每题生成 review packet，至少包含：

- 问题、上游答案和上游 gold 摘要，仅供审核，不写入运行时 expected answer；
- 被排除 gold 的 hash 和缺失证明；
- 精确/近重复扫描结果；
- Dense/BM25/Hybrid Top50 文档、分数和命中关键词；
- 人工审核结论、Reviewer、时间和备注。

审核未完成前：

```json
{
  "status": "draft",
  "evidence_checked": false,
  "answer_checked": false,
  "whole_corpus_checked": false
}
```

只有 reviewer 明确确认后才能改为 `verified` 和三个 checked=true。不能由构建脚本自动伪造审核状态。

## 8. 已实施：修正和补充检索评测口径

### 8.1 当前失败口径的问题

现有 `eval.metrics.match_evidence()` 要求：文档名相同，并且完整 evidence snippet 必须被某一个最终 chunk 完整包含。该条件把“正确文档已经被检索到，但 evidence 跨 chunk 边界”判成失败。

基于现有 k=15 JSONL 的只读复算：

- 官方报告 evidence 口径 Hit Rate：96%。
- 文档级 Hit Rate：99%。
- 文档级 Recall：96.50%。
- 文档级 MRR：96.33%。
- 199 条 evidence 中，175 条被当前完整字符串规则命中；15 条是 gold 文档已在 Top5、但完整 snippet 没落入单个 chunk；9 条对应 gold 文档不在 Top5。

四道报告失败题：

| 题目 ID | 已确认原因 |
|---|---|
| `crud-qa-1doc-64fa9b2cb82641eb8ecbeeba` | gold 文档占最终第 1/2/3，evidence 跨 chunk，属于评分误判 |
| `crud-qa-1doc-64fa9b27b82641eb8ecbe187` | gold 文档占最终第 1/2/3，evidence 跨 chunk，属于评分误判 |
| `crud-qa-2docs-64fa9b31b82641eb8ecc0686` | 一个 gold 文档在第 1/2 但 evidence 跨 chunk；另一个 gold 未进入 Top5 |
| `crud-qa-2docs-64fa9b2cb82641eb8ecbf2d0` | 两个 gold 均未进入最终 Top5；返回的是高度近主题的福岛排海/抗议文章 |

历史旧 run 没开启阶段 Trace，所以当时无法确认最后一道题的 gold 是未进入 Dense/BM25/RRF 候选，还是进入候选后被 Reranker 压出 Top5。2026-08-23 已按本节方案接入新 Trace 并重跑，新的阶段事实见第 17 节；这里保留旧结论是为了避免用新证据倒写历史判断过程。

### 8.2 v3 必须同时报告的指标

可回答题至少同时报告：

1. **document Hit@K**：TopK 是否包含任一 gold 文档。
2. **document Recall@K**：多文档题的 gold 文档覆盖率。
3. **document MRR**：第一个 gold 文档的排名。
4. **exact evidence containment**：保留当前严格完整片段命中，作为诊断指标，不再单独代表检索成功。
5. **evidence overlap/coverage**：用 gold 字符区间和 chunk 区间计算覆盖，而不是要求完整 evidence 落在单 chunk。
6. **多文档完整召回率**：1/2/3 篇 gold 是否全部进入 TopK。

不可回答题至少报告：

1. 空检索/拒答门控准确率；
2. `unanswerable_llm_entry_rate`，即虽然不调用 LLM，但检索结果是否会让链路进入生成阶段；
3. 不可回答题 Top1 distance、RRF、Reranker score 分布；
4. 与可回答题的分数分离度；
5. 在降低不可回答误进入率时，对可回答题造成的 false refusal rate。

不得为了让 exact evidence containment 通过而直接增大 chunk 或 overlap。先补充正确的文档级/区间级指标，再判断切分参数是否真的影响回答所需信息。

## 9. Embedding 和 Reranker 迁移 GPU：方案与实施状态

### 9.1 迁移前环境快照

2026-08-19 只读检查结果：

| 项目 | 当前值 |
|---|---|
| Python | 3.14.0 |
| PyTorch | 2.13.0+cpu |
| `torch.cuda.is_available()` | false |
| `torch.version.cuda` | null |
| CUDA device count | 0 |
| GPU | NVIDIA GeForce RTX 4060 Laptop GPU |
| 显存 | 8188 MiB |
| 驱动 | 610.62 |
| sentence-transformers | 5.6.0 |
| FlagEmbedding | 1.4.0 |
| ChromaDB | 1.5.9 |

机器有 GPU，但当时唯一的项目虚拟环境安装的是 CPU-only PyTorch，因此历史评测不可能使用 CUDA；当时 `RERANKER_DEVICE=cpu` 也在配置中明确指定。本快照只解释迁移原因，2026-08-23 的迁移后事实见第 15 节。

### 9.2 历史 CPU 耗时来源

神经网络推理：

- 入库：`bge-large-zh-v1.5` 对 2914 chunks 生成 embedding。
- 查询：同一 embedding 模型对每道问题生成 query embedding。
- 精排：`bge-reranker-v2-m3` 对 15/20/30 个 query-chunk pair 做 Cross-Encoder 推理。

其他仍会留在 CPU 的环节：

- structured-v2 解析、token 计数、切分；
- Chroma/HNSW 向量索引与检索；
- Jieba/BM25；
- RRF、排序、去重、单文档 chunk 上限；
- SQLite 和 JSONL 写入。

k 从 15 增加到 30 时，平均单题耗时从 9.754 秒增加到 14.878 秒，与 Reranker batch 数增加一致。现有结果没有阶段 Trace，因而只能确认 Reranker 是主要增量嫌疑，不能声称已经精确量出各阶段比例。

入库慢还与调用粒度有关：当前 structured ingest 每处理一篇文档就调用一次 `store.add_chunks(chunks)`；1000 篇文档产生约 1000 次小批量 embedding，而不是跨文档聚合为较大的批次。GPU 迁移后仍应优化该微批问题，否则 GPU 利用率可能偏低。

### 9.3 GPU 实施步骤

以下是迁移前制定的执行门禁。G1--G3 已于 2026-08-23 完成并留存证据；G0 中“基于 120 题另跑 CPU 对照”和后续全量 GPU 基线仍依赖 20 道不可回答题先完成冻结，不能由小输入 smoke 代替。

#### G0：冻结 CPU 基线

- 保留当前 `runs/crud-rag-1000-retrieval-v1/`，禁止覆盖。
- 保存 Python、torch、sentence-transformers、FlagEmbedding、ChromaDB 和 GPU 驱动版本。
- 基于 120 题新数据另跑一份 CPU 对照；GPU 和 CPU 必须使用同一份 dataset、corpus、参数和 split。
- 开启 Trace，至少记录 query embedding、dense、BM25、RRF、rerank 和总耗时。

#### G1：先建独立 GPU 环境

为了不破坏当前可运行的 `.venv`，优先创建项目独立的 `.venv-gpu`。安装前必须完成：

1. 通过 PyTorch 官方兼容矩阵确认 Python 3.14、Windows、当前驱动可用的 CUDA wheel。
2. 记录准备安装的 torch 版本、CUDA runtime 版本、下载量和预计磁盘占用。
3. 明确卸载/回退方式；当前 `.venv` 保留为 CPU 回退环境。
4. 不使用系统 Python，不修改全局 CUDA/Python 包。

GPU 环境最低验证：

如果官方 wheel 对当前 Python 版本不兼容，应停止并报告，不得静默安装非官方 wheel或降级到 CPU。

#### G2：增加显式设备配置

建议新增配置：


代码改造：

- `backend/services/embedding.py`：创建 `SentenceTransformer` 时显式传入 `device=settings.EMBEDDING_DEVICE`，encode 使用明确 batch size。
- `backend/services/reranker.py`：把当前写死的 `use_fp16=False` 改为配置项，并继续显式传入 device、batch size、max length。
- `backend/config.py`：新增配置、合法值验证和 GPU/CPU 默认行为。
- `eval/adapters.py`：运行配置快照中记录 embedding device、batch size、reranker FP16、torch/CUDA 版本和实际设备名。

#### G3：显存和正确性冒烟测试

RTX 4060 只有 8GB 显存，且桌面程序也会占用显存。先逐级验证：

1. 只加载 Embedding，编码 1/8/32 个真实 chunk。

3. 同一进程同时加载两个模型。
4. 连续执行 20 个查询，观察显存峰值、OOM、内存泄漏和首轮 warm-up。
5. 用 `nvidia-smi` 和进程内 CUDA memory API 双重记录显存。

发生 OOM 时的调整顺序：

1. 保持两个模型都在 GPU，先降低 Reranker batch size。
2. 确认 FP16 已生效。
3. 降低 Embedding batch size。
4. 必要时分阶段加载/释放模型。

#### G4：优化入库批处理

在不破坏逐文档 metadata 和状态事务的前提下，将多个文档生成的 chunks 汇总成可配置批次后调用 embedding。建议初始测试 32/64/128 chunks，不直接一次性编码全部 2914 chunks。

- 每个 chunk 的 document_id、document_name、unit、offset 不变；

- GPU 批处理和原 CPU 按文档处理生成相同维度、相同数量的向量。

- 使用新的 120 题数据和独立 run 目录，例如 `v3/runs/gpu-baseline-120q/`。

硬性条件：

- `torch.cuda.is_available() == true`。
- 报告同时记录配置设备和实际模型设备，二者均为 `cuda:0`。

- 相同 120 题、k=15 下，mean 和 p95 至少降低 30%；
- 入库耗时至少降低 30%；

## 10. 待实施：完整检索参数优化

### 10.1 现有候选数实验实际改变了什么

当前 `RERANKER_CANDIDATE_K` 被 `_candidate_k()` 用作整个前级候选数：

- Dense 请求 candidate_k；
- BM25 虽先取 `max(candidate_k, BM25_TOP_K)`，随后仍截断到 candidate_k；
- RRF 输出 candidate_k；
- Reranker 接收该 candidate_k。

因此 k=15/20/30 不是纯 Reranker 参数扫描，而是同时改变 Dense、BM25、RRF 和 Reranker 深度的耦合扫描。v3 不能用该结果回答“是哪一级候选不足”。

### 10.2 参数解耦建议

建议将内部参数拆为：

```text
DENSE_CANDIDATE_K
BM25_CANDIDATE_K
FUSION_CANDIDATE_K
RERANKER_CANDIDATE_K
RETRIEVAL_TOP_K
```

并在 Trace 中分别记录每一级：

- 候选 chunk ID、文档名、rank、distance/BM25/RRF/Reranker score；
- 淘汰原因；
- gold 首次出现在哪一级、在哪一级丢失；
- 每一级耗时。

### 10.3 为什么距离阈值必须重新校准

当前 0.67 来自旧的 21 题、68 chunks 数据，而 CRUD_RAG 是 120 题、2914 chunks、1000 文档，题目分布和近主题干扰都不同。旧阈值不能自动外推。

现有离线 threshold sweep 只对最终 retrieval rows 按 `distance <= threshold` 过滤；但 Hybrid 的真实链路在 Dense 后、RRF 前过滤。因此它不能完整模拟修改阈值后 BM25/RRF/Reranker 的候选变化。

v3 应选择以下一种方式：

- 实际重放每个阈值的完整 Hybrid 流程；或
- 一次保存足够深的无阈值 Dense、BM25 候选和 Reranker pair score，再离线重放 threshold、RRF、TopK。

第二种更快，但必须先验证离线重放与真实链路逐题一致。

### 10.4 不可回答题需要新的拒答门控

Hybrid 中即使 Dense 被 distance threshold 全部过滤，BM25 仍可能凭常见词返回候选；RRF 是排名融合，也不会自动产生“没有答案”的绝对阈值。只调 Dense distance threshold 可能无法降低不可回答题进入生成阶段的比例。

需要同时评估：

- Dense distance threshold；
- sparse-only 候选是否允许进入最终结果；
- Reranker 绝对分数阈值或可校准拒答分数；
- 最少跨路支持规则；
- 可回答 false refusal 与不可回答 false positive 的权衡。

不得只围绕 20 道不可回答题把阈值调到全拒答；必须同时保持 100 道可回答题质量。

### 10.5 推荐实验顺序

不要跑完整笛卡尔积。按以下顺序逐阶段冻结：

1. **修正指标并建立 CPU/GPU Trace 基线**。
2. **检索模式消融**：Dense、BM25、Hybrid，先关闭 Reranker。
3. **前级候选深度**：分别扫描 Dense 和 BM25 的 10/15/30/50。
4. **Dense threshold**：以现有 0.67 为中心，先检查 0.55/0.60/0.65/0.67/0.70/0.75，再根据分数分布缩小区间。
5. **RRF**：测试 RRF k 和 fusion candidate k；只在 Hybrid 明确优于单路时继续。
6. **Reranker candidate k**：在前级参数冻结后测试 10/15/20/30/50。
7. **拒答门控**：利用 20 道不可回答题校准 Reranker/跨路门控。
8. **最终 TopK**：3/5/8/10，分别报告文档召回和下游上下文长度。
9. **切分参数**：最后测试 300/60、400/80、500/100；每组需要重新建索引，且不能以修复错误指标为目标。

BM25 k1/b 属于二级优化。只有 BM25/Hybrid 在 development 上确实带来增益时，才扫描 k1/b，避免无效计算。

### 10.6 split 使用规则

- development：参数搜索和错误分析。
- validation：比较候选配置并选择唯一方案。
- frozen_test：所有参数和拒答门控冻结后只运行一次。

当前 100 题 candidate sweep 使用了全部 split，所以旧的 20 道 `frozen_test` 已经被观察，只能作为历史回归集，不能继续称为未污染盲测。v3 实施仍冻结它们的 split 标签，以便和旧结果逐题对齐；新增 4 道不可回答 `frozen_test` 也不足以代表完整 RAG 盲测。

因此必须区分两种结论：

- 本方案可以完成可复现的 120 题优化评测和历史回归验收；
- 如果要求正式、未见过的 frozen acceptance，必须另外选择一批从未参与本轮诊断和调参的新可回答题及不可回答题。仅重新给已看过的 120 题换 split 名称不能恢复盲测有效性。

## 15. 2026-08-23 GPU 迁移执行记录（阶段 V3-3）

### 15.1 本轮采用的迁移顺序

本轮按“先保留 CPU 环境、在独立环境证明 GPU 真实可推理、再决定是否切换默认运行入口”的顺序实施。这样做不是把 CPU/GPU 混在同一个环境里反复替换，而是把环境变更和生产入口变更拆成两个可验收步骤：

1. 保留原 `.venv`，作为已知可运行的 CPU 回退环境；
2. 新建 `.venv-gpu`，只在其中安装 CUDA 版 PyTorch 和项目依赖；
3. 用临时环境变量把 Embedding 和 Reranker 指向 `cuda:0`，不修改 `.env`；
4. 先分别验证两个模型，再验证二者同时驻留；
5. 只有模型、精度、显存和实际设备全部通过后，才讨论切换默认启动入口。

这一顺序的理由是：只看到 `nvidia-smi` 或 `torch.cuda.is_available()` 不能证明项目模型真正使用 GPU；必须检查模型参数的实际设备并完成一次真实前向推理。同时，原启动脚本固定使用 `.venv`，所以仅修改 `.env` 会让 CPU-only PyTorch 因 CUDA 不可用而启动失败，不能把“改了配置”误记为“完成迁移”。

### 15.7 历史停止点：默认运行入口切换决策（已解除）

只修改 `.env` 并不能完成切换，因为 `scripts/start.ps1` 当前固定使用：

```powershell
$python = Join-Path $repoRoot ".venv\Scripts\python.exe"
```

而该 `.venv` 安装的是 CPU-only PyTorch。若把 `.env` 直接改成 `cuda:0`，设备断言会按设计拒绝静默回退并使服务启动失败。因此下一步至少要同步完成：

1. 把 `.env` 的 `EMBEDDING_DEVICE`、`RERANKER_DEVICE` 改为 `cuda:0`，把 `RERANKER_USE_FP16` 改为 `true`；
2. 让 `scripts/start.ps1` 默认使用 `.venv-gpu`，或增加一个明确的环境参数并把 GPU 设为默认；
3. 更新 README 的安装、启动和测试命令；

```text
query embedding -> Dense raw -> Dense eligible -> BM25 -> RRF -> Reranker candidates -> selected Top5
```

每个阶段保存 chunk ID、排名、distance、BM25 score/rank、RRF score、Reranker score、是否通过过滤和是否最终选中；同时保存 query embedding、Dense、BM25、RRF、Reranker、总耗时。这样可以把“没召回”“被阈值过滤”“融合丢失”“重排候选内但未进 Top5”和“只因 evidence 跨 chunk 被旧指标判错”分开，而不是看到最终失败后猜原因。

本次四道 exact containment 失败在 GPU Trace 中表现为：

| 题目 | 阶段事实 | 正确分类 |
|---|---|---|
| `crud-qa-1doc-64fa9b2cb82641eb8ecbeeba` | Dense/BM25/RRF/Reranker/selected 均命中 gold，文档 Recall=1、coverage=1，但 exact=false | 正确文档已检出，evidence 跨 chunk；旧口径误判 |
| `crud-qa-1doc-64fa9b27b82641eb8ecbe187` | 同上 | 正确文档已检出，evidence 跨 chunk；旧口径误判 |
| `crud-qa-2docs-64fa9b31b82641eb8ecc0686` | GPU Dense、BM25、RRF、Reranker 和 selected 都只覆盖 1/2 gold | 前级候选深度/召回不足，不是单纯 Reranker 候选数问题 |
| `crud-qa-2docs-64fa9b2cb82641eb8ecbf2d0` | 两篇 gold 均进入 Dense、BM25、RRF 和 Reranker 15 候选，但 selected Top5 为 0/2 | Reranker 排序/最终 TopK 阶段丢失 |

这也确认了此前“三组候选数失败题相同”不能据此认为只需测试 Reranker 候选数：不同失败发生在不同阶段，V3-5 仍必须分别扫描 Dense/BM25 深度、阈值、融合、Reranker candidates 和 final TopK。

### 17.5 CPU/GPU 性能与设备证据

GPU report 中 Embedding 和 Reranker 的 configured/actual device 均为 `cuda:0` 且 `verified=true`；PyTorch 为 `2.13.0+cu130`，CUDA runtime 13.0，设备为 NVIDIA GeForce RTX 4060 Laptop GPU。PyTorch 记录 CUDA 峰值 allocated 2397.9 MiB、reserved 2764.0 MiB，无 OOM。运行期间间歇 `nvidia-smi` 抽样观察到整卡显存约 2859--3779 MiB、GPU utilization 峰值约 69%、功耗峰值约 137.57 W；这些是离散抽样，不是连续遥测。

| 性能指标 | CPU | GPU | 加速比 | GPU 耗时下降 |
|---|---:|---:|---:|---:|
| 1000 文档/2914 chunks 入库 | 1658.28 s | 289.48 s | 5.73x | 82.54% |
| 120 题 mean | 10.022 s | 0.315 s | 31.82x | 96.86% |
| 120 题 p50 | 9.993 s | 0.235 s | 42.52x | 97.65% |
| 120 题 p95 | 11.202 s | 0.312 s | 35.90x | 97.21% |
| 去掉首题冷启动 mean | 9.959 s | 0.242 s | 41.15x | 97.57% |

首题 CPU/GPU 分别约 17.489/8.981 秒，包含模型冷启动；去掉首题后的均值更能代表已加载模型的稳定查询，但仍包含完整 Hybrid 和 JSON/Trace 开销。

Trace mean 进一步说明瓶颈：

| 阶段 | CPU | GPU | 加速比 |
|---|---:|---:|---:|
| query embedding | 122.785 ms | 18.806 ms | 6.53x |
| Dense retrieval | 10.622 ms | 7.458 ms | 1.42x |
| BM25 sparse | 50.777 ms | 57.673 ms | 0.88x |
| RRF | 0.067 ms | 0.065 ms | 1.03x |
| Reranker | 9836.517 ms | 228.831 ms | 42.99x |
| total | 10021.988 ms | 314.874 ms | 31.83x |

结论是 CPU 慢的主要来源确实是 Reranker CPU 推理，Embedding 也是明显但次要部分；BM25/RRF/Chroma 等仍由 CPU 执行，迁移后不会全部消失。GPU 组的 BM25 略慢不应解释为 GPU 回退，而是 CPU 阶段的运行波动，且绝对量约 58 ms。

逐题最终结果比较：Top1 chunk 为 120/120 相同，Top5 集合和顺序为 118/120 相同。两道不同均是不可回答题；FP16 的小分数差异使候选边界发生变化，但 Top1、全部汇总质量和不可回答门控结论不变。中间 Dense 阶段还存在一处差异：`crud-qa-2docs-64fa9b31b82641eb8ecc0686` 的 CPU Dense 15 覆盖 2/2 gold，GPU Dense 15 覆盖 1/2；两组最终 selected 都只覆盖 1/2，因此最终质量仍一致。该差异已保留在对比 JSON 中，不能被“汇总一致”掩盖。

### 17.7 不可回答题门控结果

20 道不可回答题在当前 Hybrid+Reranker 链路中全部返回了非空 Top5，因此：

- `unanswerable_llm_entry_rate=100%`；
- `unanswerable_refusal_gate_accuracy=0%`；
- 可回答题空结果/误拒答率为 0%。

这不是“20 题构建失败”的直接证据，也不是 GPU 数值问题。它说明当前检索实现只有 Dense 候选的距离过滤，Hybrid 的 BM25/RRF 分支仍能产生候选，且最终没有基于融合/Reranker 分数执行可审计的拒答 gate。分数分布已写入报告，可用于 V3-5 校准，但不能在看过 frozen_test 后直接选择阈值并把同一 split 当盲测。
