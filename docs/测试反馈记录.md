# 测试反馈记录

> 用途：记录用户手动验收/测试过程中提出的 bug 与改进需求，以及对应的
> 原因分析与改进方案。每条记录三部分：**反馈内容 → 原因分析 → 改进方案**。
> 状态：`已修复`（代码已提交） / `已实施` / `待确认`。

## 一、阶段 1：多级树形标签与筛选检索

### 1. 已上传文档无法修改分类

- **反馈**：上传后的文档没有改分类（标签）的入口。
- **原因**：后端 `PUT /api/documents/id/{id}/tags` 已实现，但过渡前端未暴露编辑入口。
- **方案**：文档列表每项增加「🏷」按钮 → 展开标签编辑区（多选已有标签 + 输入新标签 + 保存）。
- **状态**：已修复。

### 2. 创建标签不直观，无法独立新建空标签

- **反馈**：只能在「上传时写新标签名」的方式创建，不能单独新建空标签。
- **原因**：标签管理只有读取展示，没有独立创建入口（后端 `POST /api/tags` 未接前端）。
- **方案**：侧栏新增「标签管理」区：路径输入 + 「➕ 新建标签」独立创建空标签；上传区也可新建，创建后自动选入本次上传。
- **状态**：已修复。

### 3. 选择文件后自动入库，缺少确认步骤

- **反馈**：选完文件可能就自动处理存入了，不直观，希望加一步确认。
- **原因**：过渡前端沿用「选择即上传」的旧交互，无暂存概念。
- **方案**：上传改为三段式——选择文件仅暂存 → 选择/新建标签 → 点「✅ 确认上传」才提交；失败文件保留暂存区可重试。
- **状态**：已修复。

### 4. 新建标签报错「Request URL is missing protocol」；标签计数显示误导

- **反馈**：标签管理/上传区新建标签报 URL 错误；新建标签后显示「默认有 1 篇文档」。
- **原因**：① 创建标签请求用了相对路径 `/api/tags`，httpx 拒绝；② 编辑对话框里输入的新标签保存时会挂到当前文档（设计行为但文案没说清），且父标签计数采用「含子级」语义，新建父标签会显示子标签的文档数。
- **方案**：① 改为绝对 URL，测试假客户端加「拒绝相对 URL」防护；② 标签列表展示「本层 N · 含子级 M」双层计数，编辑框文案注明「保存后会挂到当前文档」；新增测试锁定「新建标签不挂文档」。
- **状态**：已修复。

### 5. 上传区新建标签报 widget 错误；新建后丢失已选标签

- **反馈**：`st.session_state.upload_tag_selection cannot be modified after the widget ... is instantiated`；已有选择时新建标签会把旧选择清空。
- **原因**：Streamlit 两个机制叠加：① widget 实例化后禁止直接改其 session_state；② 点击创建的那一轮多选框未渲染，该轮结束时 Streamlit 会清理未渲染 widget 的 session 值，rerun 时旧选择已丢失。
- **方案**：按钮移到多选框之前渲染；在按钮处理函数内（旧值仍在时）快照合并「当前已选 + 新标签」入待选队列，下一次 rerun 在多选框实例化前整体替换。
- **状态**：已修复。

### 6. 缺少一键关闭服务的命令

- **反馈**：一键启动脚本只能开不能关。
- **原因**：`start.ps1` 只启动并打印 PID，停止需手动 `Stop-Process`。
- **方案**：新增 `scripts/stop.ps1`（读取 `logs/service.pids`，校验进程启动时间防误杀，`taskkill /T /F` 清进程树）；`start.ps1` 记录 PID、防双开、支持 `-Stop` 转发。
- **状态**：已实施。

### 7. 缺少标签编辑功能（重命名/删除）

- **反馈**：标签管理只有新建与查看，无法重命名/删除标签。
- **原因**：后端 `PATCH/DELETE /api/tags/{path}` 已实现，过渡前端未接入口。
- **方案**：标签管理区增加「选择标签 + 重命名输入 + ✏️ 重命名」与「🗑️ 删除（带确认提示：文档保留、仅解除关联）」。
- **状态**：已修复。

## 二、阶段 2：OCR / 多模态识别

### 8. 扫描件上传失败「Could not read Boolean object」

- **反馈**：上传真实扫描 PDF 报 HTTP 500。
- **原因**：PyPDF2 解析畸形 xref 表时抛出 `PdfReadError`（该路径 `strict=False` 也无效），失败发生在任何 OCR 逻辑之前。
- **方案**：PyPDF2 解析失败时自动回退 pdfium（Chrome 同款引擎）提取文本，并追加解析 warning「已使用备用引擎」；两个引擎都失败才报错。已用真实损坏 PDF 验证（PyPDF2 报 EOF marker 错、pdfium 正常读出）。
- **状态**：已修复。

### 9. GLM 密钥被写进代码默认值

- **反馈**：用户自行把智谱 API key 与开关写进 `config.py` 默认值（安全问题）。
- **原因**：为了让 OCR 生效选择了改代码的方式。
- **方案**：密钥与开关一律走 `.env`（gitignore 保护）；代码恢复安全默认（key 空、开关全关）；`config.py` 注释明确「密钥一律放 .env」。已提醒用户如分支曾推送需重置 key。
- **状态**：已修复。

## 三、阶段 2 验收反馈（本轮）

### 10. 第一次向量查询很慢（7-8 秒），之后变快

- **反馈**：怀疑向量库懒加载；重启后未复现。
- **原因**：确认是**模型懒加载**（非向量库缓存）——Embedding（BGE-large ~1.3GB）与 Reranker（bge-reranker-v2-m3 >2GB）都是 `lru_cache` 惰性单例，首次查询才加载；实测每次查询 rerank 阶段仍占 4-5 秒（CPU 精排 15 候选）。「重启没复现」的可能：只重启了前端未重启后端、重启后先上传文档预热了 Embedding、或首次慢被掩盖。
- **方案**：服务启动后**后台预热**两个模型（`PREWARM_MODELS=true`，失败仅告警），把冷启动成本挪到启动期。
- **状态**：已实施（待验收）。

### 11. Trace 面板耗时总额 ≠ 各阶段之和

- **反馈**：计时总数与展示的各功能耗时加起来不一致。
- **原因**：`total` 从收到请求起算，包含未展示步骤——多轮追问改写（一次额外 LLM 调用）、历史读取、标签换算、引用提取、消息落库；面板只画 7 个检索/生成阶段。
- **方案**：面板增加「其他阶段耗时」= total − 已知各项之和，并注明包含项；追问改写单独计时展示（待阶段 3 前端重写时随 SPA 实现，或提前在过渡件加一行说明）。
- **状态**：待确认（方案已说明，用户未在本轮明确勾选；随 SPA 阶段实施）。

### 12. 不选标签检索不到文档，选标签反而能检索到

- **反馈**：全库检索（不选标签）无结果，选标签后能检索到。
- **原因**：**生产索引仍为 structured-v1（2459 个旧 unit，未重建）**。引用提取有版本守卫：`parser_version ≠ structured-v2` 的 chunk 被静默丢弃 → 旧 chunk 能进检索、能被 LLM 用，但**引用/预览全部失效**，前端表现为「检索不到」。标签过滤缩小候选空间后，新的 v2 文档更容易进入 Top 候选 → 有引用 → 表现为「选标签才检索得到」。另有「候选截断 + 距离阈值」放大效应（全库 top-15 候选易被无关 chunk 占满）。
- **方案**：执行 **structured-v2 生产重建**（rebuild 全部文档 → 全库 v2 → 引用恢复）；后续可选优化：全库检索增大候选数、空结果诊断提示。
- **状态**：已实施（重建完成，见下方记录）。

### 13. Trace 只能看当前对话，切走后无法再查看

- **反馈**：切换到新对话后，上一个对话的 trace 无法再查看。
- **原因**：原设计「首期不持久化 trace」，trace 只随当次响应挂在前端内存，切换会话重新加载消息后丢失。
- **方案**（用户确认）：Trace 持久化到 SQLite——新增 `message_traces` 表（schema v3），绑定助手消息，删除会话时级联清理；总量超过 `TRACE_STORAGE_MAX_BYTES`（默认 50MB）按创建时间淘汰最旧（LRU）；复用 `RETRIEVAL_TRACE_ENABLED` 开关（关了不计算也不存储）；重放恢复已存 Trace；前端切换会话后仍可查看历史 Trace。
- **状态**：已实施（待验收）。

### 14. 模型选型：GLM-4.6V-Flash 是否够用

- **反馈**：询问将 OCR 模型换成 GLM-4.6V-Flash 是否够用。
- **原因/结论**：Flash 为 9B 轻量版（官方免费档），中文 OCR 转录（A/C 层）大概率够用；复杂图表描述（B 层）可能弱于 106B 完整版。
- **方案**：先用 Flash 实测，`VISION_MODEL` 为纯配置项，不满意换 `glm-4.6v` 零代码改动。已按 GLM 配置更新 `.env`/`.env.example` 与设计文档决策记录。
- **状态**：已实施。

### 15. 批量重建卡在视觉调用失败风暴（2026-08-14 重建现场发现）

- **反馈**：生产重建长时间停滞（解析阶段 0 文档落盘），GLM 日志刷屏 RateLimitError/BadRequestError。
- **原因**：① 免费档限流后，openai 客户端对每条失败自动重试，而**失败结果不缓存**——课件中重复出现的同一图片在每页/每份文档被反复重新请求，形成请求风暴；② 图片格式 bug：PPTX 内嵌 EMF/WMF 矢量图被直接以 `data:image/jpeg` 发送，模型无法读取 → BadRequest。
- **方案**（用户确认方案 C）：
  1. 代码修复——`normalize_image_bytes`：Pillow 嗅探并统一转 JPEG，不支持的矢量格式跳过；`run_vision` 增加**失败短期记忆**（进程内 10 分钟 TTL，相同对象不再重试；成功仍走磁盘缓存）；
  2. 本次重建**完全关闭 OCR**（纯本地）先完成全库 structured-v2 升级与引用恢复；需要 OCR 的文档由用户稍后手动重传（届时重开开关，按文档逐个触发）；
  3. 本条目及其修复记录入档。
- **状态**：已修复 + 已实施（重建完成见下方记录）。

### 16. 全库检索漏召回（候选窗口截断）—— 用户选方案 C

- **反馈**：问「第三轮手动测试反馈了什么」（目标 111.docx / scanword.pdf，均挂 pit 标签），全局检索返回「未找到相关信息」；选定 pit 标签则正常返回。
- **原因**：实测目标 chunk 全库排名 **scanword.pdf=21 / 111.docx=39**，向量距离 0.60/0.62（在 0.67 阈值内，但超出 15 的候选窗口）→ 被截断丢弃。bge 模型对该问句与目标文本的语义区分度不足，约 20 个距离更近但内容无关的 chunk 排在前面；选标签后范围缩小，目标必然进窗口。附带发现：`.env` 三个键（`RETRIEVAL_TOP_K` / `RERANKER_ENABLED` / `CITATION_PREVIEW_ENABLED`）被注释行吞掉而失效，服务一度以默认配置运行（候选 10、无重排、无引用预览），加剧了漏召回。
- **方案**（用户确认 **C**）：不修改检索代码，把「全库固定候选窗口可能漏掉边缘相关文档」记为已知限制，引导用户用标签缩小范围（这正是本阶段优化方向）；同时修复 `.env`（恢复 TOP_K=5、reranker、引用预览）。
- **状态**：已实施（.env 修复）+ 已记录（方案 C 决策）。

### 17. 带标签查询后报 409 conversation_conflict

- **反馈**：选定标签查询出现 `409 会话末尾已变化，请刷新后重试`；刷新后能看到刚才的回答已正常显示。
- **原因**：之前「一直转圈」的请求实际已在服务端完成（回答已保存），但浏览器未收到响应，本地会话落后于服务端 → 下一次提问的 `expected_last_message_id` 与服务端实际末尾不一致 → 409。属于客户端重同步缺口，非数据丢失。
- **方案**：前端收到 409（`conversation_conflict` / `request_in_progress` / `stale_retry`）时自动从服务端重同步当前会话并提示「会话已在服务端更新，请重新发送问题」；错误详情显示改为提取 `detail.message` 而非整段字典。
- **状态**：已修复（待验收）。

### 18. .env 注释乱码与键丢失事故

- **反馈**：发现 `.env` 注释大面积乱码/缺失，多个键（见 #16）被注释行吞掉而失效。
- **原因**：此前用「整文件读取-替换-整文件写回」方式修改 `.env`，对原文件编码处理不当（GBK/UTF-8 混读），导致注释乱码，部分键与注释行合并成一行（整行以 `#` 开头 → 被当作注释 → 键失效）。
- **方案**：以 `.env.example` 的注释结构重建 `.env`，保留全部现有真实值（47 键齐全），统一 UTF-8 BOM + CRLF；今后修改 `.env` 一律逐键写入/追加，不做整文件重写。附：处理过程中 DeepSeek key 曾出现在会话输出中，已建议用户重置该 key。
- **同源教训（2026-08-15 追加）**：`.ps1` 脚本同样必须保持 **UTF-8 BOM**——无 BOM 时 PowerShell 按 GBK 解码，某些中文注释的尾字节会吞掉换行符导致语法错误（`start.ps1` 已复现并修复）；编辑脚本后需校验 BOM。
- **状态**：已修复（待用户重置 key 后确认）。
