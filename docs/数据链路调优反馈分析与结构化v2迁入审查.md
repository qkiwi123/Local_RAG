## 1. v2 优化测试反馈逐项分析

### 1.1 OCR 读出的文档缺少结构，全文显示的结构数据丢失

**现象确认（只读验证）**

对生产库 `data/metadata.db` 的 `document_units.structure_json` 抽样：

- `scan.pdf`（A 层整页 OCR）：4 个 unit 的 13 个 block **全部是 `paragraph`**，
  例如第 3 页的“四、系统维护与更新”“五、安全注意事项与警告”都只是普通段落，
  没有任何 `heading` block。
- `111.docx`（C 层内嵌图片 OCR）：OCR 图片文字以 2 个 `paragraph` block
  插入，无标题/列表/表格类型。
- `scanword.pdf`（B 层页内图表说明）：视觉说明同样是 `paragraph`。

**根因（代码定位）**

- `backend/services/parsers/pdf.py:198-206`：A 层 OCR 文本
  `split_paragraphs()` 后全部构造为 `BlockDraft(block_type="paragraph", ...)`。
- `backend/services/parsers/docx.py:270-278`、`pptx.py:146-155`：C 层图片识别文本
  全部为 `paragraph`。
- 视觉模型 Prompt（`backend/services/vision.py:20-23`）只要求“转录全部文字，
  保留段落与换行”，不要求输出任何结构标记。
- 因此 `ParsedUnit.blocks` 中 OCR 内容全部扁平化，`StructuredRenderer`
  （`web/src/components/StructuredRenderer.tsx`）只能按段落渲染，
  “全文显示/引用预览”里标题、列表、表格等结构确实会丢失。
- 原生文本的结构不受影响；丢失的只是 OCR 补出来的那部分结构。

**可选改进方案（按推荐度）**

| 方案 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| A. 让视觉模型输出轻量结构标记 | OCR Prompt 要求返回 `# 标题`、`- 列表项`、`| 表格 |` 等轻量 Markdown，后端解析为 heading/list_item/table | 最接近“真实结构”，一次模型调用同时得到内容与结构 | 模型可能不遵守格式、OCR 噪声放大；需要解析容错与回退 |
| B. 确定性后处理 | 对 OCR 文本做保守启发式：`^[一二三四五六七八九十]+、`、`^\d+\.\d*`、短行且无句末标点 → heading；`·`/`•` 开头 → list_item；连续 `|` → table | 不依赖模型、可复现、无额外费用 | 启发式对扫描件版式误判；只作为 A 的回退 |
| C. 仅改前端渲染 | 段落内按行做视觉排版，不改数据结构 | 改动小 | 数据结构仍是平的，引用/检索语义没有结构，不解决根本问题 |
| D. C 层图片内容标记为“图注/插图说明” | 新增 block_type 或 attributes 区分 | 显示更诚实 | 需要模型约定与 schema 扩展 |

**推荐**：A + B 组合。模型主路径输出 Markdown 结构；解析失败或格式不合规时
回退到 B 的确定性规则；所有 OCR 块继续保留 `attributes.ocr=True`。

**版本与数据影响**：如果只改变 block 类型、不改变 `block.text` 与
`canonical_text`，chunk/向量可以不变，`document_units.structure_json` 可重算；
一旦为识别结构而改写 OCR 文本，就属于 canonical text 语义变化，按项目规则必须升
`PARSER_VERSION` 并重建索引。实施时请先定清这条边界。

### 1.2 知识库管理缺少按“文档名称”的模糊搜索

**现状（代码定位）**

- 后端 `GET /api/documents`（`backend/routers/upload.py:254-285`）只支持
  `tags` 查询参数，没有名称搜索参数。
- 前端 `web/src/api/client.ts:87-94` 的 `listDocuments(tags?)` 只拼 tags；
  `DocumentTable.tsx` 工具栏只有标签筛选和刷新按钮，没有搜索框。

**推荐实现（后续实施时）**

- 后端：`GET /api/documents` 增加可选 `q` 参数，在 `list_document_records` 结果上
  对 `original_name` 做模糊匹配；SQL 层用
  `WHERE original_name LIKE ? ESCAPE '\'`，并先转义 `%`/`_`/`\`，
  避免用户输入被当作通配符。与现有 `tags` 参数取交集。
- 前端：`KnowledgePage` 增加防抖 300ms 的 `Input.Search`；`api.listDocuments` 增加
  `q` 参数；`refreshDocuments` 同时携带当前 `q` 与 `documentFilter`。
- 只检索 `original_name`（按需求），不扩展到正文；文档量大后再考虑
  SQLite FTS5，当前规模 LIKE 足够。

**权衡**：也可以纯前端过滤（当前文档量小），但后端查询能保证与标签筛选、
分页和未来权限一致，推荐后端实现。

### 1.3 “前端回复不是流式输出”

**排查结论：React 主前端已经是流式，旧 Streamlit 不是。**

- React 主前端：`useChatController.ts:205-229` 调用 `streamChat()` →
  `web/src/api/stream.ts:36` 请求 `POST /api/chat/stream`，逐行解析 NDJSON，
  `onDelta` 累计到 `streamingText`；`MessageTimeline.tsx:99-114` 在
  `streaming` 状态下实时渲染 `streamingText + Spin`。这条链路是真正的增量流式。
- 旧 Streamlit 前端：`frontend/app.py:231` 调用的是非流式 `POST /api/chat`，
  必须等 LLM 全部生成完才一次性显示。**如果验收时打开的是 8501 端口的
  Streamlit，就会看到“非流式”。**
- 后端流式端点本身：`backend/routers/chat.py:445-506` 使用 `StreamingResponse`
  逐行 yield，`llm.py` 的 `ask_stream/ask_with_history_stream` 使用
  `stream=True` 逐 token yield，没有刻意缓冲。

**建议**：

1. 功能验收统一使用 React SPA（`http://localhost:8000/`），不要用 Streamlit
   验收流式特性；
2. 如果 React 页面仍“一次性出现”，优先检查是否走了旧端口、是否被反向代理/网关
   缓冲（本地直连一般不会），而不是先改后端；
3. 不建议给即将移除的 Streamlit 回填流式支持。

### 1.4 Trace 看不到多轮对话里“查询重写后的语句”

**根因（代码定位）**

- `RetrievalTrace` 模型（`backend/models/schemas.py:243-259`）没有
  query / standalone_question / original_question 字段。
- `retrieve_with_trace()`（`backend/services/retriever.py:211-227`）接收了
  `standalone_question`，但没有把它写入 Trace；
- 流式 `meta` 事件（`chat.py:308-314`）虽然带 `standalone_question`，
  但 TraceDrawer 打开的是消息里的 `trace`（`ChatPage.tsx:193-195`），
  两者没有打通；
- 持久化 Trace 只存 `message_traces`，会话重放时同样看不到改写语句。
- `TraceDrawer.tsx` 目前只显示检索模式、标签、耗时和阶段表，没有查询语句区域。

**推荐改动点（后续实施，按文件）**

1. `models/schemas.py`：`RetrievalTrace` 增加
   `query: str = ""`（实际用于检索的 standalone_question）与
   `original_question: str = ""`（用户原始问题）；旧 Trace 反序列化时默认空串，
   前端只在非空时显示，完全向后兼容。
2. `services/retrieval_trace.py`：`TraceCollector.__init__` 接收 `query`，
   `finish()` 写入 `query`；或由 `retrieve_with_trace` 在返回前写入。
3. `routers/chat.py`：检索返回后把 `request.question` 写入
   `trace.original_question`（非持久化单轮两者相同，可只写一个）。
4. `components/TraceDrawer.tsx`：在标题下方增加
   “用户问题 / 改写后检索语句”两行，并在 `api/types.ts` 同步类型。
5. 已有 18 条持久化 Trace（当前库 `message_traces`）无需迁移，打开时只显示
   已有字段即可。

这样多轮场景下能直接看到“原问题 → 改写问题 → 各阶段候选”，排查方向（改写错了
还是排序错了）会更清晰。

### 1.5 “灵犀X3的系统维护介绍”命中失败：黄金 chunk 同文档第 4 位被淘汰

#### 1.5.1 用真实 Trace 复现（只读抽样）

查询本地库中该问题的几次 Trace：

**失败样例（短问句，`RETRIEVAL_MODE=hybrid` + Reranker）**

黄金 chunk 是 `scan.pdf 第 3 页` 的“四、系统维护与更新…”（chunk_id
`f063ad6b88f4cb17_s0_e393`）。它的各阶段位置：

| 阶段 | 黄金 chunk 位置 | 分数 |
|---|---|---|
| Dense 候选 | 第 12 / 15 | distance 0.5067 |
| BM25 候选 | 第 5 | score 10.17 |
| RRF 融合 | **第 3** | rrf 0.0293 |
| Reranker 精排 | **第 6** | -0.2713 |
| 最终上下文 | 未入选 | — |

精排后前 5 名全部是 `scan.pdf`：第 4 页保修(1.27)、第 2 页通信(0.56)、
第 1 页封面(0.36)、第 4 页 FAQ(0.23)、第 1 页 SIM(0.02)；黄金 chunk 是
scan.pdf 的第 6 名、同文档第 4 个不同页面。`_limit_per_document`
（`retriever.py:133-148`，max_per_document=3）先选前 3 条 scan.pdf，
跳过同文档后续所有候选（含黄金），再用 HomiCenter 的两个负分 chunk 补足 top5。
LLM 因此只看到电池保修相关内容，答“未找到系统维护”。

**成功样例（长问句“系统维护与更新介绍”，dense + Reranker）**

黄金 chunk：Dense 第 12 → **Reranker 第 2（0.6598）** → 成功入选。

**关键结论**：

1. 候选召回（Dense top15 / BM25 top15 / RRF）**没有漏掉黄金证据**；短问句下
   RRF 甚至把黄金排到第 3。
2. 是 **Reranker 在短问句上把黄金压到第 6**，再叠加
   “同文档最多 3 条”的硬规则，才把它淘汰。
3. 若不启用 Reranker，该短问句在 hybrid-RRF 下反而会入选（RRF 第 3），
   说明这不是单纯的“候选数不足”，而是“精排打分 + 文档配额”的联合失败。
4. 你看到的“同文档第 4 位被淘汰”是下游症状；扩大同文档配额确实能直接解决这个
   样本，但根因还有 Reranker 对短问句的排序质量。

> 注：当前库里维护与更新的黄金内容实际在 `scan.pdf`（OCR 扫描件）第 3 页；
> `111.docx` 在本次抽样中只包含“手动测试反馈”文字。若你的 gold 位于 111.docx
> 的另一个版本，机制相同——都是 `max_per_document=3` 在精排后截断同文档候选。

#### 1.5.2 调优方案对比（按“投入/收益/风险”排序）

| 方案 | 做法 | 对本样本效果 | 优点 | 代价/风险 |
|---|---|---|---|---|
| **O1 可配置同文档配额（短期推荐）** | 把 `max_per_document=3` 改为环境变量，扫描 3/4/5 | 设为 4 时黄金入选（成为 scan.pdf 第 4 条 + 1 条其他文档） | 改动极小，与你“把开关接到前端”的方向一致 | 只治标；配额过大时单文档垄断上下文、跨文档多样性下降；需要评测 |
| **O2 按来源单元去重 + 配额** | 同一 page/slide/section/logical page 只保留 1 条，再执行文档配额 | 单用本项不解决本样本（前 3 名已是 3 个不同页面），但与 O1 组合后能避免同页冗余 chunk 占位 | 减少 400/80 重叠 chunk 的重复上下文 | 规则更复杂，需离线验证 |
| **O3 精排与词法证据融合（中期推荐）** | 最终得分 = 归一化 reranker_score + α·词法排名奖励（BM25/RRF rank 折算），或用“词法强证据救回槽位” | 黄金 BM25 第 5 / RRF 第 3，有较大概率被救回 | 直接针对“精排把强词法证据压下去”的失败模式 | 需要新的消融实验和超参扫描；不能靠单个样本定 α |
| **O4 查询侧增强** | 单轮问题也做轻量改写/扩展（LLM 或同义词表），如“维护”补“更新/升级/保养” | 可能让 Reranker 打分接近长问句 | 提高此类短问句整体鲁棒性 | 增加延迟/成本；你已说明本轮不做（T-10），可列下一阶段 |
| **O5 换/调 Reranker** | 试 max_length、FP16、其他中文 reranker 模型 | 未知，需评测 | 若模型排序质量提升则全链路受益 | 可能引入新依赖、内存/延迟变化，必须有 Dataset v3 证据 |
| **O6 回归用例入库（建议马上做）** | 把“灵犀X3的系统维护介绍（短）”与“系统维护与更新介绍（长）”作为一对 canary 加入评测集，断言黄金 chunk 必须进入最终上下文 | 防止任何后续参数调整再次静默回归 | 低成本、可长期守住该缺陷 | 需要按 Dataset v3 规范补 evidence/locator/审核 |

**推荐路线**：

1. 立即：O1 落地为环境变量（默认仍 3），把“灵犀X3 短问句”加入离线回归用例
   （O6），扫描 cap=3/4/5 后选择有证据的最优值；
2. 下一轮：实现 O3（词法/精排融合），在 Dataset v3 上做五组消融，
   类似当年 `hybrid-ablation` 的部署门槛；
3. 如仍不满足：再评估 O5 或 O4。
4. 同时建议把 `RETRIEVAL_TOP_K` 与同文档配额联动评估：cap=4 且 top_k 仍为 5 时，
   其他文档只剩 1 个席位，可能考虑 top_k=6。

**为什么不只扩大同文档数量**：它解决的是“选择策略”层，不解决“精排把正确页排到
第 6”的排序质量层；语料变大后同类问题会继续出现，只是阈值从 3 变成 4/5，
而且单文档垄断会让多文档综合题（“A 和 B 有什么区别”）退化。

## 2. T-08 详解：BM25 内存索引与缓存机制

### 2.1 它是怎么工作的

实现文件：`backend/services/sparse_retriever.py`。

1. **分词**（`tokenize`，26-34 行）：
   - 文本先 NFKC 规范化 + 转小写；
   - 正则只保留 `[\u4e00-\u9fffA-Za-z0-9_.+%\-]+`，即中文、英文数字及少量符号；
   - 对每段用 `jieba.lcut(cut_all=False)` 精确模式分词；
   - 过滤纯标点 token。
2. **建索引**（`_get_index`，43-78 行）：
   - 触发时机：第一次 BM25 查询，或缓存键变化时；
   - 数据来源：`vector_store.get_all_chunks()` 从 Chroma 取出全部
     `chunk_id/content/metadata`（不加载 embedding）；
   - 若带 `allowed_document_ids`，先按 document_id 过滤；
   - 对每条 content 分词得到 `corpus`，创建
     `BM25Okapi(corpus, k1=settings.BM25_K1, b=settings.BM25_B)`，
     内部计算 IDF、平均文档长度、各 chunk 长度；
   - 全部数据存在进程内存的 `_cache` 字典里（chunks + model）。
3. **缓存键**（55-60 行）：
   `(vector_store.get_index_revision(), BM25_K1, BM25_B, 排序后的 allowed_document_ids)`
   - `index_revision`：进程内计数器，Chroma 每 add/delete 一次就 +1；
   - 因此“增删文档、改 BM25 参数、换标签范围”都会触发整库重建。
4. **缓存槽位**：只有 **1 个槽**（`_cache` 单对象 + 线程锁）。新 key 到来时旧
   索引直接被覆盖丢弃。
5. **查询**（`search`，81-115 行）：
   - 查询分词 → `model.get_scores()` 得到每个 chunk 的 BM25 分数；
   - 丢弃 `score <= 0`（没有任何词命中）的行；
   - 按分数降序（同分按 chunk_id）取 top_k；
   - 返回行带 `bm25_score/bm25_rank`，`distance=None`。

### 2.2 优点

- 零外部依赖：不需要 ES/Milvus，单机 Python 即可，与项目“本地知识库”定位一致；
- 中文可用：jieba 分词比 naive 单字匹配更接近中文词义；
- 确定性：同分按 chunk_id 排序，评测可复现；
- 与 Chroma 解耦但同源：索引从 Chroma 快照重建，不维护第二份持久化数据；
- 进程内 revision 能感知**本进程**的增删；不同标签范围不会互相污染。

### 2.3 缺点

- **全量重建成本**：任何 key 变化都要 `get_all_chunks()` + 对全部分词。当前
  约 2.6k chunks 无感；语料到万级/十万级时，首次查询或切标签会明显卡顿；
- **单槽缓存颠簸**：多标签交替查询时，A 范围建完查一次 → B 范围又整库重建 →
  再回 A 又重建；内存和 CPU 反复浪费；
- **双份内存**：Chroma 进程内可能已有文本，BM25 又存一份全量 `content/metadata`
  副本和分词结果；
- **跨进程不可见**：`_index_revision` 只在当前进程自增。服务运行期间用另一个
  进程跑 `scripts/rebuild_index.py` 重建 Chroma，正在运行的服务不会知道，
  BM25 可能继续用旧快照（Dense 侧则能读到新库，造成两路不一致）；
- **无领域词表/停用词**：jieba 默认词典对专有名词可能切错；分数阈值只是
  `score>0`，对普通词命中的噪声没有进一步门控；
- **无持久化**：每次服务重启后第一次 BM25 查询都要重新分词建索引。

### 2.4 推荐优化方案（含取舍）

| 方案 | 做法 | 收益 | 代价 | 适用规模 |
|---|---|---|---|---|
| A. 全局索引 + 查询时过滤 | 永远只建一个全库 BM25 索引；查询先算全库分数，再按 `allowed_document_ids` 过滤后取 top_k | 彻底消除按标签重建；缓存永远命中（key 只有 revision/参数） | 每次查询都要算全库分数（O(N)，当前规模可忽略）；筛选后的 top_k 需要后处理 | 首选，任何规模都更简单 |
| B. 多槽 LRU 缓存 | 按 scope key 缓存 2-4 个索引，淘汰最久未用 | 高频标签来回切换不重建 | 内存成倍；仍可能在冷 scope 首查卡顿 | 语料中等、标签集固定 |
| C. 持久化分词产物 | 服务启动/首次构建时把 token 列表落盘（pickle/JSON），revision 校验后直接加载 | 重启不再付 jieba 成本 | 需要可靠失效机制（revision/配置/文件 hash）；多一层缓存一致性问题 | 语料大、重启频繁 |
| D. jieba 用户词典/停用词 | 加入产品名（如“灵犀X3”）和领域词；配置停用词 | 直接改善词法召回质量 | 需要维护词典，评测验证 | 与规模无关，随时可做 |
| E. 服务运行期禁止外部重建或共享 revision | 规定重建必须停服；或把 revision 落盘由两进程共享 | 避免 Dense/BM25 两路不一致 | 增加运维约束或跨进程同步复杂度 | 建议先把“重建必须停服”写成操作规范 |

**推荐**：先做 A（代码改动集中在 `_get_index/search`，行为最可预期），
配合 D（领域词典）和 E（操作规范）。若不想改动算法，B 是最小改动方案。

## 3. T-12 详解：视觉（OCR）磁盘缓存

实现文件：`backend/services/vision_cache.py`、`backend/services/parsers/ocr.py`。

### 3.1 机制

1. **缓存键**：`sha256(file_sha256 + "\n" + object_id + "\n" + model)`。
   - `file_sha256`：整个源文件的哈希（PDF/DOCX/PPTX）；
   - `object_id`：PDF 用 `pdf-page:N` 或 `pdf-page-images:N`；
     DOCX/PPTX 内嵌图片用 `image_blob_sha256[:16]`（按图片内容去重）；
   - `model`：`VISION_MODEL`。
2. **文件形态**：`data/vision_cache/<key>.txt`，内容是模型返回的文本；
3. **读取**：文件存在且非空即命中，直接返回，**不占单文档视觉预算、不调 API**；
4. **写入**：先写 `.tmp` 再 `os.replace` 原子替换；写失败只吞异常，不影响入库；
5. **预算**：`VisionBudget(OCR_MAX_PER_DOCUMENT)` 只对“缓存未命中且要真实调用”的
   次数计数（`parsers/ocr.py:97-104`）；
6. **失败短期记忆**：同一 `(file_hash, object_id, model)` 在进程内失败后，
   600 秒内不再重复调用（防止批量重建时请求风暴），失败会写入 ParseWarning；
   成功结果走磁盘缓存，不受 TTL 影响。

### 3.2 优点

- 重建索引/重复上传同一文件时，OCR 不重复计费、不重复耗时；
- 键包含模型名，换视觉模型不会错误复用旧结果；
- 原子写避免读到半截文件；缓存故障不影响主入库流程；
- 预算只扣真实调用，缓存命中不会挤占单文档配额。

### 3.3 缺点与风险

- **没有淘汰策略**：`vision_cache.py` 只有写/读，没有容量上限、TTL 或 LRU。
  每份文档最多新增 `OCR_MAX_PER_DOCUMENT`(20) 个缓存文件，但文件内容可大可小，
  长期运行磁盘只增不减；
- **没有与文档生命周期联动**：删除文档后，对应 OCR 缓存不会自动清理
  （键是文件哈希，无法轻易反查）；
- **失败 TTL 是进程内的**：服务重启后失败记忆清零，可能再次重试失败项；
- 缓存文本是明文 `.txt`，含文档中的图片文字，磁盘权限即等于缓存权限。

### 3.4 推荐方案（含取舍）

| 方案 | 做法 | 收益 | 代价 |
|---|---|---|---|
| A. 总容量上限 + LRU（推荐） | 参考 `message_traces` 的 50MB LRU：写入后统计目录总字节，超限按 mtime 淘汰最旧文件 | 磁盘可控，实现模式与现有代码一致 | 极端情况下会淘汰仍可能复用的缓存，最坏多一次 API 调用 |
| B. TTL 过期 | 超过 N 天未访问（mtime）即删 | 简单 | 重建旧索引时可能缓存已过期，重复计费 |
| C. 删除文档时级联清理 | 记录缓存键与 document_id 的映射 | 释放空间更精准 | 要新增索引表/清单，复杂度高 |
| D. 手动清理脚本/命令 | 提供 `clean_vision_cache` 脚本 | 零风险，人工可控 | 需要运维记得执行 |

**推荐**：A（上限 + LRU）作为自动兜底，D 作为手动工具；若成本敏感再考虑 C。
