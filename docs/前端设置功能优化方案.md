## 1. 目标

在当前 React 主前端中增加独立“设置”页面，让使用者不需要手工修改 `.env`，即可完成：

1. 配置问答模型的服务商、API 地址、模型名和 API Key；
2. 开启或关闭生成模型调用；
3. 配置回答生成参数；
4. 配置检索模式、最终 Top K、候选深度和过滤阈值；
5. 查看 Embedding、Reranker、CUDA 等本地推理状态；
6. 让新设置在明确、可验证的边界内动态生效；
7. 在 Trace 中记录实际使用的配置版本；
8. 完成 V3-5 检索参数校准后，再正式开放拒答门控参数和推荐预设。

本期重点是完成全局配置功能，不建设用户权限体系。所有设置对当前工作空间全局生效，不区分用户、会话或浏览器。

## 2. 当前实现与问题

### 2.1 已确认的当前结构

| 模块 | 当前事实 |
|---|---|
| 主前端 | `web/`，React 19 + TypeScript + Ant Design，由 FastAPI 托管 `web/dist` |
| 兼容前端 | `frontend/app.py`，旧 Streamlit 界面，暂时保留但不是本期设置页实现目标 |
| 前端路由 | 当前只有 `/` 对话和 `/knowledge` 知识库管理 |
| 配置入口 | `backend/config.py` 从环境变量和 `.env` 读取配置 |
| 配置生命周期 | `settings = Settings()` 为模块级单例，服务启动时初始化 |
| LLM 客户端 | `backend/services/llm.py::_get_client()` 使用单实例缓存 |
| 检索参数 | 聊天请求已使用冻结的 `RetrievalRuntimeConfig`；评测脚本仍保留模块配置兼容入口 |
| BM25 缓存 | 缓存键包含请求级 k1/b；对应设置变化时还会显式清空进程内缓存 |
| Trace | 已能记录 Dense、BM25、RRF、Reranker、selected 和阶段耗时 |

### 2.2 为什么不能只让前端修改 `.env`

直接从设置页改写 `.env` 有以下问题：

- 当前 `Settings` 已经在模块导入时创建，修改文件不等于运行中立即生效；
- LLM 客户端带缓存，API Key、Base URL 或超时改变后旧客户端仍可能被复用；
- 多个字段分次写入时可能形成半更新状态；
- `.env` 同时包含存储路径和设备等启动级配置，前端误写会影响生产数据目录或导致服务无法启动；
- API Key 可能被意外返回、记录或覆盖；
- 无配置版本，事后无法判断某次回答使用了哪一组参数。

因此本方案不让前端直接编辑 `.env`，而是在后端增加“允许动态修改的配置白名单”和持久化运行时配置。

### 2.3 “过滤阈值”必须拆分

当前 `RETRIEVAL_DISTANCE_THRESHOLD=0.67` 是 Dense cosine distance 上限，数值越小代表越相似。它只过滤 Dense 候选，不等于最终拒答门控：

- Dense 模式：距离阈值可以直接导致空结果；
- BM25 模式：没有 Dense distance；
- Hybrid 模式：即使 Dense 全被过滤，BM25/RRF 仍可能产生非空候选；
- Reranker 只是排序，当前没有依据最终分数执行拒答的正式 gate。

最新 120 题预基线中，20 道不可回答题全部仍有 Top5，`unanswerable_refusal_gate_accuracy=0%`。因此设置页不能把 Dense 阈值描述为“最终过滤阈值”，也不能在未经 V3-5 校准时给出一个看似可靠的拒答推荐值。

## 3. 本期范围与明确不做

### 3.1 本期实现

- 全局设置页和顶部导航入口；
- 非敏感运行时配置的持久化和版本管理；
- 问答 LLM 的 API Key、Base URL、模型名、温度、最大输出和超时；
- DeepSeek 预设和通用 OpenAI-compatible 自定义端点；
- 生成模型启用/停用；
- Dense/BM25/Hybrid 模式；
- final Top K、Dense candidates、Dense distance、BM25、RRF、Reranker candidates；
- 配置关系校验、应用影响提示、恢复默认；
- API 连通性测试；
- 实际模型设备和运行状态只读展示；
- 配置版本写入聊天 Trace；
- V3-5 完成后开放拒答 gate 和推荐预设。

### 3.2 本期不实现

- 登录、用户身份、管理员角色或操作权限；
- 每用户、每会话或每次提问独立参数；
- 自动从各厂商拉取模型列表；
- 同时保存多套 API provider profile；
- 自动余额或计费查询；
- Embedding/Reranker 模型和 CPU/GPU 设备热切换；
- chunk size、overlap、strategy 的运行时修改；
- 一键重建生产向量索引；
- 将同一设置页重复实现在旧 Streamlit 前端；
- 在自动化测试中调用真实外部模型 API。

不做用户权限不代表可以明文暴露 API Key。密钥不回显、不写日志、不进入 Trace 仍是功能正确性要求。

## 4. 总体设计决策

### 4.1 配置分层

有效配置按以下层次解析：

```text
代码安全默认值
    ↓
.env / 进程环境变量（部署默认）
    ↓
持久化运行时覆盖（设置页保存）
    ↓
单次请求获取的不可变 EffectiveSettingsSnapshot
```

只对白名单字段允许运行时覆盖。下列配置继续保持启动级只读：

- `CHROMA_PERSIST_DIR`；
- `METADATA_DB_PATH`；
- `UPLOAD_DIR`；
- `EMBEDDING_MODEL`、`EMBEDDING_DEVICE`；
- `RERANKER_MODEL`、`RERANKER_DEVICE`、`RERANKER_USE_FP16`；
- chunk size、overlap、strategy、max tokens；
- OCR 图片、缓存和生产存储路径。

原因是这些字段会影响索引兼容性、模型驻留或生产数据位置，不能与普通查询参数放在同一个“保存并立即应用”动作中。

### 4.2 全局配置

本期只维护一份全局配置，作用于保存后的新请求：

- 已经开始的请求继续使用开始时取得的旧快照；
- 保存完成后的下一次请求使用新版本；
- 一个请求内不允许中途读取到两个不同版本；
- 配置更新使用 `expected_revision` 防止两个页面互相覆盖。

### 4.3 配置生效等级

| 等级 | 含义 | 示例 |
|---|---|---|
| `immediate` | 下一请求直接生效 | Top K、Dense threshold、候选数、RRF k、温度 |
| `cache_refresh` | 保存后清理相关缓存，下一请求重建 | API/Base URL、BM25 k1/b |
| `restart_required` | 本期只读展示，不允许保存 | Reranker FP16、设备、batch、预热策略 |
| `reindex_required` | 本期只读展示，不允许保存 | Embedding 模型、chunk 参数 |

设置页必须显示生效等级，不使用模糊的“保存成功”掩盖重启或重建索引要求。

### 5.1 导航和路由

```text
对话 | 知识库管理 | 设置
```

```text
web/src/pages/settings/

├── RetrievalSettingsCard.tsx
├── RuntimeStatusCard.tsx
├── SettingsApplyBar.tsx
└── settings-page.css
```

### 5.2 页面区域

#### A. 问答模型

| 字段 | 控件 | 默认/约束 |
|---|---|---|
| 启用生成模型 | Switch | 默认启用；关闭后进入 retrieval-only 展示模式 |
| 服务商 | Select | `DeepSeek`、`OpenAI-compatible` |
| Base URL | Input | DeepSeek 预填 `https://api.deepseek.com`；自定义时可编辑 |
| 模型名 | Input | 默认从当前有效配置读取 |
| API Key | Password Input | 永不回填明文；留空表示保留原值 |
| 清除 API Key | 独立危险操作 | 二次确认，不能由清空输入框隐式触发 |
| Temperature | Slider + number | 0 至 2，默认保留现值 0.3 |
| Max tokens | number | 1 至实现允许的上限，默认 2000 |
| Timeout | number | 1 至 600 秒 |
| 测试连接 | Button | 使用表单草稿，不保存；显示可能产生少量 API 调用 |

第一版回答生成和追问改写共用 provider、Base URL、API Key 和模型名。追问改写继续使用固定 `temperature=0`、`max_tokens=200`，避免一个普通设置同时改变检索改写行为。以后如有必要再拆分独立 rewrite model。

生成模型关闭时：

- 仍执行检索；
- 不执行追问 LLM 改写和答案生成；
- 返回确定性摘要，例如“已检索到 N 条相关内容，请查看引用”；
- 正常返回 citations 和可选 Trace；
- 前端明确显示“检索模式，未调用生成模型”。

#### B. 基础检索

| 字段 | 建议范围 | 说明 |
|---|---:|---|
| retrieval mode | dense / bm25 / hybrid | 当前生产有效模式由 API 返回，不在前端硬编码 |
| final Top K | 1--20 | 最终送入上下文的 chunk 数 |
| Dense candidates | final Top K--100 | 与 final Top K 独立，解决当前候选深度耦合问题 |
| Dense distance threshold | 0--2 | 数值越小越严格；只影响 Dense 分支 |
| max chunks per document | 1--final Top K | 当前代码固定为 3，本期改为可配置 |

#### C. 高级检索

| 字段 | 建议范围 | 关系校验 |
|---|---:|---|
| BM25 Top K | 1--100 | Hybrid/BM25 时显示 |
| BM25 k1 | 大于 0 | 修改后重建 BM25 内存缓存 |
| BM25 b | 0--1 | 修改后重建 BM25 内存缓存 |
| RRF k | 1--200 | Hybrid 时显示 |
| Reranker enabled | boolean | 关闭时隐藏分数 gate |
| Reranker candidate K | final Top K--100 | 不能小于 final Top K |
| refusal gate enabled | boolean | S7 前禁用并标注“等待 V3-5 校准” |
| refusal gate signal | reranker score 等 | S7 根据实验结论确定，不提前伪造统一信号 |
| refusal gate threshold | 由信号决定 | S7 才给出推荐范围和默认值 |

页面提供简短说明，不把所有参数都放在第一视觉层。基础参数默认展开，高级参数折叠。

#### D. 本地推理与索引状态

只读展示：

- Embedding 模型、configured device、actual device、loaded、verified；
- Reranker 模型、enabled、configured/actual device、FP16、loaded、verified；
- PyTorch、CUDA runtime、GPU 名称；
- 当前索引 parser、chunk 配置和 Chroma 路径的脱敏摘要；
- 当前配置版本和更新时间；
- 哪些设置来自环境变量、哪些来自页面覆盖。

生产路径不向前端返回完整绝对路径，只返回“生产/测试”和必要的目录名称摘要。

### 5.3 保存交互

页面底部固定操作栏：

- `放弃修改`：恢复到最近一次后端有效值；
- `恢复部署默认`：删除当前区域的运行时覆盖，回到 `.env`/默认值；
- `保存并应用`：先做前端校验，再由后端完成完整校验和原子更新；
- 保存后显示新 revision、实际生效时间和是否完成缓存刷新；
- 离开存在未保存修改的页面时弹出提示；
- 连接测试和正式保存是两个独立动作，测试成功不自动保存。

## 6. 后端组件设计

建议新增：

```text
backend/
├── routers/settings.py
├── services/runtime_settings.py
├── services/settings_store.py
├── services/secret_store.py
└── models/settings_schemas.py
```

### 6.1 `runtime_settings.py`

职责：

- 定义动态字段白名单和默认值来源；
- 合并环境配置与持久化覆盖；
- 构造不可变 `EffectiveSettingsSnapshot`；
- 提供当前 revision；
- 在保存后原子替换进程内快照；
- 调用 LLM/BM25 缓存刷新钩子；
- 对外提供经过脱敏的状态。

聊天入口在请求开始时只获取一次快照，并显式传给：

```text
chat router
  ├── follow-up rewrite
  ├── retriever
  ├── context formatter
  └── answer generation
```

不建议继续让各服务在一次请求的不同阶段反复读取可变的模块级 `settings`，否则保存动作可能造成同一请求前后参数不一致。

### 6.2 `settings_store.py`

非敏感设置继续放在当前 metadata SQLite，但使用独立表，不与文档记录混合。

建议 schema：

```sql
CREATE TABLE runtime_settings (
    singleton_id INTEGER PRIMARY KEY CHECK (singleton_id = 1),
    revision INTEGER NOT NULL,
    payload_json TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE runtime_settings_history (
    revision INTEGER PRIMARY KEY,
    payload_json TEXT NOT NULL,
    changed_keys_json TEXT NOT NULL,
    created_at TEXT NOT NULL
);
```

规则：

- `payload_json` 不包含 API Key；
- 保存使用 SQLite transaction；
- `expected_revision` 不匹配时返回 409；
- 每次成功更新产生递增 revision；
- 历史表为 S1 建立，历史查询/回滚 UI 可后续开放；
- 保留最近固定数量版本，例如 50，防止无限增长。

### 6.3 `secret_store.py`

本地 Windows 第一版使用系统用户级 DPAPI 加密 API Key，密文放在独立文件，例如：

```text
data/runtime_secrets.bin
```

要求：

- 不把密钥写入 SQLite `payload_json`；
- 不在 `GET /api/settings` 返回密钥；
- 日志、异常、Trace 和测试快照统一脱敏；
- 环境变量已有 Key 时可继续作为默认来源；
- 页面保存新 Key 后形成运行时覆盖；
- “恢复部署默认”删除覆盖并重新使用环境变量 Key；
- “清除 Key”同时取消覆盖且不自动回退时，需要在响应中明确最终来源；
- DPAPI 不可用时拒绝保存新 Key，不允许静默降级为明文。

本期不做权限体系，因此 settings API 与其他 API 一样可访问；部署边界默认仍是可信本地工作空间。该限制必须写入 README，但不阻塞本期功能实现。

### 7.2 保存设置

```http
PATCH /api/settings
```

请求必须包含：

```json
{
  "expected_revision": 3,
  "llm": {
    "model": "deepseek-v4-flash",
    "api_key_update": null
  },
  "retrieval": {
    "final_top_k": 5
  }
}
```

`api_key_update` 采用三态：

- 字段缺失或 `null`：保留现有密钥；
- `{ "action": "replace", "value": "..." }`：替换；
- `{ "action": "clear" }`：显式清除。

成功响应包含：

- 新 revision；
- 完整脱敏后的有效配置；
- `changed_fields`；
- `effects`，例如 `llm_client_cache_cleared`、`bm25_cache_cleared`；
- `warnings`。

### 7.3 模型连接测试

```http
POST /api/settings/test-llm
```

规则：

- 使用页面当前草稿，可以测试尚未保存的新 Key；
- 不写入数据库或 secret store；
- 使用最小 chat completion 请求，设置很小的输出上限；
- 明确提示这是一次真实外部 API 请求，可能产生少量费用；
- 返回成功、耗时、provider、model 和脱敏 endpoint；
- 401/403、模型不存在、超时、网络错误分别返回稳定错误码；
- 服务端不得记录请求中的 API Key；
- 自动化测试全部 mock，不调用真实 API。

### 7.4 恢复默认

```http
POST /api/settings/reset
```

支持 `section=llm|retrieval|all`。恢复动作删除对应运行时覆盖，重新解析环境变量和代码默认值，并产生新 revision。

### 7.5 状态接口

```http
GET /api/settings/runtime-status
```

返回模型 configured/actual device、loaded、verified、torch/CUDA 版本和模型缓存状态。状态接口不得为了展示页面而强制冷加载模型；尚未加载时返回 `loaded=false`，不能伪造 actual device。

## 8. 校验规则

### 8.1 LLM

- provider 只能是后端白名单；
- Base URL 必须为合法 HTTP(S) URL，不允许本地文件协议；
- model 不能为空并限制最大长度；
- API Key 替换值不能为空且限制长度；
- temperature 为 0--2；
- max tokens 为正数且不超过后端安全上限；
- timeout 为 1--600 秒；
- `llm.enabled=true` 时必须存在有效 Key 和 Base URL；
- 关闭 LLM 时不因缺 Key 阻止服务启动或检索。

### 8.2 Retrieval

- final Top K：1--20；
- Dense/BM25/Reranker candidate K：1--100；
- Dense candidate K 和 Reranker candidate K 不能小于 final Top K；
- Dense threshold：0--2；
- BM25 k1 大于 0，b 为 0--1；
- RRF k：1--200；
- max chunks per document：1--final Top K；
- Dense-only 字段在其他模式下可以保存但不生效，响应需明确 inactive；
- Hybrid 模式不能把 Dense threshold 误记为最终 refusal gate；
- S7 前拒绝保存 `refusal_gate.enabled=true`，返回稳定校验错误。

后端是最终校验来源；前端校验只用于即时反馈，不能代替服务端校验。

## 9. 运行时接入与缓存刷新

### 9.1 LLM 客户端

当前 `_get_client()` 的无参数单实例缓存需要改造。建议由 `runtime_settings` 根据配置 revision 管理客户端：

- API Key、Base URL、provider、timeout 任一变化后清理旧客户端；
- 下次真实调用惰性创建新客户端；
- 模型名、temperature、max tokens 从本次请求快照传入调用；
- 客户端创建失败不得回退旧 Key 后仍声称新配置生效；
- 旧请求已经持有的客户端允许完成，不强行中断。

### 9.2 Retriever

为避免参数耦合，检索内部接口接收同一 `RetrievalRuntimeConfig`：

```text
final_top_k
dense_candidate_k
dense_distance_threshold
bm25_top_k
bm25_k1
bm25_b
rrf_k
reranker_enabled
reranker_candidate_k
max_chunks_per_document
refusal_gate
```

Dense、BM25、RRF、Reranker 和 selected 不再共同依赖单一 `_candidate_k(top_k)`。每一级使用独立深度，并在 Trace 中记录输入和输出数量。

### 9.3 BM25

BM25 k1/b 更新成功后：

1. 保存新 revision；
2. 原子替换运行时快照；
3. 调用 `sparse_retriever.clear_cache()`；
4. 下一次 BM25 请求使用新参数重建内存索引。

只重建内存 BM25，不重写 Chroma 或生产 metadata。

## 12. 失败处理与回退

| 风险 | 处理 | 回退 |
|---|---|---|
| 新配置校验失败 | PATCH 整体失败，不写部分字段 | 继续使用旧 revision |
| LLM 新配置不可用 | 连接测试不自动保存；正式调用返回明确错误 | 设置页恢复上一个 revision/部署默认 |
| Key 加密失败 | 拒绝保存，不降级明文 | 继续使用原 Key |
| BM25 重建慢 | 下一请求显示一次冷缓存耗时 | 恢复旧参数并重新清缓存 |
| candidate K 关系非法 | 后端 422 | 原配置不变 |
| 多页面覆盖 | expected revision + 409 | 重新加载后再修改 |
| 动态快照切换 | 已开始请求固定旧快照 | 新请求使用新 revision |
| 设置页前端故障 | API 与当前 `.env` 默认仍可启动 | 移除运行时覆盖或暂时隐藏路由 |
| refusal gate 误拒答 | S7 前不可启用；上线前做 false refusal 验收 | 一键关闭 gate/恢复上个 revision |

设置功能不能删除、覆盖或迁移 Chroma 数据；本期不提供任何“重建索引”按钮，因此配置回退不应涉及向量库删除操作。

### 15.2 实际完成内容

#### A. metadata schema v4

修改 `backend/services/metadata_schema.py`：

- schema version 从 3 升到 4；
- 新增单例表 `runtime_settings`；
- 新增有界历史表 `runtime_settings_history`；
- 增加显式 `v3 -> v4` 保留性迁移；
- 空库直接创建完整 v4 schema；
- 旧 v1/v2 数据库仍逐级迁移，旧 v3 数据库迁移后保留原业务记录。

没有在表中创建 API Key 字段，`payload_json` 只允许非敏感覆盖。首次启动没有任何覆盖时也不主动插入 revision 0 记录；revision 0 是“尚未保存运行时覆盖”的逻辑状态，第一次成功保存才写入 revision 1。

为什么这样做：当前 metadata SQLite 已有明确版本迁移机制，继续沿用同一机制比另建无版本数据库更容易备份和验证；把设置放在独立表中又能避免与文档、会话记录混写。

#### B. 非敏感设置存储

新增 `backend/services/settings_store.py`：

- `SettingsStore.load()` 在无记录时返回 revision 0 和空覆盖；
- `save()` 使用 `BEGIN IMMEDIATE`，在同一事务内校验 `expected_revision`、写当前值、写历史并裁剪历史；
- revision 每次成功保存递增；
- 默认只保留最近 50 个历史版本；
- stale revision 抛出 `SettingsRevisionConflict`，保存前后的当前值和历史不会部分写入；
- API 层在 S3 接入时把该异常稳定映射为 HTTP 409；
- 保存前递归拒绝 `api_key`、password、secret、access token 等敏感字段；
- JSON 使用确定性序列化并拒绝 NaN/Infinity。

为什么使用数据库事务而不是进程内计数：多个页面或未来多个后端进程可能持有不同快照，只有数据库事务内比较 revision 才能防止旧页面覆盖新值。

#### C. 动态白名单、范围和有效快照

新增：

```text
backend/models/settings_schemas.py
backend/services/runtime_settings.py
```

当前可覆盖白名单包括：

- LLM：enabled、provider、Base URL、model、temperature、max tokens、timeout；
- Retrieval：mode、final Top K、Dense candidate K、Dense threshold、BM25 Top K/k1/b、RRF k、Reranker enabled/candidate K、单文档最大 chunk 数；
- refusal gate 目前只接受 disabled，启用会被稳定拒绝，等待 V3-5。

明确不在白名单中的 storage path、Chroma path、Embedding/Reranker device、模型文件、chunk size/overlap/strategy 等字段会被拒绝。字段范围和关系同时校验，例如 Dense/Reranker candidate K 不能小于 final Top K，单文档 chunk 上限不能大于 final Top K。

合并顺序为：

```text
代码/环境部署默认 < SQLite 非敏感运行时覆盖
环境 API Key < DPAPI 运行时 Key 覆盖
```

`RuntimeSettingsManager` 在启动时读取一次存储并构造冻结的 `EffectiveSettingsSnapshot`。更新时先完整构造候选快照，验证成功后才写 SQLite；SQLite 保存成功后再原子替换进程内引用。已经取得旧快照的请求不受新 revision 影响，后续请求才会取得新快照。真实聊天链路将在 S3/S4 显式接入，目前没有提前改变生产问答行为。

#### D. 环境部署默认

`backend/config.py` 和 `.env.example` 增加了 S1 所需的部署默认解析：

```text

LLM_PROVIDER
LLM_TEMPERATURE
LLM_MAX_TOKENS
LLM_TIMEOUT_SECONDS
DENSE_CANDIDATE_K
MAX_CHUNKS_PER_DOCUMENT
```

实际 `.env` 没有被读取后改写，也没有被提交。`DENSE_CANDIDATE_K` 留空时保持历史候选逻辑：Reranker 开启时使用至少 Reranker candidate K，否则使用 final Top K 的两倍；单文档上限默认保持历史值 3，并在 final Top K 更小时收敛到 final Top K。

这些字段目前只进入运行时设置底座，`llm.py`、`retriever.py` 和 `sparse_retriever.py` 仍使用原有模块级配置；对应业务接入分别属于 S3/S4。

需要明确区分：S1 的隔离 `RuntimeSettingsManager` 已验证 `llm.enabled=false` 时可以构造无 Key 快照，但 S1 当时的应用启动仍沿用原有 `Settings` 规则，要求 `.env` 存在 `DEEPSEEK_API_KEY`，以避免形成“服务可启动但旧聊天链路必然调用空 Key”的半成品状态。该历史限制已在 S3 完成 retrieval-only 全链路后解除，详见 17.4。

#### E. DPAPI 密钥存储

新增 `backend/services/secret_store.py`：

- Windows 使用当前用户级 DPAPI；
- 使用项目固定 optional entropy，密文文件默认位于 metadata 同目录的 `runtime_secrets.bin`；
- 文件整体加密，明文 API Key 不进入 SQLite；
- 写入使用同目录临时文件、flush、`fsync` 和 `os.replace`；
- DPAPI 不可用或返回空密文时拒绝保存，不存在明文回退；
- 当前只允许 `llm_api_key` 一个密钥名；
- 异常消息不回显密钥或密文内容；
- 快照内部使用 `SecretStr`，且 `model_dump()` 和 `repr()` 排除明文。

使用用户级而不是机器级 DPAPI 的原因：这是本地单用户工作空间，密文应绑定当前 Windows 用户，避免同一机器上其他用户直接复用。该方案解决“落盘明文”问题，但不等同于账号权限体系；API 暴露边界仍在后续 README/API 阶段说明。

### 17.2 LLM 设置写接口和密钥语义

新增：

```http
PATCH /api/settings
POST /api/settings/test-llm
```

S3 阶段的 `PATCH /api/settings` 只接受 `expected_revision` 和 `llm`，当时 Retrieval 字段仍被 schema 拒绝并留给 S4。非敏感 LLM 字段包括 enabled、provider、Base URL、model、temperature、max tokens 和 timeout。响应返回新 revision、完整脱敏设置、changed fields、实际 effects 和 warnings。S4 已在同一原子 PATCH 上增加 `retrieval`，详见 18.2。

API Key 使用三态协议：

- 缺失或 `null`：保留当前运行时密钥；
- `replace`：校验后写入当前 Windows 用户级 DPAPI 文件；
- `clear`：删除运行时密钥覆盖；如果环境变量仍有 Key，则明确 warning 并回退环境 Key，而不是错误声称“当前已无 Key”。

非敏感配置和 DPAPI 文件无法使用单个数据库事务，因此 `RuntimeSettingsManager.update_llm()` 采用进程级提交锁：先在锁内核对 SQLite revision、构造包含未来密钥的完整候选快照，再原子替换密钥文件并提交 SQLite。SQLite 保存失败会恢复旧密钥；stale manager 在写密钥前就因 revision 409 被拒绝。这样覆盖当前单后端进程部署和同进程多个 manager 的并发。多个独立后端进程共享同一密钥文件仍不在本期支持范围，不能把该锁描述成分布式事务。

保存成功后清理 LLM 客户端缓存，effect 如实返回 `llm_client_cache_cleared` 和 `next_request`；客户端并未在保存请求中提前创建。旧请求已经持有的客户端/流允许完成，新请求使用新 revision。

### 17.3 动态客户端和请求级快照

`backend/services/llm.py` 的单一无参数缓存已改为有界客户端缓存。缓存键包含 revision、provider、Base URL、timeout 和 Key 的单向 fingerprint，不保存或记录明文 Key；最多保留 4 个客户端引用。创建 OpenAI-compatible 客户端时使用当前快照的 Base URL、Key 和 timeout，调用时使用当前快照的 model、temperature 和 max tokens。

DeepSeek 和 `openai_compatible` 都走 OpenAI 兼容协议。第一版仍共用同一组调用字段，不引入供应商私有参数。追问改写使用同一 provider/model/Key/timeout，但继续固定 `temperature=0`、`max_tokens=200`，避免普通回答参数意外改变检索改写行为。

同步 `/api/chat` 和流式 `/api/chat/stream` 都在请求开始时取得一次冻结的 `EffectiveSettingsSnapshot`，并把同一对象传给追问改写和回答生成。设置在请求中途更新不会让一次请求前后混用两个 revision。

LLM 调用错误不再把 `str(exception)` 原样返回给客户端，而只返回稳定的异常类型摘要，避免上游错误正文意外携带敏感信息。

### 17.4 retrieval-only 行为

`llm.enabled=false` 现在是完整链路行为，不只是“最终回答阶段少调用一次”：

- 持久化会话跳过追问改写，使用用户原问题检索；
- 同步和流式回答都不创建客户端、不调用外部 API；
- 有检索结果时生成确定性的“生成模型已关闭”说明，并附真实 `【来源N】` 标记；
- 继续使用原引用解析器生成 citations；
- Retrieval Trace 继续返回，`llm_generation=0`；
- 无检索结果时继续使用原固定提示。

因此 S3 起 `backend.config.Settings` 不再单独要求环境变量中必须有 `DEEPSEEK_API_KEY`。最终约束改由 `RuntimeSettingsManager` 在合并环境、SQLite 和 DPAPI 后检查：LLM enabled 时必须有有效 Key，disabled 时允许无 Key。这样既支持仅检索启动，也支持重启后继续使用 DPAPI Key，不需要把运行时密钥重新抄回 `.env`。

### 17.6 422 密钥回显缺陷及修复

专项测试发现：正常设置响应虽然不含明文 Key，但 Pydantic 对“超长 Key”抛出校验错误时，FastAPI 默认 422 会把原始 `input` 放入响应。这是实际泄漏面，不能因为只发生在非法输入上而忽略。

`backend/main.py` 现在为 `RequestValidationError` 增加敏感字段清洗：只有错误定位包含 api_key/api_key_update、password、secret、authorization、access_token 或 refresh_token 时才移除原 input/ctx，并返回固定掩码；普通 `max_tokens` 等非敏感校验仍走 FastAPI 默认处理。测试确认超长 Key 的完整值和特征片段都不会出现在 422 响应。

### 18.2 Retrieval 原子写入

`PATCH /api/settings` 现在接受 `llm`、`retrieval` 或两者同时提交，但至少必须存在一个分区。两者共用同一个 `expected_revision`、候选快照校验和 SQLite revision 提交，所以组合更新不会出现 LLM 已保存而 Retrieval 失败的半更新。

本阶段开放的 Retrieval 字段为：

```text
mode
final_top_k
dense_candidate_k
dense_distance_threshold
bm25_top_k
bm25_k1
bm25_b
rrf_k
reranker_enabled
reranker_candidate_k
max_chunks_per_document
```

服务端在写库前验证范围和跨字段关系：Dense、BM25、Reranker candidate K 均不得小于 final Top K，单文档最大 chunk 数不得大于 final Top K。非法组合返回 422，revision、SQLite 和当前进程快照均保持旧值。`refusal_gate.enabled=true` 仍被稳定拒绝，因为 20 道不可回答题的正式校准尚未完成。

保存成功后，普通 Retrieval 字段返回 `next_request`；如果 `bm25_k1` 或 `bm25_b` 实际变化，还返回 `bm25_cache_cleared`。只改 Retrieval 不会误清 LLM 客户端，也不会产生“生成模型已关闭”的无关 warning。

### 18.3 请求级检索快照

同步 `/api/chat` 和流式 `/api/chat/stream` 在请求开始时已经取得同一个冻结 `EffectiveSettingsSnapshot`。S4 把其中的 `runtime.retrieval` 继续传入完整检索链，并转换为不可变的 `RetrievalRuntimeConfig`。因此：

- 已经开始的请求继续使用旧参数；
- 保存完成后的下一请求使用新参数；
- 一次请求内 Dense、BM25、RRF、Reranker 和 selected 不会跨 revision 读取全局值；
- 原有评测和脚本未传快照时仍读取模块配置，显式 `top_k` 入口保持兼容，没有强迫历史基线改用生产运行时数据库。

这里没有把 S6 的 settings revision 提前写入 Trace。当前 Trace 可以验证阈值和候选结果实际变化，但还不能直接显示 revision；这仍是下一阶段之后的独立验收项。

### 18.4 候选深度解耦

旧实现先用一个 `_candidate_k(top_k)`，再把同一数值同时传给 Dense、BM25、RRF 和 Reranker。这会导致只调整 Reranker candidate K 时，前级 Dense/BM25 也一起变化，无法判断指标变化究竟来自哪一层。

S4 的实际执行语义改为：

| 阶段 | 使用参数 | 行为 |
|---|---|---|
| Dense | `dense_candidate_k`、`dense_distance_threshold` | 先保留原始候选和 Trace eligibility，再过滤超阈值项 |
| BM25 | `bm25_top_k`、`bm25_k1`、`bm25_b` | 只生成本分支指定数量 |
| RRF | `rrf_k` | `rrf_k` 只作为排名常数；融合池上限取两路深度和启用时 Reranker 所需深度的最大值 |
| Reranker | `reranker_candidate_k` | 只重排融合结果的前 N 项，不反向改变 Dense/BM25 取数 |
| selected | `final_top_k`、`max_chunks_per_document` | 排序完成后做单文档限额并截取最终结果 |

融合池允许大于单路候选数，是因为 Dense 与 BM25 的非重复结果合并后可能足以供应更大的 Reranker 输入；实际数量仍受两路去重后并集大小限制。这种供给关系不是把前级深度重新绑在 Reranker 上：调整 Reranker candidate K 不会让 Dense 或 BM25 各自多取数据。

### 18.5 BM25 缓存

`sparse_retriever.search()` 新增请求级 `k1/b` 参数。内存索引缓存键现在使用：

```text
vector index revision + effective k1 + effective b + allowed document set
```

因此即使遗漏显式清缓存，不同 k1/b 也不会错误复用旧模型；设置 PATCH 在 k1/b 变化时仍主动调用 `clear_cache()`，释放旧引用，让下一次 BM25 请求按新参数惰性重建。该操作只影响当前进程内存，不写 Chroma、不改 metadata SQLite、不重新计算 Embedding，也不触发生产索引重建。

### 20.2 Trace 数据契约和旧数据兼容

`RetrievalTrace` 增加三个可选字段：

```json
{
  "settings_revision": 12,
  "effective_config": {
    "retrieval_mode": "hybrid",
    "final_top_k": 5,
    "dense_candidate_k": 15,
    "dense_distance_threshold": 0.67,
    "bm25_top_k": 12,
    "bm25_k1": 1.5,
    "bm25_b": 0.75,
    "rrf_k": 60,
    "reranker_enabled": true,
    "reranker_candidate_k": 10,
    "max_chunks_per_document": 3,
    "refusal_gate_enabled": false
  },
  "llm": {
    "called": false,
    "provider": "deepseek",
    "model": "deepseek-v4-flash"
  }
}
```

相比 9.4 的最初示例，实际契约补充了 `bm25_k1`、`bm25_b` 和 `max_chunks_per_document`。原因是只记录部分动态字段不足以复现 BM25 排名和最终选取生命周期；这些字段均为非敏感查询参数，不包含路径、授权头或密钥。

三个新字段保持 optional，而不是强制旧 JSON 满足新 schema。既有 SQLite `message_traces.trace_json` 无需迁移，旧持久化 Trace 可以继续通过对话详情和幂等重放读取；前端对缺失 revision/config/llm 显示“旧 Trace 未记录”，不会把未知历史状态伪报为 revision 0 或 `called=false`。

### 20.3 实际检索参数的采集位置

`effective_config` 在 `retriever._retrieve_internal()` 已完成 `_runtime_config()` 解析之后构造，因此记录的是检索器真正使用的参数，而不是设置页草稿、模块默认或请求前的推测值。该快照与实际候选链共用同一个不可变 `RetrievalRuntimeConfig`，所以：

- Dense 记录实际 candidate K 和 distance threshold；
- BM25 记录实际 top K、k1 和 b；
- Hybrid 记录实际 RRF k；
- Reranker 记录开关和实际输入上限；
- selected 记录 final Top K 与单文档 chunk 上限；
- refusal gate 继续如实记录 `false`。

普通 `retrieve()` 关闭 Trace 时不会构造这份 Pydantic 快照，保持原有无 Trace 热路径。`retrieve_with_trace()` 用于离线评测时也会得到实际 effective config，但因为没有聊天运行时 manager，settings revision 和 LLM 摘要保持 `null`；聊天同步/流式完成时才补齐这两部分。

### 20.4 请求级 revision 和 LLM `called` 语义

同步 `/api/chat` 和流式 `/api/chat/stream` 都在请求开始时取得一次冻结的 `EffectiveSettingsSnapshot`。`finalize_chat_trace()` 使用该同一对象写入 `settings_revision`，不会在回答结束时重新读取可能已经变化的全局设置。因此保存前后的两个请求可以分别保留旧、新 revision，而一个正在执行的请求不会被中途保存动作改写版本。

`llm.called` 表示本请求是否实际尝试调用过外部问答模型，包括持久化多轮对话的追问改写和最终回答生成：

- `llm.enabled=false`：追问改写和回答生成都不调用，记录 `false`；
- 有检索结果且生成模型启用：在调用 ask/stream 前标记 `true`；
- 无检索结果且没有追问改写：直接返回固定提示，记录 `false`；
- 多轮追问已尝试改写、之后没有检索结果：仍记录 `true`，因为本请求确实已发生一次模型调用尝试；
- 旧 Trace 或离线 retrieval-only Trace：LLM 摘要为 `null`，不猜测历史行为。

provider/model 取自同一请求快照。`RetrievalTraceLLMSummary` 和 `RetrievalTraceEffectiveConfig` 均拒绝未知字段；模型只定义 `called/provider/model`，没有 API Key、Base URL、authorization header 或 secret source。持久化和 NDJSON 序列化都使用该强类型模型，不从完整运行时设置做无约束 `model_dump()`。

### 20.5 同步、流式、持久化和重放

四条返回路径均已接入新字段：

- 同步有结果；
- 同步无结果；
- 流式有结果；
- 流式无结果。

持久化对话仍把完整强类型 Trace 序列化到助手消息的 `trace_json`，对话详情重新加载和相同 request ID 幂等重放会返回首次请求记录的 revision/config/LLM 摘要，不会使用重放时的最新设置覆盖历史事实。Trace LRU 容量和随会话级联删除语义没有变化。

`RETRIEVAL_TRACE_ENABLED=false` 时仍按既有设计不计算、不返回、不持久化 Trace。本文“每次问答可回溯”是指启用 Trace 后产生的每条新问答 Trace；S6 没有为了满足展示功能而强制所有部署永久保存候选原文。

## 22. 视觉模型设置扩展（2026-09-18）

设置页新增视觉模型区域，沿用问答模型的配置约束，不再要求用户只能修改 `.env`：

- 默认选择“跟随问答模型”，直接复用问答 provider、Base URL、模型和密钥；需要独立额度或不同模型时可切换为“自定义”；
- 文字识别与图片描述分别配置思考模式、思考强度、Temperature、最大输出长度和超时；
- API Key 仍使用用户级 DPAPI 保存，读取接口不回填明文；
- “测试视觉模型”使用未保存草稿发送程序生成的测试图片，只验证真实多模态输入，不写入设置；
- 正式识别在单个后端进程内限制为 1 路并发，记录 429、服务商错误码和 request ID。这个限制可降低本进程并发，但不能证明或消除账号级免费额度限制；
- 视觉设置只影响下一次上传或重新解析，已经入库的文档不会自动重跑 OCR。

## 23. 模型思考展示扩展（2026-09-18）

聊天 NDJSON 协议增加独立 `reasoning_delta`，不把思考文本混入正式回答、引用提取或下一轮历史上下文。当前轮收到思考内容时面板默认展开；第一段正式正文到达后自动折叠，用户可手动再次展开。成功消息把思考内容保存到 metadata schema v5，重新打开历史会话时默认折叠。

如果上游只返回思考而没有正文，后端会明确报空回答错误，前端不会把它误报为成功消息；失败或用户中止的临时思考只保留在当前页面，不落成成功历史。不同兼容端点是否返回 `reasoning_content` 仍取决于服务商，设置页的开关不能保证所有模型采用同一字段协议。
