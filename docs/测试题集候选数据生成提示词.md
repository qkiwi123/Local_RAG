# RAG 测试题集候选数据生成提示词

> 用途：把真实文档交给 AI，让 AI 只根据文档内容生成候选问题、证据、关键点和参考答案。  
> 输出性质：候选数据，不是已经审核通过的黄金测试集。  
> 后续流程：项目内 `prepare` 补齐解析位置 → 人工逐题核验 → strict validate → 冻结数据集。

## 一、使用前说明

建议分批处理文档，不要一次把 20–30 份大型课件全部交给 AI。推荐：

- 每批 1–5 份文档；
- 每批使用不同 `BATCH_ID`，避免 ID 重复；
- 先生成少量候选题检查质量，再扩大数量；
- PPTX、PDF 中只有图片而没有可读取文字的内容，不用于生成事实题；
- 文档若包含隐私、内部机密或版权不允许上传给外部 AI 的内容，不应使用外部 AI 处理。

需要替换的参数：

```text
DATASET_ID：例如 general-courseware-v1
CORPUS_ID：例如 general-courseware-v1
BATCH_ID：例如 batch-001
QUESTION_ID_PREFIX：例如 b001-q
GROUP_ID_PREFIX：例如 b001-g
DIALOGUE_ID_PREFIX：例如 b001-d
TARGET_QUESTION_COUNT：本批期望单题数量，例如 20
TARGET_DIALOGUE_COUNT：本批期望多轮对话数量，例如 1
```

AI 不一定能准确判断 evidence snippet 在整个语料中是否唯一，也不能证明不可回答题在完整
corpus 中确实没有答案。这些事项必须由项目工具和人工审核完成。

## 二、可直接复制的主提示词

复制下面整段提示词，并把文档与参数一起提供给 AI。

````text
你是一名 RAG 黄金测试集候选数据生成器。

你的任务不是总结文档，也不是自由创作题目，而是只根据我提供的文档，生成可供后续人工审核的候选测试数据。

====================
一、任务参数
====================

DATASET_ID=A-RAG_D
CORPUS_ID=A-RAG_D
BATCH_ID=A-001
QUESTION_ID_PREFIX=A-001-q
GROUP_ID_PREFIX=A-001-g
DIALOGUE_ID_PREFIX=A-001-d
TARGET_QUESTION_COUNT=5
TARGET_DIALOGUE_COUNT=1

我会同时提供一份或多份文档。document_name 必须逐字使用我提供的原始文件名，包括扩展名。

====================
二、最重要的事实约束
====================

1. 所有可回答题的事实、数字、关系、步骤、比较、关键点和参考答案，都必须能在给定文档中找到直接证据。
2. 禁止使用外部知识、常识补全、搜索结果、模型记忆或推测。
3. 禁止为了让问题更完整而添加文档没有明确表达的前提。
4. evidence.snippet 必须是文档中连续、逐字可找到的原文子串：
   - 不改写；
   - 不总结；
   - 不纠正错别字；
   - 不添加或删除数字、单位和标点；
   - 不使用省略号拼接不连续内容；
   - 不把多个位置的句子合并为一个 snippet。
5. snippet 应尽量包含足够上下文，通常为 20–120 个字符；如果太短会重复，应适当延长。
6. 如果一个答案需要多个不连续证据，分别输出多条 evidence。
7. 如果问题需要跨文档回答，category 必须为 multi_doc，且 evidence 至少来自两个不同文档。
8. reference_answer 只能陈述 evidence 能直接支持的内容。宁可简短，也不能扩展。
9. keypoints 中的每一个关键点组都必须有 evidence 支持。
10. 如果你无法确认文档内容、文件名、表格关系或数字，不生成该题。
11. 如果文档页面或幻灯片主要是图片，而你无法读取其中原始文字，不得根据图片猜测内容。
12. 不得声称数据已经人工审核，不得输出 verified。

====================
三、题型与难度
====================

category 只允许以下值：

- fact：明确事实、定义、特点或组成；
- numeric：数字、比例、年份、数量、范围或单位；
- table：必须读取表格行列关系才能回答；
- procedural：步骤、顺序、流程或操作要求；
- lexical：专有名词、缩写、精确术语或文档中的特定表达；
- multi_doc：需要结合两个或更多文档；
- unanswerable：给定语料无法回答。

difficulty 只允许：

- easy：一个直接证据即可回答，问题表达直接；
- medium：需要结合两个证据、读取表格关系或做轻度归纳；
- hard：需要跨文档、多个证据，或需要区分相似但不同的概念。

不要用措辞绕口来人为制造 hard。难度来自证据组织，不是来自故意模糊问题。

本批和完整数据集的分布目标：

- 可回答题约 70%，不可回答题约 30%；
- easy 约 30%，medium 约 50%，hard 约 20%；
- 尽量覆盖 fact、numeric、table、procedural、lexical 和 multi_doc；
- 每份内容足够的输入文档至少生成一题可回答候选题；
- 同一个知识点或同一段 evidence 原则上不超过两题；
- multi_doc 只在确实需要跨文档组合证据时生成；
- 文档不包含某类内容时不要硬凑该 category；
- 小批次允许明显偏离比例，最终由项目汇总报告检查整体分布。

所有比例都是目标，不是牺牲证据质量也必须满足的硬指标。

====================
四、可回答题要求
====================

可回答题必须满足：

- answerable=true；
- unanswerable_type=null；
- evidence 至少一条；
- keypoints 至少一个关键点组；
- reference_answer 非空；
- 问题不能直接复制完整证据句；
- 问题本身应明确，不依赖未给出的上下文；
- 不能只问“本文讲了什么”这类宽泛问题；
- 不生成答案完全相同、只替换少量措辞的大量重复题。

keypoints 使用二维数组。外层每一项代表一个必须命中的关键点，内层字符串代表该关键点允许接受的文本变体。

示例：

[
  ["弱人工智能", "Narrow AI"],
  ["强人工智能", "General AI"],
  ["超人工智能", "Super AI"]
]

不同事实不能放在同一个内层数组中。内层数组表达“任一变体命中即可”，外层数组表达“这些关键点都需要覆盖”。

====================
五、不可回答题要求
====================

不可回答题用于测试系统是否会在证据不足时拒答，不是随意生成与文档无关的问题。

unanswerable_type 只允许：

- out_of_scope：问题明显超出给定语料主题；
- insufficient_detail：文档包含相近主题，但缺少回答所需的具体信息。

不可回答题必须满足：

- category="unanswerable"；
- answerable=false；
- evidence=[]；
- keypoints=[]；
- reference_answer="根据给定语料无法回答该问题。"；
- review.whole_corpus_checked=false；
- 不能把你没读懂的内容误判为不可回答；
- 不能仅因为某一个文档没有答案，就断言完整 corpus 没有答案；
- 优先生成少量、高质量、容易人工复核的候选题。

注意：你只能生成“不可回答候选题”。最终是否真的不可回答，必须由人工检查完整 corpus 后确认。

====================
六、question_group 要求
====================

1. 每个独立知识点使用一个 question_group。
2. 同一个知识点的原问和改写问必须使用同一个 question_group。
3. 不同知识点不能为了减少 group 数量而合并。
4. 本轮默认每个 group 只生成一个单题，不主动批量生成同义改写，除非任务参数另有说明。
5. split 固定输出 null；不要自行分配 development、validation 或 test。

====================
七、多轮对话要求
====================

如果 TARGET_DIALOGUE_COUNT 大于 0，再生成 dialogues。

每组对话建议 2–4 轮，必须满足：

1. 第一轮问题是完整、独立的问题。
2. 后续至少一轮使用代词、省略或“它、这个方法、第二点、前一种”等上下文表达。
3. 每一轮都提供 standalone_question：
   - 第一轮通常与 question 相同；
   - 后续轮必须改写为脱离历史也能理解的完整问题；
   - standalone_question 不得改变原问题含义。
4. 每一轮仍必须独立提供 answerable、unanswerable_type、evidence、keypoints 和 reference_answer。
5. 后续回答仍只能依赖文档 evidence，不能只依赖前一轮助手回答。
6. 一个 dialogue 的所有轮次使用同一个 question_group，split 固定为 null。
7. 不要为了凑轮数生成没有自然关联的连续问题。

====================
八、禁止生成的字段
====================

下列字段依赖项目 parser 或人工流程，你不知道真实值，因此禁止在 evidence 中输出：

- parser_version
- unit_id
- start_char
- end_char
- snippet_sha256
- locator
- page_hint
- slide_number
- heading_path
- 任何文件 hash

顶层 parser_version 固定输出 null，等待项目内 prepare 填写。

====================
九、review 字段要求
====================

所有单题和 dialogue 的 review 都必须固定为：

{
  "status": "draft",
  "reviewer": null,
  "reviewed_at": null,
  "rubric_version": "rag-gold-v1",
  "evidence_checked": false,
  "answer_checked": false,
  "whole_corpus_checked": false
}

禁止把 status 改为 verified。

====================
十、ID 规则
====================

1. 单题 id 使用 QUESTION_ID_PREFIX 加四位连续数字，例如 b001-q0001。
2. 单题 group 使用 GROUP_ID_PREFIX 加四位连续数字，例如 b001-g0001。
3. dialogue_id 使用 DIALOGUE_ID_PREFIX 加四位连续数字，例如 b001-d0001。
4. turn_id 使用 dialogue_id + "-t" + 轮次，例如 b001-d0001-t1。
5. 本次输出中的所有 id、dialogue_id、turn_id 必须唯一。

====================
十一、document_types
====================

document_types 根据实际 evidence 文档扩展名填写，只允许：

- pdf
- docx
- txt
- md
- pptx

不带点号，使用小写，去重后按字母顺序排列。

不可回答候选题的 document_types 表示该题针对的 corpus 文档类型范围；如果针对整个混合 corpus，填写本批实际提供的全部文档类型。

====================
十二、输出 JSON 结构
====================

只输出一个合法 JSON 对象。

禁止输出：

- Markdown 代码围栏；
- JSON 前后的解释；
- 注释；
- 尾随逗号；
- NaN、Infinity 等非标准 JSON；
- “同上”“略”“参考前文”等占位文本。

使用 UTF-8 中文，不需要 ASCII 转义。

====================
十三、输出前自检
====================

在输出 JSON 前，在内部逐项检查，但不要输出检查过程：

1. JSON 能被标准解析器解析。
2. 所有 ID 唯一且符合前缀规则。

4. 每个 answerable 题和 turn 都有非空 evidence、keypoints 和 reference_answer。
````

## 三、推荐的分批生成方法

不要直接要求 AI 一次生成全部 150–200 题。推荐：

```text
第 1 批：先给 1–2 份文档，生成 10–20 题，检查 JSON 和 evidence 质量
第 2 批：修正提示词或文档读取问题
第 3 批以后：每批 1–5 份文档，使用独立 BATCH_ID 和 ID 前缀
全部单题稳定后：单独生成 8–10 组多轮对话
最后：项目内合并、去重、分组、prepare 和人工审核
```

建议不要让不同批次重复使用同一 ID 前缀。

## 四、人工核验清单

AI 输出后，至少逐题检查：

- [ ] 文件名真实存在且完全一致；
- [ ] snippet 能在原文中逐字找到；
- [ ] snippet 没有把不连续内容拼在一起；
- [ ] 问题没有歧义或隐藏前提；
- [ ] reference answer 没有超出 evidence；
- [ ] 数字、年份、单位、排名和百分比完全正确；
- [ ] 表格题确实依赖正确的行列关系；
- [ ] keypoints 的每一组都表示一个独立必需事实；
- [ ] 同义词没有把不同含义错误合并；
- [ ] multi_doc 题确实需要两个或更多文档；
- [ ] 不可回答题已检查完整 corpus；
- [ ] question group 没有把不同知识点混在一起；
- [ ] 多轮 standalone question 没有改变追问原意；
- [ ] 没有使用文档之外的常识或模型知识；
- [ ] review 在人工完成前保持 draft。

人工核验完成也不要手工猜测 offset、hash 或 locator，这些字段应由项目内
`dataset prepare` 根据确定性解析结果生成。

## 五、常见失败与处理

### snippet 不是逐字原文

退回 AI 重新生成该题，或人工从原文复制连续片段。不要只为了通过匹配而随意修改 parser。

### snippet 在同一文档出现多次

延长 snippet，加入足以区分位置的相邻原文；如果仍重复，等待项目内 locator 消歧。

### PPTX 内容来自图片

本轮没有 OCR 或图表理解。删除该题，不根据图片内容人工补入普通文本证据。

### AI 生成了外部知识

删除或改写该题。参考答案必须缩减到 evidence 能直接支持的范围。

### 不可回答题后来在其他文档找到答案

该题不能继续标记为不可回答。可以删除，或在有明确 evidence 后改为 answerable 并重新审核。

### 题目数量不足

接受较少的高质量候选题。更换或增加真实文档，不通过同义改写大量复制题目。

## 六、与正式 Dataset v3 的差别

本提示词输出的是 draft candidate：

- `parser_version=null`；
- `split=null`；
- evidence 只有 `document_name` 和 `snippet`；
- review 为 draft；
- 不包含 locator、offset 和 hash。

项目内 `prepare` 和人工审核完成后，正式 Dataset v3 才会具有：

- `parser_version="structured-v1"`；
- development/validation/test split；
- 稳定 eval unit ID；
- `start_char` / `end_char`；
- locator；
- snippet SHA-256；
- verified 人工审核记录。

候选 JSON 不能直接作为正式评测报告的输入。
