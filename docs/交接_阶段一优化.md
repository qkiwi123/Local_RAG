## 六、手动上传回归与修复

2026-07-17 手动测试出现两种前端报错：

1. `后端连接被关闭`；
2. `Expecting value: line 1 column 1 (char 0)`，且失败文件再次添加不再触发上传。

排查证据：

- 两轮报错后的 SQLite 均没有 `processing/failed` 记录，后端访问日志也没有对应
  `POST /api/upload`，说明请求根本没有到达入库路由；
- 四份原始文件位于 `eval/corpus`。使用与 Streamlit 相同的 HTTP 调用从冷启动后端
  逐个上传，全部返回 200，分别生成 7、12、14、17 chunks，证明文件、解析器、
  embedding 和 Chroma 均正常；
- 第二个报错来自前端对空响应或非 JSON 响应直接调用 `resp.json()`；
- 重试失效来自前端无论上传成功与否都把文件名写入 `_uploaded_set`；
- 原一键脚本同时启动前后端，前端可访问时后端可能仍未完成监听；现场还残留了一
  个旧版 Uvicorn `--reload` 进程，放大了端口切换窗口的不确定性。

已修复：

- 只有成功上传才写入完成集合，失败项保留并提供“重试失败文件”按钮；
- 上传标识从文件名改为“文件名 + 大小 + SHA-256”，同名不同内容不会互相屏蔽；
- 从 uploader 移除文件会清除本次完成标记，重新选择同一文件可创建新版本；
- 历史失败项加入独立失败状态，普通 rerun 不再自动提交，只有用户点击按钮才重试；
- 当前选择全部成功后轮换 `file_uploader` key，上传框自动恢复为空；部分失败时不
  清空，继续保留失败文件和重试入口；
- 空响应、非 JSON 响应统一降级为明确 HTTP 错误，不再抛 JSONDecodeError；
- 上传前先做后端健康检查，未就绪时整批不提交，只显示一次可重试错误；
- 本地 HTTP 客户端固定 `trust_env=False`，默认地址改为 `127.0.0.1`；
- 后端未预期入库异常记录 document ID、原始名、大小和 traceback；
- `scripts/start.ps1` 默认关闭热重载、等待后端健康后才启动前端，并把输出写入
  `logs/`；开发时可显式传 `-Reload`。

验证：前端状态回归测试 7 passed，包含 Streamlit `AppTest` 对“上传成功后控件值
为空”的页面级断言；定向上传/API 测试 15 passed；新脚本实测
先输出 `Backend health: ready` 再启动前端；冷启动后四文件批量上传全部 200，测试
版本均按 document ID 清理；浏览器真实上传 `sample.txt` 后，上传框立即清空且文档
列表出现 1 chunk 记录，随后测试记录已按 document ID 删除；全量测试为

## 十三、P2-1 Dense + BM25 + RRF（实现完成，未部署）

已实现应用侧中文 BM25、RRF 排名融合和 `dense` / `bm25` / `hybrid` 三种模式：

- BM25 使用 NFKC + 小写 + jieba 分词，索引快照由 Chroma revision 驱动懒重建；
- RRF 默认 `k=60`，按稳定 `chunk_id` 去重，保留 Dense/BM25 原始诊断字段；
- Hybrid 先合并 Dense top 15 和 BM25 top 15，Reranker 开启时再统一精排并截取 Top 5；
- dataset v2 完整保留 v1 的 21 题，并增加 6 道精确术语/数字陷阱题；
- `hybrid-ablation` 一次入库后执行五组检索，不调用 DeepSeek。

真实隔离评测共入库 68 chunks，五组结果：

| 模式 | Hit Rate | Recall | MRR | 原21题 Recall | Lexical Recall | 不可回答题进入 LLM | P95 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Dense | 90.91% | 86.36% | 78.79% | 88.24% | 80.00% | 80.00% | 0.088s |
| BM25 | 95.45% | 90.91% | 86.74% | 88.24% | 100.00% | 100.00% | 0.000s |
| Hybrid | 95.45% | 90.91% | 82.95% | 88.24% | 100.00% | 100.00% | 0.082s |
| Hybrid + Reranker | 100.00% | 95.45% | 95.45% | 94.12% | 100.00% | 100.00% | 8.097s |
| Dense + Reranker | 100.00% | 95.45% | 95.45% | 94.12% | 100.00% | 80.00% | 8.452s |

部署结论：**保留生产 Dense + Reranker，不切换 Hybrid**。Hybrid + Reranker 没有任何
Hit/Recall/MRR 增量或改善题，并使 q18 完全域外题进入 LLM。根因是 q18 中“公司”“员工”
等普通词产生了 BM25 sparse-only 候选；Dense 原本被 0.67 阈值全部过滤，RRF 联合集合却会
保留稀疏候选，而当前 Reranker 没有绝对分数拒绝门槛。这是算法取舍，不是隔离或缓存错误。

由于离线门槛已经失败，本轮没有执行两组各 27 题的 DeepSeek 完整回答评测，也没有修改
