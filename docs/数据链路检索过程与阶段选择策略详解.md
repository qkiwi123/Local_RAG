## 1. 项目整体架构与数据链路总览

### 1.1 系统组成

```text
React SPA (web/) ── /api ──► FastAPI (backend/)
                              ├─ 入库链路：upload → structured-v2 parser → chunker
                              │            → BGE embedding → Chroma + SQLite
                              └─ 问答链路：chat/chat stream → 标签范围解析
                                           → 追问改写 → Dense/BM25/Hybrid 检索
                                           → 阈值过滤 → Reranker 精排 → 文档限额
                                           → 上下文拼接 → DeepSeek → 引用提取/预览

SQLite (data/metadata.db, schema v3)   Chroma (data/chroma_db)
├─ documents                           └─ collection: knowledge_base
├─ document_units                        ├─ hnsw:space = cosine
├─ conversations / messages              ├─ chunk_id + content
├─ chat_requests / message_traces        └─ metadata(document_id/locator/offset…)
├─ tags / document_tags
└─ schema_meta (SCHEMA_VERSION=3)

评测链路 (eval/)
└─ 隔离 Chroma + SQLite + uploads → Dataset v3 校验 → ingest → retrieve/answer
   → metrics → report；另有 threshold-sweep / retrieval-sweep / hybrid-ablation
   三个“不调用 LLM”的离线参数选择工具。
```

### 1.3 两条主链路

**A. 入库链路（write path）**

```text
HTTP POST /api/upload (file + tags)
  → 文件名校验 / 扩展名白名单 / 50MB 上限
  → UUID document_id + 临时文件 .uploading
  → SQLite documents 登记 processing
  → structured-v2 parser（按后缀分发，可选 OCR）
  → ParsedUnit（稳定 unit_id / locator / blocks / canonical_text）
  → chunk_units（recursive 400/80 + 480 token 硬上限）
  → SQLite document_units 替换（事务）
  → BGE 批量向量化 + Chroma add
  → tags 写入
  → os.replace 原子落盘 + mark_ready
```

**B. 问答链路（read path）**

```text
POST /api/chat 或 /api/chat/stream
  → 问题清洗、长度校验、标签路径规范化
  → 标签集合 → 子孙展开 → ready document_id 集合（并集）
  → （持久化会话）begin_chat 幂等/并发守卫
      → bounded_history → rewrite_followup → standalone_question
  → retrieve_with_trace：
      候选预算 _candidate_k
      ├─ dense：embed_query → Chroma $in 过滤 → top candidates
      │        → cosine distance ≤ 0.67 硬过滤
      ├─ bm25：jieba 分词 → BM25Okapi(k1=1.5,b=0.75) → score>0 的 top
      └─ hybrid：dense + bm25 → RRF(k=60) 合并
      → Reranker(bge-reranker-v2-m3, CPU, top15 候选) 精排
      → 每文档最多 3 条 → 截取 top5
  → format_retrieval_context → 【来源N】上下文
  → DeepSeek(temperature=0.3, max_tokens=2000) 生成答案
  → extract_citations：正则 → 映射回本次检索结果 → 强校验 metadata
  → ChatResponse(answer, citations, trace)
```

## 2. 入库数据链路（write path）各阶段实现与选择策略

### 2.1 上传入口与文件安全

**实现位置**：`backend/routers/upload.py:57-151`

- `ALLOWED_EXTENSIONS = frozenset(ADAPTERS)`，当前为 `.pdf / .docx / .txt / .md / .pptx`
  （`backend/services/parsers/__init__.py:14-20`）。
- `MAX_FILE_SIZE = 50MB`（硬编码，非环境变量）。
- 文件名只接受纯文件名：拒绝绝对路径、目录穿越、`.`/`..`；非法标签抛 422。
- 每次上传生成 `document_id = uuid4().hex`，磁盘文件为 `{document_id}{suffix}`；
  临时文件为 `.{document_id}.uploading{suffix}`，全部成功后才 `os.replace` 为正式文件。
- 同名文件允许共存为多个版本；`original_name` 只用于展示，`document_id` 才是
  Chroma / SQLite / 文件 / 删除操作之间的稳定主键。

**选择策略**：

1. 稳定 ID 先于展示名：避免同名文件互相覆盖、支持版本化共存。
2. 先写临时文件再原子替换：失败清理只删临时文件，避免半成品入库。
3. 失败补偿（`upload.py:84-113`）：删除可能已写入的 Chroma 向量、document_units、
   标签关联与临时文件，并把 SQLite 记录置为 `failed`（保留错误用于排查）。

### 2.2 解析器分发与 structured-v2 结构契约

**实现位置**：`backend/services/parsers/__init__.py`、`backend/services/parsers/assembler.py`、
`backend/models/document_structure.py`

- `PARSER_VERSION = "structured-v2"`（`parsers/constants.py:7`）。
  即使 OCR 全部关闭，版本也全局为 v2，保证不会出现“部分文档 v1、部分文档 v2”的混写。
- `parse_document_structure()` 按后缀调用 `DOCUMENT_ADAPTERS`，返回
  `ParsedDocument(units=[ParsedUnit...], warnings=[ParseWarning...])`。
- 统一结构模型：
  - `ParsedBlock`：`block_id / block_type / text / sequence / heading_level / list_level /
    table_rows / attributes`；类型包括 `heading/paragraph/list_item/table/code/quote`。
  - `LocatedBlock`：追加 `start_char/end_char`，并校验
    `end-start == len(text)`、切片与 `canonical_text` 一致。
  - `SourceLocator`：`kind ∈ {page, virtual_page, slide, section, sheet}` +
    `unit_index/location_label/page_number/slide_number/heading_path`。
  - `ParsedUnit`：`unit_id` 必须等于
    `sha256(document_id|parser_version|locator_json)[:16]`；
    `canonical_text` 必须等于所有 `block.text` 以 `\n\n` 连接；
    block `sequence` 从 0 连续递增；`block_id` 由 unit_id + sequence 确定。
  - `assemble_parsed_unit()` 统一生成上述 ID、sequence 与 offset
    （`document_structure.py:277-328`），各 Adapter 只负责“识别结构”。

**选择策略**：把 ID/offset/canonical_text 的确定性规则集中到 assembler，
使引用定位可以跨格式校验；后续 chunker 只依赖 `ParsedUnit`，新增格式无需改动下游。

### 2.3 五格式 Adapter 的分单元策略

| 格式 | locator.kind | 单元划分规则 | 主要 block 策略 | 说明 |
|---|---|---|---|---|
| PDF | `page` | 每真实页一个 unit | 段落；空页输出 `[第X页无可提取文本]` 占位；OCR A/B 层可注入视觉块 | PyPDF2 失败自动回退 pdfium，并记 warning |
| DOCX | `virtual_page` | 每 30 个非空段落一个逻辑页；表格不占段落配额，跟随当前逻辑页 | 标题(outlineLvl 或 Heading/标题样式)→heading；编号段落→list_item；表格→确定性 Markdown | 保持 XML 阅读顺序；合并单元格去重、空行/重复表头过滤 |
| TXT | `virtual_page` | 固定 50 行一个逻辑页 | 按空行拆 paragraph | 无真实分页，label 为“逻辑页 N” |
| Markdown | `section` | 一级/二级标题开启新 section；单 section 超过 12,000 字符时确定性切分 | heading/paragraph/list_item/table/code/quote；front matter 丢弃；链接保留 URL；表格转 Markdown | label 为“章节：A / B”，无标题时为“第 N 节” |
| PPTX | `slide` | 每张幻灯片一个 unit；无原生文本的 slide 只记 warning 不入库 | 标题占位符→heading；正文按 top/left 排序；组合形状递归展开；列表判定用 paragraph.level/buChar/buAutoNum；表格转 Markdown | C 层 OCR 图片按阅读顺序原位插入 |

**选择策略**：

- 不把逻辑页码伪装成物理页码：DOCX/TXT 用 `virtual_page`、PPTX 用 `slide`、
  MD 用 `section`，前端统一显示 `location_label`。
- DOCX“30 段/页”与 TXT“50 行/页”是保持可定位引用的折中方案，因为无渲染引擎时
  无法还原真实分页（历史文档 `docs/交接_阶段一优化.md`）。
- MD 以标题分 section，优先保留语义单元；12,000 字符是 section 上限，避免单单元
  过大导致 chunk 定位和预览膨胀。

### 2.4 文本规范化策略

**实现位置**：`backend/services/parsers/text.py:21-49`

- 全角字母数字（0xFF10–0xFF19 / 0xFF21–0xFF3A / 0xFF41–0xFF5A）转为半角。
- `\u3000` → 空格；`\r\n`/`\r` 统一为 `\n`。
- 每行横向空白折叠并 strip；连续空行只保留一个；整体 strip。
- 明确“不改写语义内容”，不删中文标点。

**选择策略**：P1-2 实测这种“保守清洗 + DOCX 表格保序解析”把 Hit Rate 从 82.35%
提到 94.12%、Recall 76.47%→85.29%（证据：`eval/results/p1-2-docx-table/`）。

### 2.5 OCR / 视觉识别分支选择

**实现位置**：`backend/services/vision.py`、`backend/services/vision_cache.py`、
`backend/services/parsers/ocr.py`、`backend/services/parsers/pdf.py`、
`docx.py`、`pptx.py`；配置见 `config.py:125-143`。

三层能力独立开关（`OCR_ENABLED` 为总开关）：

| 层 | 开关 | 触发条件 | 实现路径 | 产出 |
|---|---|---|---|---|
| A | `OCR_PDF_SCANNED` | PDF 页 `extract_text()` 为空 | pypdfium2 渲染 scale=2 → Pillow 长边≤1600 → `recognize_text` | 段落文字 blocks（`attributes.ocr=True`） |
| B | `OCR_PDF_PAGE_IMAGES` | PDF 页有原生文本且检测到图片对象 | 整页渲染 → `describe_image` | ≤150 字图表说明 blocks（`ocr=True`） |
| C | `OCR_EMBEDDED_IMAGES` | DOCX/PPTX 内嵌图片 | 提取图片 blob → 统一转 JPEG → `recognize_text` | 按阅读顺序原位插入的文字 blocks |

关键实现选择：

1. **失败/超预算不阻塞入库**：`run_vision()`（`parsers/ocr.py:84-133`）统一处理
   预算、缓存、失败短期记忆与 warning；视觉失败只追加 `ParseWarning`。
2. **成本控制**：
   - 单文档视觉调用上限 `OCR_MAX_PER_DOCUMENT`（默认 20），缓存命中不计入预算；
   - 缓存键 = `sha256(file) + object_id + model`，存 `data/vision_cache/*.txt`，
     原子替换写入，重建索引时命中缓存不重复计费；
   - 同进程失败短期记忆 TTL 600s，防止批量重建时失败请求风暴。
3. **视觉端点与问答 LLM 完全解耦**：`VISION_*` 独立配置，默认 GLM-4.6V-Flash；
   DeepSeek 问答链路不受影响。
4. **OCR 产出进入 canonical text 并带标记**：`attributes={"ocr": True,
   vision_model, vision_kind}`，预览 UI 显示“AI 识别”徽标；因为 canonical text 变化，
   必须升 `PARSER_VERSION` 并重建索引。
5. PDF 文本提取：首选 PyPDF2（保持历史文本基线），`PyPdfError` 时回退 pdfium，
   并追加 `pdf_reader_fallback` warning（`parsers/pdf.py:136-147`）。

### 2.6 文本切分（chunker）

**实现位置**：`backend/services/chunker.py`

#### 2.6.1 两种策略

| 策略 | 行为 | 是否受 max_tokens 限制 |
|---|---|---|
| `fixed` | 按 `CHUNK_SIZE` 字符等距切，步长 `CHUNK_SIZE - CHUNK_OVERLAP` | **否**（实现忽略 max_tokens） |
| `recursive` | 目标 `CHUNK_SIZE` 字符 + `CHUNK_MAX_TOKENS` 硬上限，选择语义边界 | 是 |

#### 2.6.2 recursive 的边界优先级与算法

- 边界模式（`chunker.py:22-26`）按优先级：
  1. 段落：`\n{2,}`；
  2. 句子：`[。！？；\n]+`；
  3. 子句：`[，、]+`；
  4. 兜底：字符硬切。
- 每一步：
  1. `char_end = min(start + chunk_size, len(text))`；
  2. 用二分找到满足 `token_counter(text[start:middle]) <= max_tokens` 的最远 `hard_end`
     （BGE 实际 tokenizer，含特殊 token）；
  3. 在 `[start + min(chunk_size//3, ...), hard_end]` 窗口内选**最高优先级**的边界；
     若窗口内无边界，则回退到 `(start, hard_end]` 内任意语义边界，再不行才硬切；
  4. overlap 按**字符**回退：`start = max(start+1, end - overlap)`。
- `chunk_units()`（`chunker.py:309-375`）直接切 `ParsedUnit.canonical_text`：
  - **绝不跨 unit**（PDF 页、DOCX 逻辑页、MD section、PPTX 幻灯片之间不会互相粘连）；
  - `chunk_id = f"{unit_id}_s{start_char}_e{end_char}"`，稳定可复算；
  - metadata 携带 `unit_id/unit_index/locator_kind/location_label/page_number/
    slide_number/heading_path/content_type/start_char/end_char/char_count/token_count/
    parser_version`；
  - `content_type` 取与 chunk 相交的 blocks 的类型（单一类型时），否则 `mixed`。

#### 2.6.3 为什么选 recursive 400/80 + max 480

历史 P1-3 实验（`eval/runs/p1-3-*`、`docs/交接_阶段一优化.md` 第十节）：

| 方案 | chunks | Hit Rate | Recall | MRR | 最大 tokens |
|---|---:|---:|---:|---:|---:|
| fixed 500/50（P1-2） | 51 | 94.12% | 85.29% | 75.49% | 491 |
| **recursive 400/80** | **68** | **94.12%** | **88.24%** | **81.37%** | **381** |
| recursive 600/100 | 47 | 94.12% | 85.29% | 72.55% | 477 |
| recursive 800/120 | 49 | 88.24% | 82.35% | 67.16% | 480 |

选择 recursive 400/80 的理由：Recall 与 MRR 最优，且最大 token 381 落在 BGE 512
安全窗内；`CHUNK_MAX_TOKENS=480` 是硬上限（512 − 32 特殊标记余量）。

### 2.7 Embedding 策略

**实现位置**：`backend/services/embedding.py`、`backend/services/model_cache.py`

- 模型：`BAAI/bge-large-zh-v1.5`，1024 维，`local_files_only=True`（离线快照解析，
  首次需手动下载）。
- `SentenceTransformer.encode(..., normalize_embeddings=True)`：向量归一化后余弦距离
  数值更稳定。
- 查询侧可选 `EMBEDDING_QUERY_INSTRUCTION` 前缀；**默认与历史选择均为空（noinst）**。
- 模型惰性加载（`lru_cache`），首次真实编码才加载；服务启动时
  `PREWARM_MODELS=true` 会后台预热（`services/warmup.py:15-44`），把冷启动成本挪到启动期。

**选择策略**（P1-1，证据 `eval/results/p1-1-bge/`）：

- BGE large 相比 all-MiniLM-L6-v2：Hit +41.17pp、Recall +44.12pp、MRR +50.88pp；
- query instruction A/B：noinst 与 inst 的 Hit/Recall 相同，但 noinst 的 MRR 高
  2.94pp 且检索延迟更低，故选择 noinst；
- 代价：进程 RSS 增加约 1.1 GiB，入库耗时增加。

### 2.8 向量库写入（Chroma）

**实现位置**：`backend/services/vector_store.py:23-127`

- 模块级 `PersistentClient` + `get_or_create_collection("knowledge_base",
  metadata={"hnsw:space": "cosine"})`；Chroma `distance` 越小越相似。
- 每个 chunk 写入 `ids / documents / embeddings / metadatas`。
- metadata 是**轻量定位信息**：`document_id, document_name, chunk_index,
  content_type, block_index, start_char, end_char, char_count, token_count,
  parser_version`，以及可选的 `page_number / unit_id / unit_index / locator_kind /
  location_label / heading_path / slide_number`（`vector_store.py:84-114`）。
  注意：`heading_path` 以 JSON 字符串存储，引用提取时再解析。
- 进程内 `_index_revision` 每次 add/delete 自增，供 BM25 判断 Chroma 内容是否变化。

**选择策略**：结构化数据与向量索引分工——SQLite 保存完整 units（供预览/重建），
Chroma 只存检索所需的原文 + 轻量定位 metadata，避免 Chroma metadata 过重。

### 2.9 SQLite 业务数据与 schema 版本策略

**实现位置**：`backend/services/metadata_schema.py`、`unit_store.py`、
`document_store.py`、`tag_store.py`

- `SCHEMA_VERSION=3`：v1 基础表；v2 加 `tags/document_tags`；v3 加 `message_traces`。
- 启动时 `bootstrap_structured_database()` 幂等建库；版本化旧库逐版本迁移；
  **未版本化旧库拒绝读写**，避免静默混写。
- `document_units` 主键 `(document_id, parser_version, unit_id)`；
  写入前做完整 Pydantic 校验；读取时重新组装校验，不直接把 DB JSON 当可信对象外传。
- 数据策略：**派生数据（units/chunks/向量）清空重建，业务数据（登记/会话/标签）原地迁移**。

### 2.10 标签范围与入库标签写入

**实现位置**：`backend/services/tag_store.py`

- 标签是 `/` 分隔的路径，任意深度 ≤6，总长 ≤200；创建时自动补齐父级节点。
- 文档与标签多对多；上传可选 tags，缺失标签自动创建（含父级）。
- 检索/文档筛选统一语义：选中标签先 `expand_tag_paths` 展开全部子孙，
  再 `resolve_document_ids` 取 ready 文档 ID 集合，多标签取并集。

### 2.11 安全重建索引

**实现位置**：`scripts/rebuild_index.py`

- 从 SQLite `ready` 登记读取原文件路径，重新走 parse → chunk → embed。
- 安全约束：拒绝原地重建、拒绝覆盖非空目标目录；写入前校验
  `chunk_id == unit_id_s{start}_e{end}`、切片一致、登记 chunk 数一致
  （`--accept-chunk-count-change` 可显式接受 parser 变化）；写入后核对总块数、
  逐文档块数、document_id 与向量维度。
- 用途：改 embedding 模型、chunk 规则或 parser 版本后，必须在**独立目录**重建，
  验收后再切换 `.env` 路径。

## 3. 问答检索链路（read path）各阶段实现与选择策略

### 3.1 入口参数与检索范围（标签筛选）

**实现位置**：`backend/routers/chat.py:88-99`、`backend/services/tag_store.py:265-311`

- `question` 非空且 ≤ `CONVERSATION_MESSAGE_MAX_CHARS`（默认 8000）。
- `tags` 规范化去重后：
  - 空列表 → `allowed_document_ids=None`，全库检索；
  - 非空 → `resolve_document_ids(tags)` 得到 ready 文档 ID 列表（父级含子孙、并集）；
    结果为空列表时检索直接短路为“当前筛选范围内未找到相关内容”。
- 过滤实现：
  - Dense：Chroma `where={"document_id": {"$in": [...]}}`；
  - BM25：建索引前按 document_id 集合过滤，缓存键包含排序后的集合；
  - Hybrid：两路同过滤后再 RRF。
- 不改 Chroma metadata、存量 chunk 零迁移（设计决策见
  `docs/superpowers/specs/2026-08-13-rag-v2-optimization-design.md` 第 5 节）。

### 3.2 多轮会话前置处理

**实现位置**：`backend/routers/chat.py:101-139, 462-494`、
`backend/services/conversation_store.py:215-349`、`conversation_context.py`

1. `begin_chat` 在 SQLite 事务内完成幂等/并发控制：
   - 同 `request_id` 已完成 → 直接重放历史回答（含持久化 Trace）；
   - pending → `request_in_progress`；failed → 必须显式 `retry_failed=true`；
   - `expected_last_message_id` 与会话实际末尾不一致 → 409 并发冲突；
   - 会话消息数上限 `CONVERSATION_MAX_MESSAGES`（200）。
2. **历史裁剪** `bounded_history`（`conversation_context.py:7-21`）：
   - 先取最近 `CONVERSATION_HISTORY_MESSAGES`（12）条；
   - 从最新往前累加，总 token ≤ `CONVERSATION_HISTORY_MAX_TOKENS`（1500）；
   - 单条先按 `CONVERSATION_MESSAGE_MAX_CHARS`（8000）截断，仍超限再折半一次。
3. **追问改写**：有历史时调用 `rewrite_followup`（`llm.py:90-113`）把含指代/省略的
   追问改写成独立可检索问题；`temperature=0, max_tokens=200`；
   **改写失败时记录 warning 并回退原始问题，不阻断问答**。
4. 生成阶段历史只用于连贯表达：System Prompt 第 7 条明确“历史不能作为事实证据，
   事实必须由本轮文档内容支持”。

### 3.3 检索总编排

**实现位置**：`backend/services/retriever.py:30-189`

#### 3.3.1 候选预算 `_candidate_k`

```text
reranker 开启：candidate_k = max(RETRIEVAL_TOP_K, RERANKER_CANDIDATE_K)  # max(5,15)=15
reranker 关闭：candidate_k = RETRIEVAL_TOP_K * 2                        # 5*2=10
```

选择逻辑：精排需要更大的候选池；无精排时只多取一倍，再做阈值/文档限额，控制上下文。

#### 3.3.2 Dense 候选

- Trace 开启时拆分计时：`embed_query` → `search_by_embedding`；
  否则直接 `vector_search`（`retriever.py:44-60`）。
- Chroma 返回 cosine distance 越小越相似，取 top `candidate_k`。
- **阈值硬过滤**（`retriever.py:66-78`）：只保留
  `distance <= RETRIEVAL_DISTANCE_THRESHOLD` 的行；被滤掉的行带
  `filtered_reason="distance_above_threshold"`（仅 Trace 可见）。
- 历史选择：P1-4 在真实 21 题上扫描 0.50–0.75，等价最优平台 0.66–0.68，
  取中点 **0.67**（证据 `eval/results/p1-4-threshold-calibration/`）。

#### 3.3.3 BM25 候选（应用侧稀疏检索）

- 分词（`sparse_retriever.py:26-34`）：NFKC + 小写 → 正则抽取
  `[\u4e00-\u9fffA-Za-z0-9_.+%\-]+` → `jieba.lcut(cut_all=False)` → 过滤纯标点。
- 索引（`sparse_retriever.py:43-78`）：
  - 从 `vector_store.get_all_chunks()` 全量快照惰性构建 `BM25Okapi`；
  - 缓存键 = `(Chroma index_revision, BM25_K1, BM25_B, allowed_document_ids 排序集合)`；
  - 进程内只保留**一个**缓存槽，配置或范围变化时整体重建。
- 检索：`get_scores` 后**只保留 score > 0** 的行，按 score 降序（同分按 chunk_id），
  返回 top `candidate_k`（先请求 `max(candidate_k, BM25_TOP_K)` 再截断）。
- 历史参数：`BM25_K1=1.5 / BM25_B=0.75 / BM25_TOP_K=15`，P2-1 实现时沿用
  Okapi 惯例；`BM25_TOP_K` 保证融合前稀疏路至少有 15 条参与。

#### 3.3.4 Hybrid = RRF 倒数排名融合

- `reciprocal_rank_fusion(dense, sparse, rrf_k=60, top_k=candidate_k)`
  （`fusion.py:6-50`）：
  - 按稳定 `chunk_id` 去重，累加 `1/(rrf_k + rank)`；
  - 只融合排名、不混原始分数；两路排名字段保留用于诊断；
  - 排序键：`rrf_score` 降序 → 两路最小 rank 升序 → `chunk_id` 升序（完全确定）。
- **重要实现语义**：进入 RRF 的 dense 路已经是“阈值过滤后”的结果，
  而 BM25 路没有距离阈值；因此 Hybrid 会出现 sparse-only 候选绕过 0.67 阈值进入
  后续 Reranker/LLM 的情况。这正是 P2-1 消融中 q18 类完全域外题进入 LLM 的根因
  （证据 `eval/results/p2-1-hybrid-retrieval/decision.md`）。
- 历史结论：**P2-1 未部署 Hybrid**，生产应保持 `dense + reranker`。

#### 3.3.5 Reranker 精排

- `FlagReranker(resolve_cached_snapshot("BAAI/bge-reranker-v2-m3"),
  use_fp16=False, devices=CPU, batch_size=8, max_length=512)`；
- 对全部候选 `compute_score([(question, chunk_content)...])`，按
  `reranker_score` 降序（`reranker.py:25-43`）。
- 历史选择（P1-5）：k=15/20/30 的 Hit/Recall/MRR 完全持平，按 P95 延迟选择
  **k=15**（比 k=20/30 分别低约 0.97s/4.20s）；精排在文档限额之前执行，
  避免黄金证据被同文档高相似块提前占满名额。
- 代价：CPU 推理显著增加延迟（P1-5 平均总延迟 2.043s→9.314s）；当前已知主要
  延迟来源。

#### 3.3.6 单文档限额与最终 TopK

- `_limit_per_document(ranked, top_k)`（`retriever.py:133-148`）：
  - `max_per_document = 3`（**硬编码**，未暴露配置）；
  - 按精排后顺序遍历，每个 `document_id` 最多保留 3 条，再截取 `RETRIEVAL_TOP_K`(5)。
- 选择策略：防止长文档垄断返回结果；先精排后限额，保证限额阶段看到的是
  query-chunk 相关性而不是同文档的初始相似度。

#### 3.3.7 检索 Trace

- 仅在 `RETRIEVAL_TRACE_ENABLED=true` 时构造（关闭时不额外计时、不保留候选原文）。
- `TraceCollector`（`retrieval_trace.py:26-152`）按执行顺序记录：
  `dense → bm25 → rrf → reranker → selected` 各阶段候选快照，
  按 `chunk_id` 去重保存完整原文一次；记录 `distance/dense_rank/bm25_rank/
  bm25_score/rrf_score/reranker_score/eligible/filtered_reason/selected`。
- 计时字段：`query_embedding/dense_retrieval/sparse_retrieval/rrf/rerank/
  context_formatting/llm_generation/total`（毫秒）。
- `finalize_chat_trace` 补最终上下文 `chunk_count/char_count/token_count`。
- 持久化：`message_traces` 表，总字节 ≤ `TRACE_STORAGE_MAX_BYTES`(50MB)，
  超限按 `created_at` 淘汰最旧（LRU）；会话删除级联清理。

### 3.4 上下文格式化

`format_retrieval_context`（`retriever.py:230-264`）把最终 TopK 拼成：

```text
【来源1】《文档名》第 3 页 / 逻辑页 2 / 第 4 张幻灯片 / 章节：A / B
文本内容…

【来源2】…
```

- 来源编号是**本轮上下文的 1-based 序号**，由后端生成；
  无 `location_label` 时回退 `page_number`，否则“位置未知”。
- 注意：没有全局字符/token 预算层，上下文规模完全由“chunk 大小 + top_k + 单文档 3 条”
  间接决定（见 7.2 节问题 T-06）。

### 3.5 LLM 生成

**实现位置**：`backend/services/llm.py`

- 模型：`DEEPSEEK_MODEL`（OpenAI 兼容端点），`temperature=0.3`、
  `max_tokens=2000`（**硬编码**）。
- System Prompt 核心规则：
  1. 只能依据给定文档回答，没有信息要明确告知；
  2. 关键结论必须引用 `【来源N】`；
  3. N 必须是真实存在的编号，禁止模型自己写文档名/页码；
  4. 文档不足时回答“根据现有文档，未找到相关信息”，且不附加来源编号；
  5. 简洁准确、不编造；
  6. 文档矛盾时指出并分别引用；
  7.（多轮）历史只用于指代与连贯，不能作为事实证据。
- 无历史：`ask(question, context)`；有历史：`ask_with_history(...)`，
  把 `对话历史 + 本轮检索问题(standalone_question) + 本轮文档内容 + 用户原始问题`
  一起给模型。
- 流式版本逐 token yield。

### 3.6 引用提取与引用预览

**实现位置**：`backend/utils/citation.py`、`backend/services/structured_citation_preview.py`、
`backend/routers/citations.py`

1. 正则 `【来源\s*(\d+)】` 从原始回答提取编号，按编号去重。
2. `N` 必须落在本次 `retrieval_results` 范围内，否则丢弃（模型伪造编号不产生 Citation）。
3. 对命中结果做**强 metadata 校验**：document_name/document_id/unit_id/unit_index/
   locator_kind ∈ 5 种 / location_label / parser_version==PARSER_VERSION /
   chunk_id / start_char / end_char / heading_path 全部合法才生成 Citation；
   任一项不合规整条丢弃。
4. `excerpt = chunk.content[:200]`，`preview_available` 由全局开关决定。
5. 引用预览（可选开关 `CITATION_PREVIEW_ENABLED`）：
   - 从 Chroma 精确取 chunk，从 SQLite 取整文档 units；
   - 校验 `chunk_id == unit_id_s{start}_e{end}`、
     `unit.canonical_text[start:end] == chunk.content`、
     locator 各字段与 chunk metadata 一致；
   - 整文档字符上限 `CITATION_PREVIEW_MAX_DOCUMENT_CHARS`(500k)、单 unit
     上限 `CITATION_PREVIEW_MAX_PAGE_CHARS`(200k)；
   - 响应 `Cache-Control: private, no-store`。
6. 引用定位因此是**可验证闭环**：LLM 只输出编号 → 后端映射真实 chunk →
   预览按 offset 高亮，模型无法通过自由文本伪造系统认可的来源。

### 3.7 空检索与错误短路

- 检索结果为空时不调用 LLM，直接返回固定拒答文案；带标签筛选时使用另一套文案，
  引导用户清除标签（`chat.py:153-194`）。
- 固定文案必须与评测 `eval/adapters.py:22` 的 `REFUSAL_CANNED` 逐字一致。
- 错误码：检索失败 500/`retrieval_error`，LLM 失败 502/`llm_error`；
  流式协议中检索/生成期错误以 NDJSON `error` 事件返回。

### 3.8 流式协议与中断语义

- `POST /api/chat/stream` 返回 `application/x-ndjson`：
  `meta → delta* → citations → done`；重放已 complete 请求时以单帧 done 返回。
- 中断语义甲：客户端断开（GeneratorExit）时 `fail_chat(request_id, "interrupted")`，
  不保存半截答案，用户可显式重试（`chat.py:420-431`）。

## 4. 评测链路与参数选择机制

### 4.1 隔离约束

`eval/eval.py:41-116` 在任何 backend import 前注入独立
`CHROMA_PERSIST_DIR / UPLOAD_DIR / METADATA_DB_PATH`，并由
`adapters.assert_isolation()` 防御 `load_dotenv(override=True)` 之类的配置回归。
`adapters.ingest_corpus` 复刻 upload 链路；`answer_question` 复刻 chat 链路
（空检索固定拒答不调 LLM）。

### 4.2 Dataset v3 门禁

- v3 数据集必须通过 manifest/gold 校验；非严格模式仅允许预检
  （`--allow-draft-v3`），因为 41 个审核组仍为 draft；
- 正式评测禁止 `--limit`；严格校验要等真实审核者逐项签核（见 README 当前状态）。

### 4.3 指标口径（eval/metrics.py）

- 检索命中：文档名相同 且 `norm(snippet) ⊆ norm(chunk内容)`；不用页码判定，
  对切分策略鲁棒。
- `norm = NFKC + 去所有空白 + 小写`。
- 可回答题：Hit Rate / Recall / MRR（首条 gold 排名倒数）/ Keypoint Coverage /
  Strict Accuracy / Citation Precision / Citation Recall / Citation Emission Rate /
  False Refusal Rate。
- 不可回答题：Refusal Accuracy、伪引用数（回答出现任何 `【来源N】` 即计 1 次）。
- 关键点/严格准确率用连续字符串包含判断，对 Markdown 加粗、代码符号、空格和同义改写
  过于敏感，README 明确“当前会系统性低估回答质量，不能单独作为阻断指标”。

### 4.4 离线参数选择工具（不调用 LLM）

| 工具 | 扫描对象 | 选择规则 | 历史结论 |
|---|---|---|---|
| `threshold-sweep` | 一次真实检索重放多个 cosine 阈值 | 先避免可回答题空检索，再保 Hit/Recall/MRR，随后减少不可回答题进入 LLM；等价平台取中点 | 0.67 |
| `retrieval-sweep` | Reranker 候选数 k | 先最大化 (Hit, Recall, MRR)，质量相同取 P95 延迟更低、k 更小 | k=15 |
| `hybrid-ablation` | dense/bm25/hybrid ± reranker 五组 | 部署门槛 = 相对 `dense_reranker` 至少一个指标正增量 **且** 无回归题；同时观察不可回答题进入 LLM | 未通过，不部署 Hybrid |

### 4.5 历史参数决策一览

| 候选预算 | top_k / 2× / 15 | reranker 开=max(top_k,15)，关=2× | 精排需要更大候选池 | `retriever.py:30-34` |
| Dense 阈值 | 无/固定/扫描 | 0.67 硬过滤 | P1-4 平台中点，平衡误拒与域外题 | `retriever.py:66-78`；P1-4 证据 |
| 稀疏检索 | 无/外部 ES/应用 BM25 | jieba+BM25Okapi，score>0，k1=1.5/b=0.75 | 中文词法召回；单机零依赖 | `sparse_retriever.py` |
| 融合 | 分数混合/RRF | RRF k=60，按 chunk_id 去重 | 只融合排名，避免量纲问题 | `fusion.py` |
| 精排 | 无/Cross-encoder | bge-reranker-v2-m3 CPU，候选 15 | P1-5 质量持平选最低延迟；精排在限额前 | `reranker.py`；P1-5 证据 |
| 文档限额 | 无/可配置/固定 | 每文档最多 3（硬编码）后 top5 | 防长文档垄断 | `retriever.py:133-148` |
| 上下文 | 原样/编号格式 | `【来源N】+ 文档名 + location` | 便于 LLM 引用与后端解析 | `retriever.py:230-264` |
| LLM | 温度/长度 | 0.3 / 2000 tokens | 低温度减少幻觉；当前硬编码 | `llm.py:80-87` |
| 引用 | 模型写来源/后端映射 | 只认 `【来源N】`，后端强校验 | 杜绝伪引用 | `citation.py:37-143` |
| Trace | 全开/全关 | 默认关，本地 .env 开 | 敏感原文只进可信环境 | `retrieval_trace.py`、`config.py:71-74` |
| 预览 | 全开/全关 | 默认关，本地 .env 开 | 完整解析文本只进可信环境 | `citations.py:23-24` |

### 6.2 入库侧调优入口

| 想调什么 | 改哪里 | 注意事项 |
|---|---|---|
| chunk 粒度/重叠 | `CHUNK_SIZE / CHUNK_OVERLAP / CHUNK_STRATEGY / CHUNK_MAX_TOKENS` | 变化后用 `scripts/rebuild_index.py` 在独立目录重建并验收；不能原地改 |

| MD section 上限 | `parsers/markdown.py:16 MAX_SECTION_CHARS` | 同上 |

### 6.3 检索侧调优入口

| 想调什么 | 改哪里 | 注意事项 |
|---|---|---|
| 最终上下文块数 | `RETRIEVAL_TOP_K` | 影响 Prompt 长度与引用编号范围 |
| 召回-精度平衡 | `RETRIEVAL_DISTANCE_THRESHOLD` | 只在 Dense 路生效；用 `threshold-sweep` 基于真实 retrieval 校准 |
| 检索模式 | `RETRIEVAL_MODE` | 三选一；Hybrid 有“稀疏候选绕过阈值”语义，历史上未通过部署门槛 |
| 精排开关/候选数 | `RERANKER_ENABLED / RERANKER_CANDIDATE_K` | CPU 精排是当前延迟主因；用 `retrieval-sweep` 重扫 |
| 精排吞吐 | `RERANKER_BATCH_SIZE / RERANKER_MAX_LENGTH` | 小 batch 省内存、大 batch 通常更快（需实测） |
| BM25 | `BM25_K1 / BM25_B / BM25_TOP_K` | 影响词法路召回 |
| RRF | `RRF_K` | k 越小排名差权重越大 |
| 单文档最多条数 | `retriever.py:135 max_per_document=3` | **硬编码**，调优需改代码 |
| LLM 温度/长度 | `llm.py:83-84, 143-144` | **硬编码** |
| 历史窗口 | `CONVERSATION_HISTORY_MESSAGES / _MAX_TOKENS / _MESSAGE_MAX_CHARS` | 影响追问改写质量与 token 成本 |
| 模型预热 | `PREWARM_MODELS` | 关掉可省启动内存，但首次查询变慢 |
| Trace 开销 | `RETRIEVAL_TRACE_ENABLED` | 关闭后不计算/不持久化 Trace |

### 6.4 安全调优流程建议

1. 在 `eval/dataset/questions_v3.json` 上先跑离线检索指标（threshold-sweep /
   retrieval-sweep / hybrid-ablation 都不调 DeepSeek）；
2. 需要完整回答质量时再跑完整 eval（会调用 DeepSeek，注意成本与隐私）；
3. 变更 chunk/parser/embedding 后，用 `scripts/rebuild_index.py` 在独立目录重建，
   核对 chunk 数/维度/切片一致后再切 `.env`；
4. 每次只改一个变量，用 `compare` 命令对照报告，避免把单次 LLM 波动误判为算法收益；
5. 生产级结论以真实 Dataset v3 人工签核后的正式评测为准（当前 draft 只能预检）。

## 7. 问题与风险清单（仅记录，未改代码）

### 7.1 需要立即确认的高优先级项

**T-01：当前 `.env` 的 `RETRIEVAL_MODE=hybrid` 与 P2-1 结论和模板相反**

- 现状：`config.py:66` 默认 dense；`.env.example` 明确写“通过消融验收前保持 dense”；
  README/交接文档记录 P2-1 **未部署 Hybrid**（Hybrid + Reranker 无质量增量，且
  sparse-only 候选会绕过 0.67 阈值让完全域外题进入 LLM）；
  但本地 `.env` 当前值是 `hybrid`，且 `RERANKER_ENABLED=true`。
- 影响：线上实际运行的是历史上被判定不部署的 `hybrid + reranker` 组合；
  不可回答/域外题进入 LLM 的风险被激活。
- 建议：确认是有意切换还是误配；若维持 hybrid，应先在 Dataset v3 上重跑
  `hybrid-ablation` 并明确新的部署证据；若回退，改 `.env` 为 `dense` 后重启。

**T-02：`eval/metrics.py` 仍硬编码 `parser_version == "structured-v1"`**

- 位置：`eval/metrics.py:84`（`parse_citations` 的 `structured_location` 判断）。
  当前运行时 `PARSER_VERSION = "structured-v2"`。
- 影响：对没有 `page_number` 的 MD（section）与 PPTX（slide）来源，其引用会被
  判为 invalid，导致 Citation Precision/Recall 等指标在 structured-v2 正式评测时
  系统性低估；当前 README 的 v3 预检数字是 structured-v1 历史基线，尚未暴露此问题。
- 建议：下次 v2 评测前，将该比较改为当前 `PARSER_VERSION` 或直接判断
  `unit_id + location_label` 存在。

**T-03：`CHUNK_STRATEGY=fixed` 时 `CHUNK_MAX_TOKENS` 不生效**

- 位置：`chunker.py:175-180` fixed 分支只按字符切分，忽略 `max_tokens`。
- 影响：若有人把策略改回 fixed 且 `CHUNK_SIZE` 较大（如代码默认 500），
  实际 token 数可能超过 BGE 512 上限，SentenceTransformer 会静默截断，
  造成 chunk 内容与 Chroma 文本/向量语义不一致；引用预览切片校验此时能兜底报警，
  但检索质量已经受损。
- 建议：fixed 模式下加 token 硬上限校验，或配置校验时禁止 fixed + 大 chunk。

### 7.2 中优先级（影响调优空间与运维）

**T-04：`max_per_document=3` 硬编码**

- 位置：`retriever.py:135`。这是明确的调优旋钮，但未暴露为配置项。
- 建议：改为环境变量（如 `RETRIEVAL_MAX_PER_DOCUMENT`），并用 Dataset v3 扫描
  2/3/4 的 Hit/MRR 与回答质量后选择。

**T-05：LLM `temperature=0.3 / max_tokens=2000` 硬编码**

- 位置：`llm.py:83-84, 143-144, 176-177, 204-205` 及 `rewrite_followup` 的
  `temperature=0 / max_tokens=200`。
- 影响：长答案超过 2000 token 会被截断；不同场景无法区分温度策略。
- 建议：暴露 `LLM_TEMPERATURE / LLM_MAX_TOKENS` 配置。

**T-06：上下文没有显式字符/token 预算**

- 位置：`retriever.py:230-264`。最终上下文只由 chunk 大小、top_k、单文档限额
  间接控制；如果调大 `CHUNK_SIZE` 或 `RETRIEVAL_TOP_K`，Prompt 可能超过模型窗口。
- 建议：在 `format_retrieval_context` 增加总 token 预算与截断策略，并把预算纳入
  Trace 的 context stats。

**T-07：本地 `.env` 打开了安全默认关闭的开关**

- 现状：`RETRIEVAL_TRACE_ENABLED=true`、`CITATION_PREVIEW_ENABLED=true`、
  OCR 三层全部开启；代码和 `.env.example` 均默认 false。
- 影响：API 会返回未入选候选完整原文与整文档解析文本；OCR 会产生持续 API 费用；
  对可信单机调试可以接受，但若服务暴露到不可信网络则有泄露风险。
- 建议：区分“调试 profile”与“生产 profile”；部署前按安全基线关闭前两项。

**T-08：BM25 内存索引的缓存与一致性边界**

- 位置：`sparse_retriever.py:43-78`。
  - 每次配置/范围/Chroma revision 变化都调用 `get_all_chunks()` 全量快照并重新
    jieba 分词，且缓存只有**一个槽位**：多标签筛选频繁切换时会发生重复重建；
  - `_index_revision` 是进程内计数器，若服务运行中由**另一个进程**
    （如 `scripts/rebuild_index.py`）重建 Chroma，本进程不会感知，BM25 索引会陈旧。
- 影响：当前规模（约 2.5k chunks）无感；语料扩大或多标签高频切换后会有延迟尖峰。
- 建议：规模扩大后考虑多槽缓存/后台增量重建；明确“重建索引必须停服”的操作约束。

**T-09：Hybrid 的阈值语义不对称（当前 .env 为 hybrid 时实际生效）**

- 位置：`retriever.py:99-130` 与 P2-1 决策。Dense 路先经 0.67 过滤，BM25 路只有
  score>0 过滤；RRF 合并后的候选不再做任何距离/分数拒绝。
- 影响：拼写/术语类问题受益于词法路，但完全域外问题会因普通词命中进入 LLM，
  增加错误拒答难度与延迟。
- 建议：若保留 hybrid，应研究“稀疏门控 / 加权 RRF / Reranker 绝对分数拒绝阈值”
  （P2-1 结论中已列为后续方向），不要只靠 `RETRIEVAL_MODE` 切换。

**T-10：追问改写每次多轮请求都调用一次 LLM**

- 位置：`chat.py:126-138, 481-494`。
- 影响：每轮多一次 DeepSeek 调用（约 200 token 输出），失败静默回退原文；
  短问句/无指代时收益有限。
- 建议：可评估“仅在检测到指代词/省略时改写”或提供 `FOLLOWUP_REWRITE_ENABLED`
  开关；当前失败回退策略是正确的安全设计，保留。

### 7.3 低优先级（一致性、文案与清理）

**T-11：两代 parser/存储代码并存**

- `backend/services/parser.py`（`PARSER_VERSION="text-v1-pypdf2"`，仅 PDF/DOCX/TXT）、
  `page_store.py`、`source_page.py`、`citation_preview.py` 等仍是 legacy 链路；
  新链路已切到 `parsers/` + `unit_store` + `structured_citation_preview`。
- 影响：双轨增加维护成本；`eval/adapters.py:242` 还返回
  `"parser_mode": "structured-v1"`，`structured_citation_preview.py:72` 报错文案
  仍写“structured-v1 索引”，都是历史命名残留，容易误导排查。
- 建议：在确认无回滚需求后清理 legacy 模块，并统一文案。

**T-12：视觉缓存目录无淘汰策略**

- 位置：`vision_cache.py:61-76`。缓存只有写入逻辑，没有 TTL/容量上限；
  单文档调用预算限制了新增速度，但长期运行磁盘会持续增长。
- 建议：增加缓存总量上限或按访问时间淘汰。

**T-13：`MAX_FILE_SIZE`、`max_per_document` 之外的少量硬编码参数**

- `upload.py:58` 50MB 上传上限；`pdf.py:83` 渲染 scale=2 与 JPEG quality=85；
  `vision.py` max_tokens（识别 4000 / 描述 800）均为硬编码。
- 建议：根据实际语料决定是否配置化，改动前先在隔离环境验证。

**T-14：README 声明的“当前状态”与本地配置存在若干偏差**

- README 描述生产默认保持 Dense + Reranker、Trace/预览默认关闭；本地 `.env`
  实际为 hybrid + 全开（见 T-01/T-07）。
- 建议：统一“文档描述 = 模板 = 实际部署”三者，避免后续维护者按错误基线调优。
