## 1. 优化背景与问题来源

关系：优化[DEV-004 检索与模型推理](../开发/DEV-004-检索与模型推理.md)的词法召回路径，并补充[DEV-002 上传与索引生命周期](../开发/DEV-002-上传与索引生命周期.md)的派生索引一致性；需求来自[REQ-002 可解释检索与问答](../需求/REQ-002-可解释检索与问答.md)，验证由[TEST-002 检索质量与性能](../测试/TEST-002-检索质量与性能.md)承载，备份、重建和回滚由[OPS-002 数据备份恢复与索引重建](../运维/OPS-002-数据备份恢复与索引重建.md)约束。

当前[sparse_retriever.py](../../backend/services/sparse_retriever.py)在首次BM25查询或缓存键变化时从Chroma读取全部chunk正文，逐块执行NFKC、正则过滤和jieba分词，再在进程内构建`rank_bm25.BM25Okapi`。缓存只在当前进程有效，服务重启、`k1/b`变化或文档集合变化都可能再次付出全库读取、分词、Python对象分配和建模成本。

1000篇固定基线包含2914个chunk，GPU入库274.67秒；暖态BM25阶段均值20.839毫秒。该数字来自[TEST-002固定基线](../测试/TEST-002-检索质量与性能.md#baseline-v31)，不是8万篇规模的实测。完整CRUD-RAG语料预期超过8万篇，线性外推只能提示风险，不能当作实际容量、时延或内存结果。

## 3. 目标、范围与非目标

### 3.1 目标

1. 将中文分词、词频/文档频率和倒排结构从查询阶段移到受控建库阶段，形成可复用磁盘索引。
2. 查询阶段只分词问题并读取TopK，健康路径不得调用`vector_store.get_all_chunks()`或扫描全库。
3. 继续输出项目统一的`chunk_id/content/metadata/distance/bm25_score/bm25_rank`形态，使现有RRF、Reranker、单文档配额和Trace保持可接入。
4. 对固定完整测试语料支持一次建库、多轮选题复用，避免每个进程或每组参数重新构建BM25。
5. 以manifest绑定Chroma、SQLite、parser/chunker、中文分词器、BM25参数和有序chunk ID；错配时显式失败，不静默使用旧索引。
6. 在不改变BM25候选顺序和Hybrid质量的前提下降低冷启动耗时和内存峰值；若无法证明等价，则停止“纯性能替换”，另立算法变更实验。

### 3.2 首期范围

- 本轮只使用现有`crud-rag-1000-v1`的1000篇/2914块和`crud-rag-1000-120q-v2`的120题，不下载或扩展到1万篇/完整CRUD-RAG语料。
- 首期优先覆盖`allowed_document_ids is None`的固定1000篇全库评测路径。
- `allowed_document_ids == []`继续立即返回空结果。
- 非空标签/文档过滤集合首期保留现有子语料BM25实现，不能以“先全库TopN再过滤”冒充等价结果；后续是否采用分区索引或专业倒排服务另行决策。
- 首期使用独立测试路径和隔离索引，不修改生产默认检索模式，不写生产Chroma/SQLite/uploads。

### 3.3 非目标

- 不在本优化中迁移Milvus、Chroma Cloud、Elasticsearch/OpenSearch或其他远程服务。
- 不借持久化改动重新调`k1/b/BM25 TopK/RRF`，默认保持已测`k1=1.5、b=0.75`；参数质量优化与存储优化分开。
- 不处理拒答门控、Dense候选、Reranker或上下文预算问题；[OPT-003](./OPT-003-候选深度与拒答门控.md)的失败结论不因本方案改变。
- 不做1万篇扩展、完整CRUD-RAG下载、题库重建或人工gold审核；这些内容不属于本轮验收。

## 4. 方案比较与决策

| 方案 | 中文适配 | 持久化/内存 | 动态更新 | 当前适用性 | 决策 |
|---|---|---|---|---|---|
| 保留`rank_bm25`进程缓存 | 复用现有jieba | 不持久化；全库Python对象常驻 | 变更后重建 | 小语料可用，全量风险高 | 仅作兼容oracle和过滤回退 |
| Chroma本地原生Sparse/BM25 | 内置默认不适合中文，可自定义 | 理论上与Dense同库 | 由数据库维护 | 临时探针确认本地Sparse未启用 | 当前不采用 |
| Chroma Cloud Sparse/BM25 | 可自定义中文Sparse函数 | 服务端持久化并支持Hybrid | 支持 | 改变本地部署和数据边界 | 保留未来选项 |
| SQLite FTS5 | 默认中文分词不足，需预分词/扩展 | 持久化、运维简单 | 支持 | BM25参数与现有语义不完全一致 | 非首选 |
| BM25S磁盘稀疏索引 | 可直接消费现有jieba tokens | 可保存并`mmap`加载 | 静态索引更合适 | 符合固定全量测试库 | 首选候选，先做等价性门禁 |
| Tantivy/OpenSearch等倒排服务 | 可配置中文分析器 | 成熟持久索引 | 更适合频繁增删/过滤 | 引入新服务或绑定 | 标签过滤/生产动态场景备选 |

候选实现采用[BM25S](https://github.com/xhluca/bm25s)磁盘索引。P1证明原生评分不等价，后续只能采用“BM25S ATIRE TF + 显式`rank_bm25 epsilon=0.25`兼容IDF”的受控实现；该合同已写入P2 manifest，不能把原生BM25S描述成等价实现。`bm25s==0.3.11`已在P2依赖审计通过后固定到正式requirements。

## 5. 目标架构与查询数据流

```text
同一批structured-v2 chunks
  ├─ content → BGE embedding → Chroma Dense/HNSW
  └─ content → 现有NFKC/正则/jieba → BM25磁盘倒排索引
                    └─ ordinal ↔ stable chunk_id

问题
  ├─ BGE query embedding → Chroma Dense TopK
  └─ 同版中文分词 → mmap BM25 TopK → chunk_id批量取回正文/metadata
                                      ↓
                         现有RRF → Reranker → 配额 → final TopK
```

Dense和BM25仍是两条独立候选路；持久化只改变BM25候选的生成方式，不改变RRF的按排名融合原则。BM25S内部ordinal不得暴露给上层，跨存储连接键始终是稳定`chunk_id`。

P2/P3已按下列职责边界实现基础模块与固定全库业务接入：

| 候选模块/路径 | 职责 |
|---|---|
| `backend/services/sparse_index.py` | P2已实现统一词法索引协议、状态、命中和显式错误，不导入模型。 |
| `backend/services/sparse_tokenizer.py` | P2已抽出无Chroma副作用的现有NFKC/正则/jieba合同；`sparse_retriever`复用同一函数。 |
| `backend/services/bm25s_store.py` | P2已实现构建、保存、文件hash校验、mmap加载、TopK、dirty状态和原子活动指针。 |
| `backend/services/sparse_retriever.py` | P3已按部署配置选择backend；全库mmap、空范围短路、非空过滤子语料回退，并按active内容变化重载。 |
| `scripts/rebuild_sparse_index.py` | P2已实现显式源/目标/oracle/报告参数、源快照隔离、生产路径拒绝及源复核后发布。 |
| `eval/.../bm25_persistence_p3/verify_p3.py` | P3使用保存的同题Dense候选验证Sparse、RRF、Reranker输入和最终Top5。 |
| `eval/.../bm25_persistence_p4/run_p4_benchmark.py` | P4交替运行旧/新各3个独立进程，采集质量、阶段时间、CPU/内存/I/O/GPU、mmap、并发与句柄证据。 |

文件名和模块拆分是实施候选，不是已存在代码；开始开发后若发现职责更适合并入现有模块，须同步DEV文档，但不能削弱合同。

## 6. 索引与manifest合同

建议目录形态：

```text
<sparse-index-root>/
  active.json
  generations/
    <generation-id>/
      data.csc.index.npy
      indices.csc.index.npy
      indptr.csc.index.npy
      vocab.index.json
      params.index.json
      chunk_ids.jsonl
      manifest.json
```

`generation-id`由合同内容hash或UUID生成；先写同一父目录下的临时generation，文件flush、重新加载和完整校验通过后再用原子替换发布`active.json`。不得在查询请求中隐式构建，也不得直接覆盖活动generation。

`manifest.json`至少包含：

- schema/index格式版本和创建工具版本；
- corpus ID、文档数、chunk数及有序`chunk_id`列表SHA-256；
- 每个chunk正文规范化hash或全量摘要；
- parser版本、chunk strategy/size/overlap/max tokens；
- tokenizer名称、jieba版本、NFKC/正则规则版本、停用词版本；
- BM25实现、版本、公式/IDF变体、`k1/b/epsilon`；
- 关联Chroma collection、embedding计数和metadata逻辑摘要；
- 构建开始/结束、wall time、索引字节数、构建环境；
- 兼容oracle结果和发布状态。

索引载入必须先验证格式、必需文件、chunk数、有序ID hash、分词合同和参数。测试评测还必须验证数据集/语料manifest；任何一项不一致即中止。正文不重复存入BM25S corpus文件，查询命中后按chunk ID从Chroma批量取回，避免两份正文成为不同事实源。

## 7. 中文分词、评分与确定性

1. 文档与查询复用当前`tokenize()`：NFKC、转小写、正则保留中英文数字符号集合、jieba精确模式、移除纯标点。
2. 分词器和词典会影响索引，jieba版本、用户词典hash和停用词hash必须进入manifest；不允许查询端临时换词典。
3. 首期以当前`rank_bm25.BM25Okapi`为兼容oracle。BM25S公式/IDF变体必须通过TopK逐题对照后才能入选。
4. RRF只消费排名，但Trace仍会展示BM25分数；若分数量纲不同必须更新Trace字段说明和兼容版本，不能沿用旧分数含义。
5. 同分结果必须以`chunk_id`升序作为稳定次序；库默认顺序不能作为确定性保证。
6. 不在持久化优化中重新选择`k1/b`。参数变化需要独立generation，不能共用旧索引或查询时动态假装改变已预计算统计。

## 8. 文档过滤、动态增删与失败行为

### 8.1 范围语义

| `allowed_document_ids` | 首期行为 |
|---|---|
| `None` | 使用健康且合同匹配的全库持久化BM25索引。 |
| `[]` | 直接返回空结果，不查询任何索引。 |
| 非空集合 | 继续使用当前按过滤子语料建模的兼容路径；Trace标注backend，后续单独优化。 |

不能先取全库TopK再过滤，因为相关文档可能在截断前被未授权文档挤出，而且当前实现的IDF是在过滤后子语料上计算。Oversampling只能作为显式实验，不能作为等价替换。

### 8.2 增删与脏索引

BM25的IDF和平均文档长度依赖整个语料。单文档增删后，旧索引即与Chroma不再严格一致。首期固定评测库采用停写后全量构建；业务库若发生增删，必须把Sparse状态标成`dirty`，不得继续声称Hybrid使用最新BM25。

实施时需要在下列策略中由测试证据选一项，默认安全策略是不静默降级：

1. BM25/Hybrid请求返回明确的索引不可用错误，Dense显式请求仍可工作；或
2. 配置允许时显式降级Dense，并在响应Trace、日志和状态接口记录`fallback_reason`；评测模式禁止降级并中止。

不得在用户查询线程同步全量重建，也不得在索引损坏时自动退回可能OOM的全库`rank_bm25`路径。

### 8.3 状态与Trace候选字段

- `sparse_backend`: `rank_bm25_memory`或`bm25s_mmap`；
- `sparse_index_generation`与`manifest_hash`；
- `sparse_index_status`: `ready/dirty/missing/corrupt/mismatch`；
- `sparse_fallback_reason`；
- `sparse_index_load_ms`和现有`sparse_retrieval`查询耗时分开；
- 请求使用的tokenizer/BM25合同版本。

字段需在实现阶段同步强类型schema、API兼容和旧Trace读取测试；本轮不修改任何schema。

## 9. 分阶段实施计划与停止点

### P0：用户确认与冻结合同

### P6：生产接入实施协议（A/B已完成，C未执行）

P6按下列三个停止点实施；任一硬门禁失败即停在当前点，不自动继续或改口径。

#### P6-A：生命周期补强与隔离回归，不访问生产写路径

1. **持久失效优先于数据变更。** 当前`vector_store`只有进程内revision，服务重启后不足以证明旧索引失效。上传、删除和重建在修改Chroma前必须先把活动Sparse指针持久标为`dirty`；标脏失败则拒绝数据变更。异常退出或服务重启后仍须识别dirty，不能靠内存计数恢复为ready。
2. **重建协调。** 文档事务完成后触发单实例、可合并的后台全量重建；连续增删合并为新一代。构建绑定开始时源revision/摘要，发布前再次核对；源在构建中变化则丢弃候选代并重新排队，不发布过时索引。
3. **脏期间行为。** 全库BM25/Hybrid明确返回Sparse不可用状态；Dense仅在管理员显式切换检索模式后可用。禁止查询线程同步全量重建、继续使用旧generation或静默退回`rank_bm25_memory`。非空标签过滤只有在现有精确子语料路径验证无回归后才保留可用。
4. **生产构建入口。** 保留现有CLI默认拒绝生产路径的保护，仅增加需要显式生产参数、精确路径匹配和确认值的受控入口；继续执行源快照、只读SQLite、构建后mmap重载、120题查询oracle、源前后摘要及无覆盖发布检查。
5. **隔离测试。** 覆盖上传/删除前标脏、标脏失败不写、事务失败、重启后dirty、重复事件合并、构建期再变更、并发查询/切换、Windows句柄释放、缺失/损坏/合同错配、标签过滤、显式Dense降级和旧backend回滚；随后运行全量Python及前端回归。

P6-A结束时只交付代码、测试和报告；不生成生产generation，不改默认值。先报告结果并停下。

#### P6-A接手检查与补完（2026-09-08）

接手时已有持久标脏、线程协调器、HTTP/流式错误、状态字段和受控CLI主体，但专项测试未通过：测试种子索引目录与配置不一致、缺少corpus ID、关闭worker后仍等待完成、模拟revision持续变化、旧测试替身指向已删除函数等问题均已复现。不能用文件数量估算为“基本验收完成”。

本轮补齐以下行为：

- 文档提交及失败补偿、Sparse评分与正文回取、源快照和最终发布共用单服务进程内的事务锁；耗时全量构建在锁外执行。最终源revision、正文和metadata摘要、有效参数复核与发布不可被写入插入，复用旧代也遵循同一门禁。
- Chroma写前持久dirty；标记失败拒写。写入抛错也使内存缓存失效；后台源读取同时校验SQLite只读`quick_check`及ready文档ID/逐文档块数，失败补偿不完整时保持dirty并退避重试。
- 重建使用设置管理器当前有效的k1/b；参数保存前失效索引，构建中改变参数则丢弃候选代。清理mmap缓存不再清除已经验证的语料revision绑定。
- 构建及mmap重载使用固定120题，对旧`rank_bm25`执行K=1/5/15/50有序和分数校验。启动恢复核对完整正文/metadata摘要；停机后不发布进行中的候选，旧代句柄可释放。
- 无活动指针时返回`needs_initial_generation`，上传事件不能引导首次生产发布。删除最后一篇后记录`empty`、保持dirty并停止无意义重试，下次上传再重建；此期间全库BM25/Hybrid仍明确不可用。
- CLI保留默认拒绝生产路径，校验环境变量优先后的源/目标精确匹配和确认值；生产语料ID使用`production-`前缀，要求120道有效问题。SQLite WAL纳入前后摘要，登记ID和逐文档块数必须匹配，影子构建默认不发布，报告拒绝覆盖或写入源存储/索引关键位置。独立Dense重建的Sparse路径隔离到新目标，避免标脏生产指针。

验证和接手问题清单见[本阶段验收报告](../../eval/crud_rag_1000/v3_1/bm25_persistence_p6a/README.md)，实现见[DEV-002](../开发/DEV-002-上传与索引生命周期.md#sparse-lifecycle)，验收见[TEST-002](../测试/TEST-002-检索质量与性能.md#persistent-bm25-p6a)。本阶段验证单服务进程、多线程和真实隔离存储；不支持把多个服务进程或外部写库脚本当作共享事务参与者，生产CLI仍须停写。没有重跑P4的1000篇完整GPU性能对照，因此不把回归测试时间解释为新的性能收益。P6-B/C尚未执行，代码默认和示例默认仍为`rank_bm25_memory`。

3. 从生产一致快照构建新的影子generation，验证文件hash、manifest、chunk ID/正文/metadata摘要、mmap加载、120道固定查询对旧`rank_bm25`的K=1/5/15/50排序，以及构建前后生产源未变化。

#### P6-B实际结果（2026-09-08）

用户授权继续B阶段后，在无其他Python服务的停写窗口核对真实生产库：31篇ready文档、2620块、5条failed记录、11个标签；SQLite quick_check/schema 4、逐文档Chroma计数及31份原文均通过。与P4的1000篇/2914块是不同语料，不能混用规模或质量指标。

已创建93,705,597字节成套本地备份，并构建独立`production-rag-20260908`语料下的`production-shadow-20260908-r1`。整代1,593,104字节，构建6.085秒、总流程8.228秒；120题K=1/5/15/50全部120/120有序一致，mmap重载最大分数差0。生产active没有创建。

恢复副本先核对整套资产摘要，再运行两个mmap新进程和一个旧backend回滚新进程：每个480项有序结果对照、11个标签范围、24项四线程并发及句柄释放通过，候选代切换和切回也通过。服务启动/关闭通过真实ASGI生命周期验证，不是生产端口、浏览器或GPU完整问答验收。最终生产源及原始备份摘要均未变化，默认仍为旧backend，P6-C未执行。辅助工具/CLI专项20项通过，详见[P6-B报告](../../eval/crud_rag_1000/v3_1/bm25_persistence_p6b/README.md)及[结果](../../eval/crud_rag_1000/v3_1/bm25_persistence_p6b/result-20260908-r1.json)。

#### P6-C：原子启用、观察与回滚

1. 在停写窗口先发布已验证的活动指针，再把部署默认`SPARSE_BACKEND`、示例配置和生产配置改为`bm25s_mmap`，同时写入匹配的`SPARSE_INDEX_ROOT`与`SPARSE_INDEX_CORPUS_ID`。`RETRIEVAL_MODE=hybrid`及其他检索参数不改。
2. 启动后检查运行状态必须为`ready`且generation/manifest hash正确；执行固定冒烟查询、一次完整120题回归、标签过滤、并发读、第二次服务重启及句柄释放检查。Trace必须能证明全库路径未扫描Chroma或构建`BM25Okapi`。
3. 观察窗口记录错误率、Sparse/总检索P50/P95、CPU、RSS/Private Bytes、磁盘、GPU及重建状态；不把生产查询内容写入新增明文报告。
4. 触发任一条件立即回滚：排序/质量门禁失败、状态非ready无法恢复、服务重启后错代、数据变更未持久标脏、全库请求静默降级、暖态Sparse P95超过同期旧backend的110%，或出现新增5xx/资源不可接受回归。
5. 回滚只需把`SPARSE_BACKEND`显式恢复为`rank_bm25_memory`并重启验证；保留生产数据、失败generation和报告用于诊断，不删除旧generation。若数据也做过恢复，则Chroma、SQLite、原文/OCR和Sparse必须使用同一套快照。

若上线后动态写入频率使全量重建窗口不可接受，或任意标签过滤成为主要流量，再以同一质量与资源口径比较Tantivy/OpenSearch/Chroma Cloud/Milvus Sparse；这属于后续架构决策，不阻塞当前1000篇规模的条件采用，也不预设Milvus必然更好。

## 12. 风险、回滚与结论

- 最大正确性风险是BM25公式、IDF和tie-break变化导致RRF候选变化；P1采用严格有序TopK门禁。
- 最大一致性风险是Chroma已变而BM25 generation未变；manifest、dirty状态和评测fail-closed共同约束。
- 最大功能边界是任意标签过滤；首期保留现有精确子语料路径，不做不等价近似。
- mmap降低常驻内存不等于零内存；Windows文件句柄可能阻止替换，必须用新generation和活动指针切换。
- 1000篇结果不能证明更大语料容量；本轮取消1万篇与完整语料试验，报告不得作线性外推结论。
- 回滚是恢复旧`rank_bm25`代码路径及匹配的数据合同；若已切换索引，保留上一generation，不删除原索引。

结论：P4已证明1000篇/120题的历史同期性能收益。2026-09-08完成P6-A代码验收及P6-B真实31篇/2620块生产影子构建、成套恢复和回滚验证；源和备份摘要不变。当前停在P6-C之前，生产active尚不存在，默认仍为旧backend，正式启用与观察窗口未执行。
