## 3. 核心流程

请求开始获取一次运行时snapshot → 建立/恢复持久化请求 → 读取有界历史 → 必要时改写独立问题 → 解析标签ID范围 → 检索 → 空结果短路或生成 → 提取引用 → 完成消息与保存可选Trace。2026-09-09后，流式模型生成使用`AsyncOpenAI`和`async for`；检索、历史/标签数据库访问、引用提取及消息/Trace持久化通过`asyncio.to_thread`移出ASGI事件循环。同步`POST /api/chat`中的检索、模型调用和持久化也采用相同下放边界。

同步与异步LLM客户端分别使用最多4项的缓存，但共享revision、provider、base URL、timeout和Key摘要派生规则，缓存键不含明文Key。普通与带历史的异步流入口复用现有消息合同，上游流在正常结束或中断时显式关闭。

重复已完成request ID重放首次答案/引用/Trace；409明确标识末尾变化、进行中或过期重试。LLM关闭时不做改写/回答调用；`rewrite_enabled=false`时，有历史的追问也直接使用原问题检索并在Trace记为`disabled`。无检索结果返回固定提示；选择了标签时提示范围内没有相关文档。

[llm.py](../../backend/services/llm.py)按用途组装生成参数：回答与改写分别读取同一请求snapshot中的思考模式、强度、Temperature和Token上限，改写使用独立超时。DeepSeek显式思考开关映射为`extra_body.thinking`；OpenAI-compatible显式开关/强度映射为`reasoning_effort`。Temperature始终按配置提交，不因思考模式在代码中删除；上游是否生效由服务能力决定。当前流式循环分别处理`delta.content`和`reasoning_content`，两种内容不混合。

## 4. 失败、停止与并发

2026-09-19更新：思考通过独立reasoning_delta发送，成功后持久化，既不作为答案引用依据也不带入下一轮历史。SYSTEM_PROMPT增加部分回答、资料缺口、不得由本轮缺证据推断全库不存在等约束；带历史的入口禁止沿用历史编号。chat两个入口均用build_retrieval_sources构建全来源，仍在正文结束后发送。不增加硬拒答门控、额外判别调用或旧证据缓存。

多轮方案1沿用已有流程，不重复建设：每个新请求调用检索；有历史且开启LLM/改写时先改写，关闭或失败使用原问题。新增同步/流式×改写成功/失败四组回归，验证第二轮出现新文档时source1映射当前文档、旧消息来源保持不变。记录见[TEST-003](../测试/TEST-003-会话引用与流式协议.md#current-policy)。

流内retrieval_error或llm_error返回error事件；未完成的断开请求标interrupted，不保存半截助手答案。客户端Abort并不保证服务器尚未完成；重同步才是恢复事实的手段。应用启动会处理遗留pending请求。

## 5. 实际结果与测试

主链路、S6快照、BUG-004异步化、`chat-v2`、查询改写方案A及用途级通用生成设置代码均已存在。真实本地HTTP用例证明人工延迟delta在响应完成前逐行到达，检索工作线程等待期间健康检查仍可响应；2026-09-12全量后端833项通过/3项跳过，前端42项、lint和生产构建通过。验证见[TEST-003](../测试/TEST-003-会话引用与流式协议.md#cases)，配置/Trace见[TEST-005 设置与Trace回归](../测试/TEST-005-设置与Trace回归.md)。历史409与即时用户消息问题对应[反馈17/22](../测试/TEST-007-缺陷与历史反馈追踪.md#feedback)，UI实现由[DEV-008 React主前端](../开发/DEV-008-React主前端.md)承接。

## 6. 已知限制

当前多轮历史是有界文本，不是无限上下文记忆。没有账号权限隔离。流式路径部分耗时字段由当前实现填写为0，不能把0解释为实测没有花费；Trace计时解释见[DEV-010限制](../开发/DEV-010-检索Trace与配置追溯.md#limitations)。

同步阻塞和本地集中到达已由[BUG-004](../测试/BUG-004-流式响应缓冲至完成时一次性输出.md#regression)修复；`chat-v2`已补齐流式生成、改写、引用、会话提交和服务端delta里程碑。方案A默认值仍使DeepSeek改写关闭思考并收紧提示词，但2026-09-12后回答和改写均可在设置页独立调整，OpenAI-compatible端点使用通用effort映射。兼容端点可能不支持某些参数；同步服务仍会占用默认线程池，线程池容量、生产并发、长期改写质量和浏览器实际首字尚无完整压测结论。

## 会话编辑、重新生成与范围快照（2026-10-26）

[conversation_store.py](../../backend/services/conversation_store.py)的begin_chat接收tags和replace_message_id；普通发送将范围保存到用户消息，覆盖发送将参数暂存至chat_replacements。complete_history新增before_sequence，两条HTTP路径中的问题改写和最终回答均受同一边界约束。complete_chat调用_commit_replacement，在同一SQLite事务中验证原记录并替换，后续任何提交错误均回滚删除和编辑。每次新生成使用新请求号，网络重复提交仍重放结果。

[metadata_schema.py](../../backend/services/metadata_schema.py)升级为6，v5→v6仅添加可空范围列和覆盖暂存表，旧记录内容/身份保留，旧范围为null。来源为空或LLM关闭沿用原有正常完成语义；模型失败/正文为空/取消时不覆盖原历史。已成功替换后不保留分支，也不提供撤销历史。引用与Trace重新生成，旧思考不会进入新上下文。

便携版仅对白名单v5→v6做保留性迁移：运行锁和模型必须一致，先将SQLite一致性备份至data/migration-backups，再事务迁移和更新工作空间合同；数据库已升6但标识仍为5时可续完标识更新，不重复迁移。该能力不等于通用更新器，不接管无标识源码数据或其他不兼容版本。设计见[DES-004](../设计/DES-004-会话流式协议与来源预览.md#message-regeneration)，验证见[TEST-003](../测试/TEST-003-会话引用与流式协议.md#message-regeneration)。
