## 1. 目标、首版范围与交付承诺

目标体验：下载完整便携ZIP → 解压到可写目录 → 双击启动，优先GPU → 在现有React设置页填写API Key → 上传和使用。GPU不可用时说明原因并确认CPU备用；两种设备模式都保留混合检索和重排，不通过关闭Reranker或改为Dense来制造“等价可用”。未配置Key也能进入设置、管理文档和使用本地检索。

首版为Windows x64，Windows 11 x64为首个干净环境基线。标准包内置独立运行时、CUDA版PyTorch依赖、预构建React、Embedding与Reranker两份模型；用户无需Python、Node.js、Git、Docker或PyCharm，首次不安装依赖/下载必需模型。普通本地可写目录、中文/空格路径、停服后整目录移动属于验收范围。其他Windows版本、NVIDIA型号/驱动组合须实际验证再声明支持；包体积、显存/内存、磁盘与时延待实测。

本修订保留同一便携交付主题，替代09-21的CPU默认、Dense/内存BM25、重排可选和app层目录设计，也替代初稿在线初始化/AppData工作根。首版包含启停、CPU显式入口、目录/日志查看、分类缓存清理和移除前准备；备份、恢复、升级先采用停服人工复制的操作说明及必要兼容检查。GPU/模型在线组件管理、自动升级/迁移/恢复、个人数据一键重置后置，不作为首版完成条件。正式安装器、系统登记、托盘、账号、远程共享、自动更新平台、本地生成大模型、云同步及其他系统不在范围内。

“同本地配置”指模型/revision、依赖、检索流程和参数合同一致，不承诺不同硬件的耗时/排序细节或远程回答逐字一致。“本地”指存储/解析/检索；问答会发送问题、召回片段和有界历史，改写可能发送问题/历史，OCR发送图片。生成/OCR初始关闭，用户自行配置Key并启用，测试外部API仍需相应授权；基础初始化不调用远程模型、不安装驱动。

## 3. 最小发布结构与运行时装配

### 3.1 沿用源码相对布局

拟交付RAG-<版本>-windows-x64-portable.zip、SHA-256和简明说明。以下为拟定目录，不代表文件已经创建；data/logs/cache/temp/state首次运行创建：

```text
RAG-<版本>/
  启动.cmd                 GPU优先，校验并打开React
  CPU启动.cmd              显式CPU，保留Hybrid与Reranker
  停止.cmd                 停止当前目录实例
  维护.cmd                 目录/日志查看、缓存清理、移除前准备
  使用说明.md
  release-manifest.json    版本、提交、依赖锁、模型revision/摘要、兼容范围
  backend/                 现有后端
  web/dist/                已构建React
  runtime/                 专用Python与GPU/CPU共用的依赖（须验证）
  models/embedding/        bge-large-zh-v1.5完整必需资产
  models/reranker/         bge-reranker-v2-m3完整必需资产
  launcher/portable.py     启停及基础维护
  locks/                   依赖及模型固定清单
  licenses/                运行环境、依赖及两份模型许可
  data/                    个人数据与稳定工作空间/首次索引状态
  logs/                    服务与维护日志
  cache/                   可重建缓存
  temp/                    应用临时文件
  state/                   当前运行锁、PID、停止请求
```

保留backend/与web/dist/同根关系，复用BASE_DIR与静态托管逻辑。按白名单装配，排除.env、现有data/logs/Key、.git、.venv/.venv-gpu、node_modules、测试临时目录、旧Streamlit和私人评测材料；不以.gitignore代替发布白名单。需要的第三方运行资源不得因裁剪误删。

摘要检查下载完整性，不等于来源真实性。包从维护者确认渠道分发；私有仓库不自动公开，不在本期新增发布平台。

### 3.2 一套运行时、两种设备模式

W1优先验证官方Windows嵌入式Python，发布端用固定构建环境装配第三方依赖，配置应用搜索路径并携带所需DLL/包资源；用户端直接运行runtime内解释器，不执行pip/uv在线安装、不注册系统Python。见[Python嵌入式分发](https://docs.python.org/3.14/using/windows.html#the-embeddable-package)。不能直接复制普通开发venv当便携运行时，见[venv移动限制](https://docs.python.org/3.14/library/venv.html#how-venvs-work)。

优先沿用当前Python/torch/业务依赖版本，不同时升级框架或大规模裁剪依赖。固定GPU运行依赖及来源，完整记录传递依赖；先排除明确仅用于旧前端/测试的内容。CUDA构建可以指定CPU执行，但本机简单张量验证不覆盖无NVIDIA/无驱动条件下的依赖导入与完整模型推理，后者必须实测。

首选只携带一套CUDA运行时与两份共用模型，避免两套环境和组件下载器。若无GPU环境导入/推理不兼容，在W1调整装配方案；必要时提供包内固定的独立CPU运行环境并记录体积成本，CPU备用不能靠用户安装依赖或首次联网补齐。

NVIDIA硬件/驱动必须符合所固定构建的支持范围，见[CUDA兼容说明](https://docs.nvidia.com/deploy/cuda-compatibility/latest/minor-version-compatibility.html)。便携包不包含显卡驱动、不修改系统CUDA；驱动或显卡不兼容时说明并提供CPU。两份模型固定revision、必需文件与hash、许可，不把整份个人HF缓存打包；运行时local_files_only，缺文件明确失败而不是回全局缓存。

### 3.3 路径和配置

解压目录就是默认应用/工作根，backend、web、runtime、models、data及其余子目录均在此根内；不默认写AppData。不可写时提示换目录，不提权、不偷偷更换存储位置。启动器从自身位置解析根，不依赖终端cwd，在导入模型/存储库前设置目录内HF/PyTorch缓存、TEMP/TMP和数据路径。

W2已用RAG_DISTRIBUTION_MODE=portable|source区分模式，默认source；保留BASE_DIR相对布局，不增加任意工作根参数。便携模式跳过源码.env与继承的部署路径/Key/模型/检索等环境设置，以安全新用户默认启动；页面非设备设置覆盖仍复用。RAG_PORTABLE_DEVICE固定为cuda:0（默认）或显式cpu；W3已补GPU检查、确认CPU与有限降batch入口，不默默降级。源码模式继续使用原.env与现有入口。

稳定工作空间标识、首次Sparse发布是否已完成保存在data，随备份保留；PID/锁/停止请求在state，移动后重新识别，不作为可恢复个人数据。持久化路径尽量相对根展开。备份目标在源树外的新位置，不把自己的备份嵌入待复制目录。

<a id="system-impact"></a>
### 3.4 系统影响

应用不主动写安装注册表、全局PATH/环境变量、文件关联、服务/任务/自启、桌面快捷方式、防火墙或安全软件设置。入口只使用进程级环境；不要求永久放宽脚本策略。关闭可关闭的非必要遥测/更新探测。

模型/临时缓存设置在库导入前生效，见[HF缓存配置](https://huggingface.co/docs/huggingface_hub/en/package_reference/environment_variables)、[Python临时目录](https://docs.python.org/3/library/tempfile.html)。W5跟踪程序与子进程的文件/注册表写入，覆盖GPU和CPU启动、上传/检索、停止和清理；目录外应用写入逐项处理，不能仅设置变量就宣布完成。Windows/浏览器的独立缓存、访问或安全记录单列，不自动清理，也不承诺绝对零痕迹。

## 4. 初始化、设备选择与首次索引

### 4.1 启动顺序

1. 定位根目录，检查Windows架构、可写性、资源、端口与现有实例；获取单工作空间锁。
2. 校验随包解释器、依赖、React和两份模型。首次按清单校验完整性，日常做轻量版本/文件检查；不安装、不编译、不下载，损坏提示完整重解压。
3. 默认GPU优先：检查CUDA可用并实际加载两份模型、最小编码/重排、实际设备。显存不足可有限降低批量重试一次，不减少候选/top_k、不更换模型；模型缺失/配置错误不能伪装成GPU问题。
4. GPU不支持/驱动不兼容/仍不足时，显示原因并确认CPU；CPU启动.cmd直接选择CPU。CPU保持Hybrid及Reranker，关闭重排FP16，提示可能较慢。不在模型内部静默切设备；切换须停止并重启，只记录已确认的选择。
5. 新工作空间生成无Key配置、工作空间标识、空库和首次索引状态；已有data先做兼容检查，不能在检查前导入业务触发schema迁移/Chroma写入。
6. 后端预热成功、实例身份与React资源匹配后打开设置页。空库无首代索引属于待上传状态，不阻止设置/文档管理；非空语料索引构建中或失败不得标为Hybrid ready。

### 4.2 默认参数与GPU/CPU差别

| 参数 | GPU首选 | CPU备用 |
|---|---|---|
| Embedding | bge-large-zh-v1.5，cuda:0，沿用当前加载方式 | 同模型/revision，cpu |
| Reranker | bge-reranker-v2-m3，开启，cuda:0，FP16 | 同模型/revision，保持开启，cpu，FP16=false |
| 检索/稀疏后端 | Hybrid / bm25s_mmap | Hybrid / bm25s_mmap |
| 切分 | recursive，400/80，max_tokens=480 | 相同 |
| 重排候选/最终数量 | 15 / 5 | 相同 |
| Batch基线 | Embedding 32、Reranker 8 | 先沿用，按资源实测调整；不改变候选合同 |
| 生成/OCR | 初始关闭，Key为空；视觉连接跟随问答 | 相同 |
| 预览/Trace/预热 | 本地引用预览开启，Trace关闭，预热两份本地模型 | 相同 |

BM25参数、距离阈值0.67、RRF与文档配额按当前有效非敏感配置登记，保存到发布清单；不复制个人数据库或production语料标识。CPU/GPU精度变化可能影响分数/边界排序，依赖与模型一致不保证结果逐字/逐项相同。验证分阶段时延及同数据质量，不只看总耗时或生成文本。

<a id="sparse-bootstrap"></a>
### 4.3 新便携库首份持久化Sparse索引（W2已实现）

复用现有单进程文档事务锁、后台快照、源revision与正文/metadata摘要、mmap重载及原子发布。仅显式便携模式、当前根内新建且首发未完成的工作空间可在首次非空ready语料后构建首代，不放宽已有生产受控首代入口；首发中断可恢复，已发布库的指针缺失按故障处理，不能伪装成新安装。

空库维持待上传，不构造虚假空索引；上传完成后后台生成，连续上传合并。候选先构建/校验，发布前重新核对SQLite ready文档/逐文档chunk数、有效参数、源revision/内容摘要；源变化废弃并重排，失败保持不可用并报告。查询线程不全量重建、不回退Dense/内存BM25、不读取旧或未验收generation。首代完成后沿用已有dirty与后台重建协议；工作空间corpus ID本地生成并稳定保存。

现有后台oracle从eval读取固定120题，与发布排除私人材料冲突。便携模式从当前构建快照确定性抽取有界词组及无匹配校验查询，记录生成规则版本/样本摘要，以现有rank_bm25 oracle核对候选构建及mmap重载；不调用API、不提交用户词组/正文，也不省略oracle。源码/既有生产仍使用原120题合同。便携校验用于实现一致性，不冒充人工检索质量评测。具体代码映射见[DEV-012](../开发/DEV-012-服务托管与启动停止.md#windows-release)、[DEV-002首代边界](../开发/DEV-002-上传与索引生命周期.md#portable-bootstrap)，检索设计见[DES-003](../设计/DES-003-检索融合与上下文选择.md#portable-bootstrap)。

## 5. 日常启停与本机边界

使用预构建React与随包解释器，无reload、多worker、Streamlit或常驻系统服务；默认127.0.0.1:8000。重复启动同目录实例只打开页面，以锁、PID、开始时间、可执行路径和健康实例ID核对；其他程序/目录占端口时说明，不凭HTTP 200认领或杀进程。修正当前单向时间比较风险，启动失败只回收本次身份匹配进程。

停止优先正常退出并等待上传/后台任务与文件句柄释放。启动器可用当前目录、实例绑定的停止请求文件通知程序化Uvicorn退出，不增加无保护HTTP停止接口；超时提示并核对后强制结束。关闭浏览器不停止后台服务，入口成功/失败和实际设备可见，后台隐藏窗口。

便携模式限制Host/Origin和跨站写请求，同源React访问；不能只去掉CORS头当作阻止写入。源码Vite范围按原开发配置处理，不增加账号或远程共享。根页面、API可响应、模型ready与Sparse ready分别核对。

<a id="maintenance"></a>
## 6. 首版维护与后置能力

### 6.1 升级：人工复制，先检查兼容

首版说明流程：新版完整解压到新目录 → 停止旧版并确认退出 → 将旧目录完整备份至外部新目标 → 人工复制整套data到未启动的新包 → 启动器先检查支持的数据/依赖/模型合同 → 成功后业务冒烟。原目录不改，禁止直接将ZIP覆盖解压到旧目录。两份模型已随新版，不重复下载；不自动OCR、重设设置或重新索取仍可解密的Key。

首版只承诺已验证的兼容版本复制，不能把不兼容数据交给业务自动猜测迁移。版本/合同不支持时拒绝打开；自动升级、跨版本迁移与恢复向导后置。数据库被迁移/新写入后，只切旧程序不能视为回滚，需匹配的旧程序和升级前完整副本，说明备份后内容会丢失。

### 6.2 备份与恢复：停服人工复制

优先停服后复制完整目录，包含程序/依赖/模型/data；目标在源树外、不覆盖既有备份、保持停止直到复制结束并核对成功。仅data备份必须完整包含配置、metadata及必要WAL、Chroma、原文、OCR图像/视觉缓存、Sparse generation/指针/合同、工作空间标识及DPAPI密文；不得只复制metadata.db。

完整副本恢复到新目录，启动器重新识别state并做版本/资产检查。只恢复data时用匹配包和新的空data目标；先核对复制完整性，不覆盖活动库。原目录保留，不把中断复制当作可恢复备份；不提供首版归档自动解压/备份摘要工具。更完整自动备份/恢复与中断状态机后置，现有原则见[OPS-002](./OPS-002-数据备份恢复与索引重建.md)。备份含文档明文，DPAPI不代表整份备份加密。
