## 2. 任务开始与完成流程

开始任务先读[总导航](../README.md)，再读相关分类README和上下游；搜索已有ID/主题，判断是需求变化、设计变化、实现修正、测试发现还是优化。先读后改，不为小修复创建重复文档。

完成时：更新实际实现与测试结果 → 更新设计/需求中改变的契约 → 补双向关系与章节链接 → 更新分类导航/主要链路 → 执行检查 → 明确通过、未运行与环境阻塞。阶段边界不自动进入下一阶段。

## 3. ID、状态与历史

文件名为ID-中文主题.md；ID一旦分配不再改变，重命名文件保留ID并改所有引用。BUG放测试分类。新增前搜索全目录；不要使用v2/new/final后缀制造平行同功能文档。

状态限定规划中、设计中、开发中、测试中、已完成、已废弃、已替代。日期是文档生命周期日期；整理旧方案不冒充原始创建日期。重大方案替代时新建ID，旧文档标已替代并链接新文档，保留决策理由和反向关系。

“已完成”必须说明范围：代码存在/历史验收完成不等于本轮运行完成；测试长期未复验要保留证据日期。缺上游时明确缺口，不能虚构已批准需求或已执行回归。

| 类型 | 必须说明 |
|---|---|
| REQ | 背景、用户场景、功能/非功能、输入输出、边界、不做什么、验收 |

## 5. 缺陷与优化闭环

小Bug可记录原DEV；跨模块或改变设计时独立建修复DEV，先补DES变更。测试发现→BUG→修复DEV→TEST回归必须可追踪；回归要写执行日期、位置与结果，不只写已修复。

优化记录前后同条件指标；未实施写“暂无”，不填假结果。新旧题库、硬件精度、模型、评分器不同时注明不可比因素。

## 6. 检查与维护门禁

```powershell
.\.venv\Scripts\python.exe new_docs\工具\check_docs.py
```

移动/删除/改名后检查链接和锚点、唯一ID、导航、上下游反向关系、孤立节点、代码引用。人工再核对符号、参数、API、配置默认和运行说明，静态检查不能验证这些语义。

每次较大任务检查：

- [ ] 文档反映实际实现，创建/更新日期和状态正确。
- [ ] REQ→DES→DEV→TEST/OPT/OPS关系完整且重要关联双向。
- [ ] 分类与总导航同步，无重复ID/文件、坏链接或孤立节点。
- [ ] Bug记录修复位置和回归；优化记录前后结果或未执行原因。
- [ ] 历史证据保留原日期；未运行/阻塞单列，未泄露密钥。
