<a id="contract"></a>
## 2. 会话与幂等契约

ChatRequest携带question、可选conversation_id、request_id、expected_last_message_id、retry_failed与tags，字段以[schemas.py](../../backend/models/schemas.py)为准。

持久化请求先校验会话末尾和request身份；相同已完成请求重放原结果，冲突使用409，失败请求受重试规则约束。历史有条数、token和字符上限；追问先改写为独立问题用于检索，最终生成仍保留原问题和有界历史。LLM关闭时改写与生成均不得调用模型。

<a id="stream"></a>
## 3. 流式协议

POST /api/chat/stream使用NDJSON，不是SSE。每一行是JSON事件：

| 事件 | 内容与状态意义 |
|---|---|
| meta | 会话、请求、消息身份及standalone_question |
| reasoning_delta | 上游思考文本增量，与正式正文分离 |
| delta | 逐块文本；不能当最终持久化结果 |
| citations | 有效最终检索来源全集及正文引用状态；仍在完整答案之后发送 |
| done | 已完成，含助手消息ID和可选Trace |
| error | 失败码与可展示信息，不补造成功 |

事件顺序为meta→(reasoning_delta或delta)*→citations→done，运行期失败走error。只有思考没有正文按失败处理；思考不参与引用提取或下一轮历史。成功思考保存到schema v5；正文首块到达默认折叠，手动可展开。断开时未完成请求按interrupted处理，不保存半截助手答案；已完成事务不因浏览器Abort而回滚。需要客户端重同步判断最终状态。

这里的事件顺序是服务端逻辑合同，不等于任意部署中的客户端都必然按事件间隔收到数据。2026-09-09修复后，LLM流使用原生异步迭代，检索、会话读写、引用提取和持久化等同步服务通过线程下放让出事件循环；本地Windows真实TCP回归中，带人工间隔的delta在响应结束前逐行到达，并发健康检查不受等待中的检索阻塞。详见[BUG-004](../测试/BUG-004-流式响应缓冲至完成时一次性输出.md#regression)。反向代理仍可能另行缓冲，因此逻辑协议、本地传输和目标部署验收继续分层记录。

## 4. 来源与预览

回答中的【来源N】只映射当前retrieval列表。接口保留citations字段，但内容为有效最终TopK来源全集；cited_in_answer仅按正式正文中的有效编号标记，思考/历史中的编号不计入。前端统一标题为“本轮检索来源”，分“正文已引用/正文未引用”，组内保留检索顺序和原编号。同一文档不同chunk可分属两组，不新增文档聚合或句级高亮。拒答且无标记时全部为未引用；真正无有效检索结果时来源为空，不补造资料。

结构化来源仍包含document_id、chunk_id、unit_id、parser_version、locator和offset。预览接口与chunk高亮不变；抽屉打开动画结束后定位首个可见高亮，图片加载后校正，用户主动滚动后停止自动校正。旧消息缺少cited_in_answer时按已引用兼容，无法补回历史中未保存的召回来源；本次来源字段不新增数据库迁移。

回答提示词统一约束证据不足、部分可回答和冲突情况，不加入硬门控或额外模型裁判。每轮新问题重新检索，改写按开关/历史条件执行且失败退回原问题；幂等重放保留首次结果。本轮来源编号从当前结果重新映射，不能沿用历史编号。验收见[TEST-003](../测试/TEST-003-会话引用与流式协议.md#current-policy)。

接口GET /api/citations/{document_id}/chunks/{chunk_id}/preview；文档全文接口GET /api/documents/id/{document_id}/preview。失效引用、版本冲突和错误定位应明确失败，不从其他文档猜测来源。

## 5. 安全与取舍

历史正文、候选全文、OCR图像和Trace都可能含业务资料，可信本地访问是当前前提。流式状态比一次JSON响应复杂，因此客户端要处理分块跨行、异常结束、重试与409。旧page_store等兼容路径保留，不替代structured-v2主实现。

## 会话编辑、重新生成与范围快照（2026-10-26）

ChatRequest新增replace_message_id；目标必须属于该会话且为非pending用户消息，expected_last_message_id对比当前全部消息的尾部。每次重新生成分配新request_id；相同请求仅重放完成结果，内容/范围变更拒绝。沿用会话级pending互斥，防止另一轮追加或覆盖穿插。

保存的是标签路径选择，不冻结当时的文档集合；重新生成使用当前资料和设置。SQLite v6新增messages.retrieval_tags_json和chat_replacements暂存表；消息仍按sequence保存，后者仅记录覆盖请求与目标身份，不是分支历史。begin_chat仅记录pending请求和暂存参数，不改原消息；改写和回答均只读取目标sequence之前的complete消息。complete_chat在事务内再次核对目标请求身份和尾部，清理旧目标/后续请求与消息，更新目标用户消息并写入新答案；旧助手Trace随消息级联删除，新Trace沿用既有保存流程。失败/中断只改变新请求状态，原历史不动。实现见[DEV-005](../开发/DEV-005-会话流式问答.md#message-regeneration)，验证见[TEST-003](../测试/TEST-003-会话引用与流式协议.md#message-regeneration)。
